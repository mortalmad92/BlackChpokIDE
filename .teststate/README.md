# Реєстр тестів — читати ПЕРЕД запуском тестів

Ця тека існує тому, що прогін повного набору коштує **~210 секунд**, і
запускати його щоразу, коли нічого не змінилось, — марна трата часу.

---

## 1. Головне правило для будь-якого агента (навіть не цього)

```
python tools/test_ledger.py status      # ЗАВЖДИ спершу це
```

Далі:

| Що показує `status` | Що робити |
|---|---|
| «пройдено, код не змінювався» | **НЕ запускати.** Тест уже перевірений на цьому коді |
| «застарів (код змінився)» | запустити |
| «не запускався» | запустити |
| «ПАДАЄ» | запустити, подивитись причину |

```
python tools/test_ledger.py run         # запустить ЛИШЕ застарілі
```

Це все. Реєстр сам визначає, що саме змінилось: відбиток кожного тесту
складається з **його власного файлу** плюс **тих модулів пакета, назви яких
згадані в його коді**. Правка `chat_panel.py` не змушує перезапускати
`test_neuromesh`.

---

## 2. Як це працює (щоб можна було довіряти)

* `ledger.json` — машинний стан: для кожного тесту зберігається
  відбиток коду, статус, час, тривалість, список залежностей і хвіст
  виводу при падінні.
* `STATUS.md` — той самий стан, але таблицею для людини й для читання
  будь-якою іншою мовою чи інструментом.
* Відбиток — `sha256` від вмісту файлу тесту **і** файлів підозрюваних
  залежностей. Однакова сума = код не змінювався = тест уже актуальний.
* Падіння має пріоритет: поки тест «ПАДАЄ», він запускається завжди,
  навіть якщо відбиток збігається.

Жодного приховування: `status` завжди показує й кількість «пройдено, код не
змінювався», тож видно, на чому саме ґрунтується рішення «не запускати».

---

## 3. Команди

```powershell
# стан без запуску (швидко, ~1 с)
python tools/test_ledger.py status
python tools/test_ledger.py status --all      # разом із пройденими

# запустити лише те, що застаріло або ніколи не бігало
python tools/test_ledger.py run

# примусово все (коли є сумнів або після великої правки)
python tools/test_ledger.py run --all

# конкретні тести
python tools/test_ledger.py run tests/test_chat_store.py

# вручну поставити стан (напр. перевірив очима й переконався)
python tools/test_ledger.py mark tests/test_shell.py pass --note "перевірено вручну"

# зафіксувати базовий стан після повного зеленого прогону
python tools/test_ledger.py seed --evidence "python -m unittest discover -s tests -> Ran 2058, OK"

# очистити (наступний прогін запустить усе)
python tools/test_ledger.py forget
```

## 4. Поточний базовий стан

Зафіксовано **2026-11-10**:

```
python -m unittest discover -s tests
→ Ran 2058 tests in 206 s · OK (skipped=2)
```

Усі 124 модулі в теці `tests/` записані як пройдені на коді цієї ревізії.
Доказ і команда — у полі `evidence` записів `ledger.json`.

## 5. Відомі особливості (щоб не приймати їх за регресії)

**Два вікна IDE одночасно.** `tests/test_shell.py` та інші живі
GUI-перевірки відкривають справжнє вікно. Якщо паралельно запущено
`tests/live_every_button.py` або інший GUI-тест, вони заважають одне
одному (спільний `BLACKCHPOK_HOME`, боротьба за фокус), і `test_shell`
може впасти на перевірці ширини панелі.

* Заміряно: окремо `test_shell` проходить **4 прогони з 4**.
* Тому живі GUI-прогони запускайте **послідовно**, не паралельно.

**`BLACKCHPOK_NO_SAVE=1`.** Реєстр виставляє його сам: тести не мають
перезаписувати справжні налаштування користувача.

---

## 6. Чому не `pytest --lf`

`pytest` тут не використовується: проєкт на чистому `unittest`, а частина
тестів — скрипти з власним `main()`. Реєстр працює з обома типами й не
додає залежностей.
