# Чому «увімкнув власний рушій — все одно не працює» і звідки нулі в статистиці

Дата: 2026-11-10. Обидва дефекти зі скріншота користувача, обидва
підтверджені запуском.

---

## 1. Прапорець рушія не перемикав адресу

### Що бачив користувач

```
Не вдалось з'єднатися з локальним сервером http://127.0.0.1:8080/v1/chat/completions.
Перевір, чи ви запущений LM Studio — Developer → Start Server, або що адреса
вказана правильно. Деталі: [WinError 10061] No connection could be made because
the target machine actively refused it.
```

Прапорець «Використовувати власний рушій» стояв увімкнений.

### Справжній стан налаштувань (прочитано з диска)

```
llm.base_url       = http://127.0.0.1:8080/v1     ← агент іде СЮДИ
engine.native      = True                          ← прапорець увімкнено
engine.auto_start  = False                         ← модель не завантажиться
engine.ctx_size    = 32768
```

### Корінь

`SettingsDialog._save()` зберігав **лише прапорець**:

```python
s.engine.native = bool(...native_enabled_var.get())
```

Адресу ніхто не змінював. Агент бачив `http://127.0.0.1:8080/v1`, де нічого
не слухає, і йшов у мережу. Інтерфейс при цьому показував «вбудований
рушій» — бо підпис береться з прапорця, а запит — з адреси.

Друга частина: `auto_start = False` лишився від хмарного агента
(`_activate_cloud_agent` ставить його в `False` і не повертає). Без
автозапуску модель не завантажується у рушій узагалі.

### Виправлення

**1. Збереження перемикає все разом** (`settings_dialog.py`):

```python
if s.engine.native:
    s.llm.base_url = bridge.EMBEDDED_URL   # native://blackchpok
    s.llm.api_key = "local"
    s.llm.auto_detect = False
    s.engine.auto_start = True             # без цього модель не завантажиться
```

**2. Міграція при читанні** (`config.py`, `Settings.load`): якщо
`engine.native` увімкнено, а адреса HTTP — вона виправляється на
`native://blackchpok`, а `auto_start` повертається в `True`. Це лікує
**наявний** файл користувача без потреби відкривати налаштування ще раз.
Перевірено на справжньому `settings.json`:

```
ДО:    base_url = http://127.0.0.1:8080/v1 · auto_start = False
ПІСЛЯ: base_url = native://blackchpok        · auto_start = True
```

**3. Збереження налаштувань справді вмикає рушій** — новий метод
`_apply_engine_choice()`: якщо прапорець увімкнено, а модель не
завантажена — вантажить її; якщо вимкнено — звільняє відеопам'ять.

## 2. `main thread is not in main loop` — чат не перемикався

### Що було

`_on_native_model()` кличеться з **фонового** потоку автозапуску
(`_auto_setup_in_background` → `_autostart_local_model`). Усередині він
чіпав віджети:

```
RuntimeError: main thread is not in main loop
  File "main_window.py", line 7325, in set_status
    self.status_label.configure(text=text)
```

Через це перемикання на вбудований рушій **не завершувалось**: модель
завантажена, а `llm.base_url` лишався старим.

### Виправлення

Уся робота з віджетами винесена в `_ui_call` (виконується в головному
потоці). Налаштування й `agent.llm_settings` змінюються напряму в потоці —
це чистий Python, tkinter не потрібен:

```python
self.settings.llm.base_url = bridge.EMBEDDED_URL
self.agent.llm_settings = self.settings.llm      # агент бачить нову адресу
self._ui_call(apply_ui)                          # підписи — у головному
```

## 3. Статистика показувала нулі

### Що бачив користувач

Шкала контексту: `0 / 32.8K`, «Використано 0%», усі категорії — `0`.

### Корінь (виміряно)

Слухач подій агента показав:

```
усі види подій: ['status', 'assistant', 'done']
подій stats: 0
```

**Шлях `_chat_only` (звичайна розмова) не емітував подію `stats` узагалі.**
Будь-яке «привіт», «дякую», «поясни» йшло цим шляхом — і шкала лишалась на
нулі, хоч модель реально витратила тисячі токенів.

### Виправлення

1. **Спільний метод `_publish_stats()`** — і для роботи з інструментами, і
   для розмови. Однаковий облік на обох шляхах.
2. **Швидкість власного рушія** тепер читається: вона лежить не в
   `usage["timings"]` (як у llama-server), а в `usage["native"]`:

   ```json
   "native": {"tokens_per_second": 31.5,
              "prompt_tokens_per_second": 581.0,
              "generated_tokens": 30, "prompt_tokens": 120}
   ```

3. **Ліміт контексту — з РЕАЛЬНО завантаженої моделі.** `_probe_server_context`
   тепер спершу питає нативний рушій (`describe()["context_actual"]`), бо
   `server_state` описує HTTP-сервер і про `llama.dll` не знає нічого.
4. **Пріоритет ліміту у шкалі.** `StatsBar.set_stats` брав
   `stats.context_limit` із нового знімка й **перебивав** правильний ліміт —
   шкала показувала `0 / 8K`, хоч модель працює з 16K. Тепер головним є
   ліміт, який уже застосовано з завантаженої моделі.

### Перевірено живим прогоном

```
prompt: 7442 | completion: 17 | limit: 32768
speed: 8.48 ток/с | speed_text: 8 ток/с
fill_text: 23%
```

Усі числа — від рушія. Жодного «приблизно».
