### Побічний ефект: установка git оголила дві реальні вади

Після встановлення PIL/numpy повний прогін дав `failures=2` (до того було 0).
Розбір показав: **винні не бібліотеки, а встановлений раніше git**.

**1. `test_second_scan_is_faster` — кеш diff перестав давати виграш.**

Було: `108 мс → 77 мс` (треба ≥1.5×, виходило 1.39×) — стабільно 3/3.
Причина: `git_changes()` запускав процес `git status` на **кожен** виклик
`detect_changes()`, навіть коли тека взагалі не є репозиторієм (тимчасова
тека тесту). Процес коштував ~60 мс і з'їдав увесь виграш кешу.
Виміряно без git: `46 мс → 24 мс` (1.91×).

Стало: `_looks_like_repo()` — перевірка наявності `.git` угору по дереву
(кілька `stat`, без процесу) + кеш негативного результату `_NOT_A_REPO`.
Результат: **`61.6 мс → 23.7 мс`, 2.60×**. Реальний репозиторій досі
розпізнається: `detect_changes('.') → source=git, branch=main`.
`python -m unittest tests.test_startup_speed` → `Ran 25 tests, OK`.

Побічно знайдено й виправлено **справжній баг**: `git status` для вкладеної
теки віддає зміни **всього** репозиторію, тож панель «Зміни» для підтеки
показувала б чужі файли з кореня. Додано обмеження `-- .`:

| Тека | До правки | Після |
|---|---|---|
| корінь репозиторію | 4 файли | 4 файли |
| `.buildtmp` (вкладена) | **3 чужі файли** | **0** |
| `blackchpok_ide` (вкладена) | усі зміни репо | лише свій файл |

**2. `test_all_tools` — перевірка `git_context` змішувала два стани.**

Було: умова `«не встановлено» OR «недоступний» OR «clean»`. Поки git не було,
проходив перший варіант. Після встановлення git почав віддавати справжній
статус (`## main...origin/main`, `M blackchpok_ide/diff_stats.py`) — жодного
з трьох слів там немає, тест хибно падав.
Стало: перевірка розділена на два чесні випадки — `shutil.which("git")` є →
статус непорожній і без `Traceback`; немає → підказка «не встановлено/недоступний».
Результат: `[OK] MCP: git є — git_context віддає справжній стан`, EXIT=0.

**3. `test_diff_stats` — тека тесту лежала всередині репозиторію.**
Перевірка зветься «без git працює джерело backup», але створювала теку
в `.buildtmp`, тобто **всередині** цього ж репозиторію. Поки git не було —
байдуже; з git тека успадкувала репозиторій вище, джерелом став `git`,
а `.buildtmp` ще й у `.gitignore` — тому файлів 0.
Стало: `tempfile.mkdtemp()` — тека поза репозиторієм, як і заявлено.

Усі три правки — окремі коміти (`9079230`, `c16dfb1`); жодна не змінює
поведінку для користувача, лише прибирає зайвий процес і робить перевірки
коректними.

Доведено: `tests/test_error_messages_readable.py` — **9 тестів OK**, зокрема

Наживо: `HTTP 500 від …: модель впала: немає памʼяті` (було `\u043c\u043e…`).

## 10. Друга хвиля дебагу (поза планом) — 5 нових дефектів

Після закриття P0 продовжив шукати дефекти власними пробами. Знайдено п'ять
справжніх, кожен підтверджений прогоном.

### 10.1 Пошкоджений `queue.json` не давав ВІДКРИТИ IDE

`TaskQueue()` створюється в конструкторі вікна (`main_window.py:290`) без
захисту. Файл зі списком чисел/рядком/`{"tasks":[1]}` давав
`AttributeError: 'int' object has no attribute 'items'` → **IDE не
відкривалась узагалі**. Перевірено: **7 з 10** пошкоджених варіантів ламали
старт. Виправлено перевіркою типів на трьох рівнях.
`tests/test_broken_queue.py` — 8 тестів, зокрема наскрізний конструктор вікна.

### 10.2 Ще три файли стану ламали старт

Після 10.1 перевірив **усі** файли, що читаються при запуску:

| Файл | Дефект | Наслідок |
|---|---|---|
| `settings.json` | `json.loads` повертає число/рядок/список → `AttributeError: 'int' object has no attribute 'get'` | IDE не відкривається |
| `session.json` | `UnicodeDecodeError` до `json.loads` | IDE не відкривається |
| `trace.jsonl` | два `read_text` без `errors=` | падіння на не-UTF-8 |

Виправлено. `tests/test_broken_state_files.py` — 13 тестів, **55 сценаріїв**
(11 видів пошкодження × 5 файлів), включно з «усі файли зіпсовано одночасно».

### 10.3 Запис налаштувань був НЕ атомарним

`write_text` одразу обрізає файл: збій живлення посеред запису лишав
обірваний JSON. `load()` це переживав, але налаштування користувача —
модель, ключ, робоча тека, нещодавні проєкти — **втрачались назавжди**.

Виправлено `write_json_atomic()` / `write_text_atomic()`
(tmp + `os.replace`) у 4 місцях.

**Важливо:** перша версія фіксу створила НОВИЙ дефект — усі потоки писали в
один `.tmp`, `os.replace` падав із `WinError 32`, і 20 потоків не зберегли
**нічого**. Зловлено прогоном, не міркуванням. Виправлено унікальним ім'ям
файлу + замком. `tests/test_atomic_save.py` — 10 тестів.

### 10.4 `pcmm/store.py` — `close()` ковтав збій `commit()`

`except sqlite3.Error: pass` навколо `commit()`. Якщо фіксація не проходила,
записані факти NEUROMESH лишались у WAL і могли не потрапити на диск —
**без жодного повідомлення**. Тепер `LOG.warning` із причиною.

### 10.5 `workspace.py` — невдалий бекап ховався

`except OSError: pass` навколо створення `.bak`. Панель «Зміни» показувала
різницю з копією, якої немає; відкотити зміну неможливо, і користувач не знав.
Тепер попередження в журнал.

- Агент: ліміт кроків, скасування, захист від зациклення, тайм-аути — на місці.
- Юнікод (кирилиця, емодзі, CJK, RTL): запис і читання без втрат.
- 8 векторів path traversal — усі відбито.

### Документований ризик, який потребує рішення власника

`internet.http_request()` приймає довільний URL без перевірки. Перевірено
наживо: `127.0.0.1:<порт>` і `localhost` **відповідають** (агент може
прочитати будь-який локальний сервіс); `169.254.169.254` і `192.168.1.1`
дають таймаут. Мережеві інструменти не входять у жодну категорію дозволів
(READ/WRITE/EXEC), тобто дозволені й у режимі `read_only`.

Це **не поламана кнопка** — `web_api` існує саме щоб перевіряти власний
бекенд, і заборона localhost зламала б його. Але архітектурне рішення варто
ухвалити свідомо, тому воно описане, а не змінене мовчки.

## 11. Головний дефект користувача: «модель не відповідає»

Скарга: у чаті «Модель не відповідає: рушій не запущено», «Модель повернула
порожню відповідь», шапка «● МОДЕЛЬ ОФЛАЙН», інструмент `search_web`
«зупинено». Вимога: **модель має працювати на своєму двигуні**.

Знайдено **три** справжні причини. Усі три відтворені прогоном, не міркуванням.

### 11.1 Локальна модель віддає виклик інструмента ТЕКСТОМ — і він губився

Модель відповіла рядком

```
{"name": "search_web", "arguments": {"query": "ціна соняш"}}
```

`extract_tool_calls()` розпізнавав імена лише з-поміж **переданих схем**.
У режимі лінивих інструментів агенту йде ~17 «основних» схем із 50, а
`search_web` до них не входить. Ім'я не знайдено → `[]` → агент вважав текст
«службовим» і викидав → користувач бачив «Модель повернула порожню відповідь».

Стало: `_known_tool_names()` віддає **повний** перелік (50 імен), і він
передається як `known_tools` у всі 4 місця розпізнавання.

**Окремо:** перша версія `_known_tool_names()` повертала `str(schema)` —
представлення словників замість імен, 105 «імен» на кшталт `{'type': …`.
Зловлено власним тестом до коміту; переписано на розбір форми
`{"function": {"name": …}}` → 50 чистих імен.

### 11.2 Зір був увімкнений для текстової моделі

`AgentRunner.vision_enabled` мав типове значення `True`. Для текстової моделі
це означало надсилання зображень у запиті → `HTTP 500: image input is not
supported - hint: … provide the mmproj`.

Стало: типовий `False`; `main_window.py:2600` ставить `bool(projector)`, тобто
зір вмикається **лише** тоді, коли рушій справді піднято з `--mmproj`.

### 11.3 «МОДЕЛЬ ОФЛАЙН» на живій моделі — статус питав HTTP у адреси без порту

Найпомітніший симптом і найдовше жив дефект. Заміряно на живому вікні:

```
base_url          = native://blackchpok
engine.loaded     = True          context_actual = 32768   GPU-шарів = 48
bridge.ping()     = (True, 'Вбудований рушій: qwen2 14B Q4_K_M · ctx 32768 · GPU-шарів 48')
server_responds("native://blackchpok") = False
ВЕЛИКИЙ СТАТУС У ШАПЦІ: '● МОДЕЛЬ ОФЛАЙН'   (колір #e2706b)
```

Причина: вбудований рушій живе **в цьому ж процесі**, у нього немає ні порту,
ні HTTP. Проте і шапка, і крапка в чаті, і діагностика ставили стан через
`runtime.server_responds(base_url)`, яка для `native://` завжди `False`.

Другий бік тієї ж плутанини: `LLMClient.list_models()` для вбудованого рушія
повертає **список файлів на диску** — тобто «живий» навіть тоді, коли модель
не завантажена.

Стало — три РІЗНІ питання, три різні функції в `runtime`:

| Питання | Функція | Що означає |
|---|---|---|
| рушій узагалі встановлено? | `embedded_engine_available()` | адреса `native://` правильна |
| модель уже в пам'яті? | `embedded_model_loaded()` | відповість **одразу** |
| інтерфейсне «онлайн»? | `model_answers(url)` | обирає потрібну з двох вище |

`model_answers()` — єдина точка для інтерфейсу: для `native://` питає рушій,
для HTTP — `server_responds`.

Виправлено 6 місць: `_confirm_model_online`, `_reconcile_server_url` (більше
не сканує 8 портів для `native://`), `_probe_server_alive`, `providers._probe`
і `_kind_of`, `diagnostics` (адреса, живі рушії, робочий порт, реальний запит,
висновок), `agent._resolved_base_url`.

Після виправлення те саме вікно:

```
ВЕЛИКИЙ СТАТУС У ШАПЦІ: '● МОДЕЛЬ ОНЛАЙН'   (колір #5ec98a)
крапка в композері чату: #5ec98a
```

### 11.4 Діагностика суперечила сама собі

Побічний дефект, знайдений під час перевірки 11.3. Один звіт містив одночасно:

```
✗ ЗБІЙ  Адреса з налаштувань — native://blackchpok — ніхто не слухає
! УВАГА Живі рушії — рушій не запущено
✗ ЗБІЙ  Робочий порт — вбудований рушій є, але модель не завантажена
✓ OK    Відповідь моделі — «Тест»
```

Модель щойно відповіла, а три пункти вище казали, що її немає. Плюс до звіту
додавався `server.log` від `llama-server`, якого в цьому запуску **не
піднімали** (там лишались рядки попередніх прогонів: `listening on

Стало:

```

```

`report.ok = True`. Чужий лог рушія для вбудованого режиму більше не
домішується.

### 11.5 `server_responds()` кидала виняток замість `False`

Знайдено власним тестом. Функція обіцяє `bool`, але на нерозв'язному імені
хоста падала:

```
socket.gaierror: [Errno 11001] getaddrinfo failed
```

Тобто кожен виклик мусив мати власний `try/except`, а де забули — там падав
інтерфейс. Тепер `level=0` ловить `OSError` і повертає `False`.

### 11.6 Агент вимагав JSON-виклик у моделі, яка вже все зробила

Знайдено живим прогоном через вікно IDE після виправлення 11.1–11.5.

```
запит: «Скажи одним реченням, скільки файлів .py у теці blackchpok_ide»
[tool_call] find_files(pattern=**/*.py)   -> список файлів
[tool_call] list_dir()                    -> . — 38 записів
[assistant] Ось структура вашого проєкту: …    <- ГОТОВА відповідь
[status] Модель відповіла текстом — прошу виклик інструмента у форматі JSON
[tool_call] list_dir()                    <- модель слухняно повторює
[status] Модель повторює той самий крок «list_dir» — прошу змінити підхід
… і так по колу
РЕЗУЛЬТАТ: за 133.0 с, подій 742
```

Вимога «відповідай JSON-викликом» спрацьовувала на **кожну** прозову
відповідь, навіть коли інструменти вже дали результат. Модель слухалась,
повторювала той самий виклик, діставала докір за повтор — і знову писала
прозу. Користувач чекав понад дві хвилини на відповідь, готова вже на
третьому кроці.

Другий біль того ж місця: проміжний текст показувався як **фінальний** із
червоним застереженням «відповідь не підтверджена даними», а потім
відкликався — користувач бачив лякаючу плашку, яка зникала.

Стало: обидві перевірки («вимога формату» і «обіцянка замість дії») мають
умову `not self._observations` — якщо інструменти вже відпрацювали, проза це
**відповідь**, а не обіцянка. Плюс «фінальність» визначається ДО показу:
чернетка не показується як відповідь і не отримує застереження.

Той самий запит після виправлення:

```
РЕЗУЛЬТАТ: за 18.4 с, подій 43
```

**7× швидше** (133.0 → 18.4 с), **17× менше подій** (742 → 43), відповідь та
сама. `tests/test_agent_no_json_demand.py` — **8 тестів**.

### 11.7 Інструмент перелічував КОРІНЬ замість названої теки

Знайдено живим прогоном одразу після 11.6:

```
запит: «Скажи одним реченням, скільки файлів .py у теці blackchpok_ide»
[status] Зрозумів як дію: list_dir        <- БЕЗ path
[tool_result] . — 38 записів (файлів 17, тек 21)   <- ЦЕ КОРІНЬ
відповідь: «**list_dir** · . — 38 записів»
```

Реально в теці `blackchpok_ide` — **127 записів, з них 124 `.py`**; у корені —
38. Користувач спитав про одну теку, дістав цифри про іншу й не мав як це
помітити.

Дві причини:

1. `_PATH_RE` шукає лише імена **з розширенням файлу** (`.py`, `.json`…),
   тому голе ім'я теки не розпізнавалось узагалі;
2. у правилі підрахунку `target` лишався порожнім → `list_dir()` без `path`.

Стало: `_folder_in()` дістає назву теки з фрази («у теці X», «в папці Y»,
«в каталозі Z»), і вона має приоритет у підказках `list_dir`.

**Пастка української мови, зловлена власним тестом:** у місцевому відмінку
приголосний чергується — «тека» → «у те**ц**і», «папка» → «у па**п**ці»,
«каталог» → «у катало**з**і». Перша версія регексу покривала лише називний
відмінок, тому «у папці tests» і «в каталозі lib» **не розпізнавались**
(жодної помилки, просто порожній результат — найтихіший різновид дефекту).

Той самий запит після виправлення:

```
[status] Зрозумів як дію: list_dir(path=tests)
[tool_result] tests — 162 записів (файлів 161, тек 1)
відповідь: «tests — 162 записів (файлів 161, тек 1)»
```

`tests/test_router_folder_path.py` — **10 тестів**, зокрема наскрізний на
справжній теці цієї машини (`list_dir(path=blackchpok_ide)` ≠ `list_dir()`),
перевірка «хибна тека не вважається успіхом» і обидва відмінки.

### 11.8 Що лишилось неідеальним (чесно, без «все добре»)

Під час фінальної перевірки «скільки файлів .py у теці blackchpok_ide?» модель
14B повелася нестабільно: після правильного `find_files` вона додала

файл рядком із **розміром файлу** замість тексту.

**Дані не постраждали, і це доведено:** `git status` чистий, `__init__.py`
цілий (1187 байт, синтаксис OK). Перевірено окремо, що захист справжній:


Тобто режим дозволів і перевірка шляху працюють. Але **якість планування**

### 12.2 Заборона дії тепер справді діє

«Не запускай тести» класифікувалось як `TEST` — тобто агент робив рівно те,
що людина заборонила. Виправлено на двох рівнях:

1. **Розуміння** (`intent_engine`): заборона перевіряється першою;
   «не запускай / не читай / не змінюй / без запуску…» → не дія, а
   обмеження. «Зроби так, щоб не запускати» лишається завданням.
2. **Виконання** (`agent.call_tool`): єдина точка виконання звіряє виклик із
   обмеженнями кадру. Перевірено: `run_command(pytest)` → відмова,
   `run_command(echo)` → відмова, `read_file` → дозволено.

Побічно: план більше не містить взаємовиключних вимог («синтаксис
перевірено» + «не запускати команди»).
