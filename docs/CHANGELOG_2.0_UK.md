# BlackChpok IDE 2.0 — звіт про модернізацію

Цей документ описує **фактично виконану** роботу над IDE: що було зламано,

що виправлено, що додано і як це перевірено. Усі твердження тут

підкріплені конкретними прогонами, команди яких наведені в кінці.

Версія: `1.7.1` → `2.0.0` (див. `blackchpok_ide/config.py`).

---

## 1. Головний баг: новий чат «знищував» попередній

### Що насправді відбувалось

Повідомлення й записи чатів зберігались правильно — губився **контекст

агента**. У програмі була ОДНА сесія `AgentSession` на весь застосунок

(`main_window.py`, `self.agent = AgentRunner(...)` — створюється один раз).

Наслідки:

* після перемикання на інший чат модель не бачила жодного попереднього

  кроку — «продовжити розмову» було неможливо;

* якщо сесію не очищали, у новий чат просочувався контекст **сусіднього**;

* кроки черги викликали `start(fresh=True)`, що стирало контекст поточного

  чату;

* натискання «Новий чат» під час роботи агента очищало сесію, у яку

  фоновий потік ще дописував, — відповідь зникала.

Окремо знайдено в журналі `ide.log` помилку, що валила весь цикл агента:

```

UnboundLocalError: cannot access local variable 'exc'

  agent.py, у _broken_python()

```

### Що зроблено

1. **Контекст належить чату.** У `chat_store.Chat` додано поле `context`

   (повідомлення у форматі OpenAI, разом із `tool_calls`/`tool_call_id`).

2. `AgentSession.snapshot()` / `AgentSession.restore()` — знімок і

   відновлення контексту.

3. `ChatStore.store_context()` / `load_context()` — збереження на диск.

4. Вікно (`main_window.py`):

   * `open_chat` — зберігає контекст попереднього чату й відновлює новий;

   * `new_chat_session` — зберігає попередній, очищає сесію, **відмовляє**,

     якщо агент працює;

   * `_remember_message` — зберігає контекст разом із повідомленням;

   * `on_close` — зберігає контекст перед виходом;

   * `close_chat` / `_after_chats_cleared` — очищають сесію.

5. Для старих чатів (без поля `context`) контекст збирається з видимих

   повідомлень — `_context_from_messages`.

### Перевірено наживо

`python .buildtmp/probe_chat_isolation.py` — 19 перевірок, зокрема:

* 10 чатів мають 10 різних `id`;

* у кожному рівно своє повідомлення (жодного перехресного);

* після **перезапуску** вікна всі 10 на місці;

* контекст агента відповідає відкритому чату (`повідомлення 3` → саме воно);

* новий чат має порожній контекст.

## 2. Нова верхня шапка та Command Palette

### Реєстр команд (`commands.py`, новий модуль)

Єдине джерело правди: 92 команди з ключем, категорією, гарячими клавішами,

рівнем (`primary` = кнопка в шапці, `menu` = випадаюче меню, `palette` =

лише пошук) і предикатом доступності. Меню, шапка й палітра беруть команди

**звідси**, тому більше немає трьох списків, які розходяться.

### Шапка (`header_bar.py`, новий модуль)

```

◈ BLACKCHPOK │ проєкт ▾ │ ＋ ▤ ⤓ ↶ ↷ │ ◈ Агент ▾ ⊟ модель ▾ ● сервер │ ▶ ⏹ ⌨ 🌐 │ ⑂ гілка ▾ │ ⌕ Команди ⚙ ⋯

```

* логотип, назва відкритого проєкту (меню: відкрити / створити / останні);

* швидкі дії файлів: створити, відкрити, зберегти, скасувати, повторити;

* перемикач агента, вибір моделі, **справжній** індикатор стану сервера;

* запуск / зупинка проєкту, термінал, **LIVE BROWSER**;

* Git: гілка, кількість змін, commit, push, pull;

* пошук команд (Ctrl+Shift+P), налаштування, «⋯» з усіма командами.

### Адаптивність

Шапка **не стискає** кнопки й не робить горизонтальної прокрутки: при

звуженні вона прибирає цілі групи (`wide` → `compact` → `narrow`), і кожна

прибрана команда лишається в меню «⋯». Live Browser не ховається ніколи.

### Старі меню збережені

Файл / Правка / Вигляд / Агент / Git / Довідка — на місці (75 пунктів).

Перевірка «жодної втраченої команди» є в тестах: кожна дія з `_build_menu`

мусить бути зареєстрована в `commands` (тест `test_v2_audit.py`).

## 3. Live Browser: сторінка стала даними

### Що було

Вбудований браузер — це окремий процес Chromium, вставлений у вікно через

`SetParent`. З коду було видно лише «вікно», а не сторінку: ні консолі, ні

помилок, ні DOM. Через це не існувало ні інспектора елементів, ні видимих

помилок.

### Що додано

**`cdp.py` (новий модуль)** — справжній клієнт Chrome DevTools Protocol

без жодної нової залежності: WebSocket-кадри зібрано вручну (RFC 6455,

маскування клієнта, фрагментація, ping/pong).

| Можливість | Реалізація |

| --- | --- |

| Консоль і помилки JS | `Runtime.consoleAPICalled`, `Runtime.exceptionThrown`, `Log.entryAdded` |

| Помилки ресурсів | `Network.loadingFailed` |

| Помилки HTTP | `Network.responseReceived` (4xx/5xx) |

| DOM-інспектор | `Runtime.evaluate` + `elementFromPoint` / `querySelector` |

| Знімок сторінки | `Page.captureScreenshot` (не екран!) |

| Перевірка адаптивності | `Emulation.setDeviceMetricsOverride` |

| Клік по елементу | DOM `click()` (влучає точно, не по координатах) |

| Введення тексту | `Input.insertText`, `Input.dispatchKeyEvent` |

| Аудит сторінки | один запит: посилання, кнопки, форми, зображення, доступність |

Для живої перезагрузки тепер використовується `Page.reload` — раніше кожне

оновлення перезапускало **весь процес** браузера.

### Те, що знайдено й виправлено під час перевірки

* **ASI у JavaScript.** `return` з переносом рядка означає `return;` —

  інспектор повертав `undefined`. Виправлено: виклик в одному рядку зі

  `return`.

* **Розсинхронізація сокета.** Таймаут посеред кадру лишав напівпрочитаний

  кадр, і всі наступні відповіді читались зі зсувом. Тепер читання

  блокуюче, зупиняється закриттям сокета.

* **Хибна вкладка.** `targets[0]` міг бути `about:blank`; тепер обирається

  вкладка з потрібною адресою, і кешована сесія перевіряється на

  відповідність.

### Інструменти агента (8 нових)

`web_url`, `web_console`, `web_inspect`, `web_screenshot`, `web_audit`,

`web_responsive`, `web_click`, `web_type` — у схемах, каталозі для моделі й

журналі з українськими підписами.

### Інспектор у панелі

`live_preview.py`: кнопка «◎» вмикає режим інспектора, клік по елементу

показує тег, CSS-селектор, розміри, позицію й стилі; **«→ Передати агенту»**

вставляє все це в запит (і зберігає те, що користувач уже написав).

### Перевірено наживо

* `python .buildtmp/probe_cdp.py` — **29/29** на справжньому Chrome:

  консоль, помилки JS/ресурсів/HTTP, інспектор, клік, знімок, viewport,

  аудит.

* `python .buildtmp/probe_live_browser.py` — **22/22** у справжньому вікні:

  dev-сервер, сайт у браузері, консоль у панелі, інспектор, передача

  елемента агенту, знімок, аудит, адаптивність, клік змінює DOM.

## 4. Хмарні провайдери: три справжні протоколи

### Що було

Один формат запиту (`/chat/completions` + `Bearer`) до будь-якої адреси.

Для OpenAI, DeepSeek, OpenRouter, Groq, Mistral, Gemini-OpenAI і локальних

серверів це правильно, але:

* **Anthropic** потребує `POST /v1/messages`, заголовки `x-api-key` +

  `anthropic-version`, `system` окремим полем і власний SSE. Запит у

  форматі OpenAI отримував 404 — «підтримка» була фіктивною.

* **Gemini** (нативний) потребує `?key=` і `:generateContent`.

### Що зроблено

`provider_adapters.py` (новий) — три протоколи з автовизначенням за адресою:

`openai` / `anthropic` / `gemini`. Перетворення повідомлень, схем

інструментів, відповідей і використання токенів — для кожного окремо.

Перевірено на справжньому HTTP-сервері (`probe_providers.py`, **28/28**):

шляхи, заголовки авторизації, тіла запитів, розбір відповідей і

`tool_calls` — для всіх трьох протоколів.

### API-ключі

* **DPAPI (Windows).** `secrets.py` (новий): `CryptProtectData` /

  `CryptUnprotectData` через `ctypes`, без залежностей. У файлі —

  `api_key_enc: "dpapi:v1:…"`, відкритого тексту немає.

* **Міграція.** Старий відкритий ключ читається й перешифровується під час

  найближчого збереження.

* **Локальний ключ** (`local`/`lm-studio`) лишається як є — це не секрет.

* **Вичищення логів.** Фільтр журналу прибирає `Bearer …`, `sk-…`,

  `api_key=…`, `?key=…` з КОЖНОГО запису — провайдери іноді повертають

  фрагмент ключа в тілі помилки.

* **Перевірка ключа** більше не блокує вікно: запит іде у фоні (раніше

  інтерфейс завмиравав до 15 с).

## 9. Виправлення зациклення моделі (баг зі скріншота)

Користувач показав скріншот: на запит «яка ціна SOL сьогодні?» модель

зробила **14 однакових викликів** `router:search_web`, у чат висипався

**сирий JSON** виклику як «відповідь», і жодного разу не було сказано

справжньої причини.

### Три окремі дефекти

**1. Сирий JSON виклику показувався користувачу.**

`strip_tool_json` вирізав лише об'єкти, чия назва є **в списку схем**. Модель

вигадує назви (`router:search_web`), яких у схемах немає (MCP не

підключено) — і тоді JSON лишався в тексті. Тепер додано вирізання **за

формою**: об'єкт із ключем назви ТА ключем аргументів є викликом. Справжня

JSON-відповідь (`{"price": 150}`) не чіпається — перевірено 14-ма випадками.

**2. Не було захисту від повторів.**

Цикл ішов до ліміту кроків і показував «Досягнуто ліміт кроків». Тепер

`_RepeatGuard` порівнює пару «виклик + результат»:

* 2-й однаковий результат → моделі дається **конкретна** вказівка змінити

  підхід (а не абстрактне «спробуй інакше»);

* 4-й → робота припиняється з поясненням.

Важливо: різні результати того самого інструмента (напр. дописування в

файл) циклом **не вважаються** — перевірено окремим тестом.

**3. «Спробую інший запит» вважалось відповіддю.**

Модель писала обіцянку замість дії. Тепер такий текст:

* між викликами інструментів — спільна рекомендація моделі діяти;

* як фінальна відповідь — замінюється чесним підсумком: «модель

  зупинилась на обіцянці, нічого не змінилось».

Додатково: на вигаданий інструмент модель тепер отримує перелік

## 11. Справжній HMR (без повного перезавантаження)

Раніше в звіті стояло «справжній HMR не реалізовано». Реалізовано —
`hmr.py` (новий модуль), і він працює **всередині IDE**, а не лише в тесті.

### Що робить

| Тип файлу | Що відбувається |
| --- | --- |
| `.css` | підміна `href` у `<link>` або вмісту `<style>` — **без перезавантаження** |
| `.html` | точкове оновлення `innerHTML`, якщо структура верхнього рівня збігається |
| `.js` / `.ts` | перезавантаження, але **позиція прокрутки відновлюється** |
| інше | пропускається (не впливає на вигляд) |

### Стан сторінки зберігається

Найважливіше — те, що руйнувалось раніше:

* **прокрутка** — не смикається;
* **введений у поля текст** — зберігається (збираємо значення ДО заміни
  розмітки й повертаємо ПІСЛЯ);
* **чекбокси та `<select>`** — теж зберігаються;
* **стан JS** — не скидається, бо сторінка не перезавантажується.

### Знайдені й виправлені дефекти

* **`<script>` у порівнянні структури.** Браузер створює вузол `script`,
  але виконувати його повторно не можна. Через це структура «не
  збігалась», і HMR марно перезавантажував сторінку.
* **Порожні елементи.** `<input>` не має закривного тегу, тому лічильник
  вкладеності більше не повертався до нуля: усі наступні теги помилково
  вважались вкладеними.
* **Втрата введеного тексту** при підміні `innerHTML` (див. вище).

### Фактичні результати

* `probe_hmr.py` — **17/17**: CSS без reload, колір змінився, `boot`
  лічильник лишився 1, текст і прокрутка збережені; HTML оновився
  точково; JS перезавантажив із поверненням прокрутки.
* `probe_hmr_gui.py` — **10/10** у живому вікні IDE: правка `style.css`
  **у редакторі** й `Ctrl+S` → сторінка оновила вигляд, не
  перезавантажившись.

## 13. Агент бачить свій проєкт: скріншоти в інтерфейсі

Раніше в цьому звіті стояло, що скріншоти — «опційні через Pillow».
Насправді вони **не працювали зовсім**: Pillow був закоментований у
`requirements.txt`, і `app_screenshot` щоразу відповідав «немає Pillow».
Інструмент існував у схемах і каталозі для моделі — і був мертвим.

### Що зроблено

**`screenshot.py` (новий модуль) — знімки без жодних залежностей:**

* захоплення через Win32 GDI (`PrintWindow` / `BitBlt`);
* власний PNG-кодер на `zlib` (стандартна бібліотека);
* пошук вікон за заголовком, **класом** і PID;
* робота з **дочірніми** вікнами (вбудований браузер вставлено в IDE
  через `SetParent`, тож `EnumWindows` його не бачив).

**Показ картинки в чаті без Pillow:** Tk 8.6+/9 уміє PNG сам, тому
зображення малюється `tk.PhotoImage` + `subsample` для зменшення. Клік
по картинці відкриває її на весь екран.

**Нові інструменти агента:**

| Інструмент | Що робить |
| --- | --- |
| `project_screenshot` | знімок САМЕ вікна проєкту (живий сайт) |
| `app_screenshot` | без заголовка — вікно проєкту; `title='*'` — весь екран |
| `app_windows` | перелік вікон, які можна зняти (щоб не гадати назву) |
| `app_logs` | журнал запуску застосунку (чому не стартує) |

### Знайдені й виправлені дефекти

* **Мертвий інструмент.** `app_screenshot` вимагав Pillow, якого не було.
* **Чуже вікно.** Пошук «за заголовком Chrome» на машині користувача
  знаходив **сторонній** Chrome — у чаті з'являвся темний незрозумілий
  знімок замість його сайту. Тепер використовується HWND вбудованого
  браузера.
* **Дочірнє вікно не знаходилось.** `EnumWindows` перебирає лише вікна
  верхнього рівня, а браузер у IDE — дочірній. Додано `describe_window`.
* **Весь екран замість сторінки.** Порожній `title` означав «весь екран».
  Тепер це «вікно проєкту», а весь екран — явний `title='*'`.
* **Хибний «успіх».** Обробник, що повертав рядок із «✗», вважався
  успішним — модель думала, що знімок зроблено.
* **Картинка не малювалась** для `project_screenshot` (оброблялись лише дві
  назви інструментів).

### Перевірено наживо (`probe_ui_screenshot.py`, 12/12)

| Перевірка | Результат |
| --- | --- |
| Сайт запущено й показано в Live Browser | так |
| `app_windows` бачить вікна | 8 вікон, серед них вбудований браузер |
| `project_screenshot` | **509×1123** — вікно проєкту, не екран |
| Шлях до PNG повернуто, файл існує | 101 КБ |
| Картка в стрічці чату | додано |
| **У чаті ЗОБРАЖЕННЯ (не текст)** | 1 зображення, 574×240 |
| Клік відкриває збільшений знімок | так |
| `app_logs` показує журнал сервера | так |

### Реальна модель у реальному інтерфейсі (`probe_model_vision.py`, 7/7)

Локальна модель `qwen2.5-coder-14b` у живому вікні IDE:

## 14. Що НЕ зроблено (чесно)

* **Anthropic і Gemini перевірені на справжніх SSE-потоках, але з локальним
  сервером-емулятором**, не з живим API: ключів у середовищі немає
  (\ANTHROPIC_API_KEY\ тощо не задані). Протокол, заголовки, тіла запитів,
  розбір подій і стрімінгу перевірені; для реального виклику потрібен ключ
  користувача.
* **Модель \qwen2.5-coder-14b\ перевірена на кількох сценаріях** (читання,
  створення, правка файлу, стрімінг). Це доводить, що ланцюг «мова →
  інструмент → файл» працює, але не гарантує якість на кожному можливому
  завданні: 14B-модель усе ще може помилятися в складній логіці. Саме для
  цього є захист від зациклення й чесний звіт про збій.
* **HMR не виконує змінений JS без перезавантаження** — це принципове
  обмеження: повторне виконання скрипта в завантаженій сторінці дає подвійні
  обробники подій. Тому JS перезавантажує сторінку (зі збереженням
  прокрутки), а не «гаряче» підмінюється.
* **Виміри продуктивності зроблені на цій машині** (64 ГБ RAM, 12 потоків).
  На слабшому ноутбуці числа будуть іншими — але механізми (обмеження
  контексту, відсікання історії, відмова від повного перезавантаження)
  працюють незалежно від заліза.
* * **Модель описує вигляд за знімком, а не «бачить» його семантично**: локальна qwen2.5-coder-14b не мультимодальна. Вона отримує шлях до PNG і точні дані сторінки (DOM, розміри, стилі через `web_inspect`), але не саму картинку як зображення. Для справжнього «зору» потрібна мультимодальна модель (напр. Qwen2.5-VL) — інтерфейс це вже підтримує: знімок показується в чаті й зберігається на диску.
