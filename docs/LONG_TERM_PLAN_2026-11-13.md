# ДОВГОСТРОКОВИЙ ПЛАН: дебаг і розвиток BlackChpok IDE

Дата: 2026-11-13. Стан на момент написання: **2378 тестів проходять** (було
2058 у базовому стані), 6 раніше «падаючих» живих тестів — зелені.

Ціль плану — те, про що просив користувач: **агент мусить працювати локально

## 1. ГОЛОВНІ ЗНАХІДКИ ЦЬОГО ДНЯ (з доказами)

### 1.1. «CUDA-збій» насправді був НАШИМ скасуванням

Рядок у консолі, який раніше вважали апаратною аварією:

```
graph_compute: ggml_backend_sched_graph_compute_async failed with error 1
llama_decode: failed to decode, ret = 2
```

Перевірено в самій бібліотеці: `ggml_status_to_string(1)` повертає
**`"warning (operation aborted)"`**. Далі `llama_decode` мапить це в `2`
(`DECODE_ABORTED`), і `llama.h` прямо документує: *«aborted (processed
ubatches will remain in the context's memory)»*.

**Висновок:** це штатне скасування генерації, а не збій GPU. Драйвер,
`n_ubatch`, `flash_attn` і квантування KV тут ні до чого. П'ять живих
скриптів «падали» саме на цьому рядку — і причину шукали не там.

### 1.2. Справжній дефект: розсинхрон мітки KV-кешу після скасування

Найважливіша знахідка. Після скасування рушій **лишає** пораховані
ubatch-і в пам'яті, а наш `CacheManager` про них не знав. Відтворено
наживо (RTX 3060, Qwen2.5-Coder-14B, ctx 16384):

```
скасування посеред prefill
  мітка CacheManager (mirror)  : 0
  llama_memory_seq_pos_max     : 1535 → у KV реально 1536 токенів
наступний хід: EngineError: Декодування не вдалось (код -1)
```

Далі ланцюжок: `EngineError` → `LLMError` → `agent._retry_once` повторює
**ту саму зіпсовану** генерацію → контекст заклинює до перезавантаження
моделі. **Ззовні це виглядає як «модель замовкла / програма зависла».**

**Виправлено:** `CacheManager.resync()` + `_verify_against_engine()` —
мітка звіряється з рушієм перед кожним промптом; коди `decode`
розрізняються (`2` = скасування, `-1` = розсинхрон, `-2` = брак пам'яті).
Регресія закріплена в `tests/test_kv_abort_resync.py` (8 тестів).

### 1.3. Агент працював із ПОЛОВИНОЮ контексту

`/props` — це ендпоінт `llama-server`. У вбудованого рушія немає ні порту,
ні HTTP, тому проба завжди падала, і код брав «половину від заявлених»:

```
рушій створено з ctx 16384 → агент працював із 8192
```

Наслідки: бюджет схем падав до 2048, вмикався лінивий режим на 15 схемах
із 52, історія різалась удвічі раніше. **Виправлено:** вікно читається з
контексту в пам'яті (`_embedded_context_window`), без ділення на слоти.

### 1.4. Зависання інтерфейсу (знайдено аудитом, виправлено)

| Місце | Що було | Виправлено |
|---|---|---|
| `_git_badge_state` | до 400 блокуючих `git diff` у GUI-потоці (кожен із таймаутом 20 с) | кеш + один фоновий перерахунок |
| `_idle_tick` | вивантаження VRAM чекало на поточний `llama_decode` | рішення в тіку, вивантаження у фоні |
| `_collect_search` | `while True` без дедлайну — потік не завершувався ніколи | стеля 45 с + чесне повідомлення |
| `_poll_planner` | `after(150)` без ліміту — «міркую…» вічно | 18 с, далі робота без плану |

### 1.5. Тихі дефекти логіки

* `diff_stats.git_changes` — рядок `entries = _parse_porcelain_z(raw)`
  стояв **після** фільтрації за префіксом теки й повністю її відкидав.
  Тобто для вкладеної теки панель «Зміни» показувала чужі файли з кореня.
* `inspect._ctx_candidates` — при явному `ctx` повертав РІВНО одне
  значення, тож «підбір під залізо» фізично не міг зменшити контекст
  (запит 32768 при 12 ГБ VRAM давав 32768 ж). Тепер це стеля драбини.
* `show_shortcuts` — рукописний перелік обіцяв `Ctrl+D`, якого в реєстрі
  немає. Тепер генерується з реєстру.

### 1.6. Чому 5 живих тестів «падали» (і це не були дефекти продукту)

* Фіксоване вікно очікування (4 с) не встигало за справжньою моделлю 14B.
  Тепер чекаємо на **справжню ознаку** завершення, зі стелею 180 с.
* Тести успадковували `chats.json` розробника, і вікно законно
  відновлювало теку `C:\AI\site`. Додано ізоляцію робочої теки.
* `e2e_stabilization_demo` вважав «правдою» лише верхній рівень теки
  (127 файлів), а модель дістала 150 через `find_files` (рекурсивно) —
  **обидва числа правильні**. Тест був неправий, не модель.

## 2. ЩО ВЖЕ ПРАЦЮЄ ДОБРЕ (не ламати)

* **Лінивий реєстр інструментів** (`tool_lazy`): 240 токенів реєстру
  замість 2005 — модель бачить назви, повні схеми — на вимогу через
  `load_tools`, виклик за назвою — `run_tool`.
* **Пам'ять NEUROMESH + RAG**: контекст із бюджетом (`project_context`),
  витіснена історія архівується (`archive_messages`), вектори з кешем.
* **Правило доказів**: вигадане число позначається як непідтверджене —
  перевірено наживо (модель назвала 399 при справжніх 127/150, система
  це зловила).

## 3. ПЛАН ДАЛЬШИХ КРОКІВ (за пріоритетом)

### Пріоритет 1 — надійність агента (без цього решта не має сенсу)

1. **Ресинхронізація замість повного очищення KV.** Зараз при розсинхроні
   кеш чиститься цілком (один повторний prefill). Можна відновлювати
   точніше: `truncate(llama_memory_seq_pos_max + 1)` і повторне декодування
   лише хвоста. Виграш — секунди на кожному скасуванні.
2. **Один контекст на розмову, не на модель.** Довгі чати впираються в
   перерахунок усього промпту. Окремий контекст на чат із власним KV дасть
   справжні «нескінченні чати».
3. **Чесний тайм-аут на кожен крок.** Зараз `DEFAULT_TIMEOUT=600` діє лише
   якщо викликач не передав свій. Крок, що «висить», мусить завершуватись
   із причиною, а не тримати чергу.

### Пріоритет 2 — розуміння людської мови

4. **Розширювати `intent_engine` живими фразами.** Зараз є 12 намірів і
   набір маркерів. Кожну фразу, яку агент зрозумів неправильно, треба
   додавати в тести (`tests/test_plain_language.py`) як регресію.
5. **Плутанина «порахувати» vs «перелічити».** Живий приклад: на
   «скільки Python-файлів у теці» модель бере або `list_dir` (верхній
   рівень), або `find_files` (рекурсивно), і числа різні. Треба явно
   уточнювати в промпті, що саме рахується.
6. **Мова відповіді.** Українська мусить лишатись типовою, навіть коли
   модель схильна відповідати російською (спостережено на Qwen2.5-Coder).

### Пріоритет 3 — економія контексту

7. **Стиснення результатів інструментів на вході, а не після.** Зараз
   великий `read_file` кладе в історію до 25% вікна. Краще — короткий
   екстракт + повний результат у файлі, який модель може дочитати.
8. **Векторний відбір історії.** Замість «викинути найдавніше» — викидати
   найменш релевантне до поточного запиту (NEUROMESH уже має вектори).

### Пріоритет 4 — дрібне, але дратівливе

9. **`changes_panel` чіпає Tk із робочого потоку** (`winfo_exists`,
   `after` не через чергу) — єдине справжнє порушення потокобезпеки,
   знайдене аудитом. Потрібна черга, як в інших панелях.
10. **`editor.highlight_all_matches`** робить тисячі `tag_add` у GUI-потоці
    на великому файлі. Обмежити кількість збігів або винести в фон.
11. **`chat_panel._flush_stream`** перемальовує ВЕСЬ накопичений markdown на
    кожен тік — це O(n²) від довжини відповіді. Малювати інкрементально.

## 4. ЯК ПЕРЕВІРЯТИ (щоб не вигадувати «готово»)

```powershell
# 1. Повний прогін (≈4.5 хв) — еталон
python -m unittest discover -s tests

# 2. Реєстр: що застаріло після правок
python tools/test_ledger.py status
python tools/test_ledger.py run

# 3. Конкретно цей дефект (KV після скасування)
python -m unittest tests.test_kv_abort_resync -v

# 4. Живі прогони — послідовно, не паралельно
python tests/test_cases_live.py
python tests/test_work_log_live.py
python tests/test_rag_ui.py
python tests/test_task_center_live.py
python tests/e2e_stabilization_demo.py
python tests/smoke_gui.py
```

**Правило:** «пройшло» означає, що команда справді виконана й показала
`OK`. Рядки `graph_compute … error 1` у консолі — це скасування, не збій;
але якщо після них наступний хід падає з `код -1`, це регресія
розсинхрону KV.

## 5. ЧОГО НЕ РОБИТИ

* Не «виправляти» CUDA-помилку зменшенням `n_ubatch` — вона не причина.
* Не вимикати тести, щоб «позеленіло». Якщо тест справді застарів —
  переписати ЙОГО ПЕРЕВІРКУ, пояснивши чому (як зроблено з
  `e2e_stabilization_demo`), а не видалити.
* Не тримати всі схеми інструментів у контексті: 52 схеми = 7345 токенів
  із 16384. Лінивість уже працює — її треба зберігати.
