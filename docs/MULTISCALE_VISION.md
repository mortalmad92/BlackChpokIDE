# Multi-scale аналіз скріншотів

Дата: 2026-11-09. Реалізовано й перевірено на реальному знімку 3440×1440.

---

## 1. Проблема, яку це вирішує

Повноекранний знімок 3440×1440 після приведення до ліміту запиту втрачає
дрібний текст. У попередньому аудиті модель на такому знімку **вигадувала**
опис інтерфейсу: назвала панелі, яких не було.

Контрольний експеримент (однакова модель, один знімок, одне питання
«прочитай дослівно перші 3 рядки»):

| Що подано | Відповідь моделі |
|---|---|
| Повний екран 3440×1440 | **«Не розібрано»** |
| Ділянка 1024×1024 із цього ж файлу | **Дослівно 3 рядки тексту + координати** |

Тобто справа не в моделі й не в проєкторі, а в роздільній здатності подачі.

---

## 2. Як працює

```
оригінал 3440×1440
      │
      ├── overview.png         ← зменшене ЦІЛЕ зображення (для композиції)
      │
      └── tiles/               ← ділянки 1024×1024, ВИРІЗАНІ З ОРИГІНАЛУ
            tile-01.png @ (0,0)–(1024,1024)      лівий верх
            tile-02.png @ (839,0)–(1863,1024)    (перекриття 185 px)
            tile-03.png @ (1678,0)–(2702,1024)
            …
```

Ключові рішення:

1. **Ріжемо з оригіналу**, а не зі зменшеної копії. Це принципово: якщо
   спершу зменшити, дрібний текст зникає ще до нарізання.
2. **Перекриття 18%** між сусідніми ділянками: елемент на межі не
   розрізається навпіл.
3. **Координати — в системі оригіналу**, не ділянки.
4. **Огляд зменшується**, ділянки — ніколи.
5. **Межа кількості** (16 ділянок): аналіз не перетворюється на десятки
   запитів до моделі.

---

## 3. Правило невпевненості

Кожна ділянка подається моделі з підписом:

```
[ділянка 2 з 8] лівий верх: прямокутник
x=839..1863, y=0..1024 на оригіналі 1024×1024px.
Якщо напис або елемент нечитабельні — напиши «не розібрано» і вкажи,
де саме. НЕ вигадуй текст, якого не видно. Краще визнати, що не видно,
ніж припустити.
```

Це прямо забороняє моделі заповнювати прогалини здогадами — те саме
«вигадування», яке виправлено в текстовому шляху через правило
NO TOOL EVIDENCE.

## 4. Інструменти для моделі

| Інструмент | Що робить |
|---|---|
| `inspect_screenshot_regions(path, size)` | нарізає великий знімок, повертає шляхи й координати |
| `crop_screenshot(path, x, y, w, h)` | вирізає область БЕЗ масштабування |
| `get_image_dimensions(path)` | розмір у пікселях (PNG/JPEG/BMP) |
| `get_screenshot_metadata(path)` | розмір, формат, вага, історія файлу |
| `capture_screen(region)` | знімок екрана або області |
| `capture_region(x, y, w, h)` | знімок прямокутної області |
| `compare_screenshots(first, second)` | піксельна різниця: відсоток, координати |
| `analyze_visual_difference(first, second)` | числа + вирізані ділянки «до/після» |

Усі 8 інструментів є в схемах (`TOOL_SCHEMAS`) і мають реалізацію —
перевіряється тестом `test_every_schema_has_handler`.

Кожен артефакт пишеться у `%APPDATA%\BlackChpokIDE\screenshots\history.json`:

```json
[{"kind": "crop", "path": "…crop-839_0_900x500.png",
  "source": "…shot-20497265.png", "box": [839, 0, 1739, 500],
  "time": 1794223..., "stamp": "2026-11-09 13:20:37"}]
```

Тримається останні 200 записів. `get_screenshot_metadata` показує історію
конкретного файлу.

## 7. Відоме обмеження: `--image-min-tokens`

Під час перевірки знайдено реальний збій:

```
--image-min-tokens 1600 →
  clip_init: failed to load model '…mmproj.gguf':
  load_hparams: image_max_pixels (802816) is less than
                image_min_pixels (1254400)
```

Сервер не стартував **узагалі**. Перевірено: 1024 працює, 1600 — ні.

Тому:

* `ServerConfig.image_min_tokens` типово **1024**;
* `launch_with_recovery` розпізнає `is_mmproj_failure()` і **повторює запуск
  без проєктора** (модель стає текстовою, але працює);
* ділянки РІЗАЮТЬСЯ з оригіналу, тому їх читабельність не залежить від
  `image-min-tokens`.

---

## 8. Обмеження

* Ділянки подаються моделі **по одній**: аналіз 8 ділянок — це 8 окремих
  запитів. Автоматичного обходу всіх ділянок в одному ході немає: модель
  сама вирішує, скільки ділянок їй потрібно.
* Немає automatic OCR: текст читає модель, а не окремий рушій.
* JPEG підтримується лише для метаданих; нарізання й порівняння працюють
  для PNG (знімки завжди PNG).
