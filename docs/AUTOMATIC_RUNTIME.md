# Автоматичний локальний runtime

Фактичний стан на 2026-11-09, версія 1.7.1.

Документ описує те, що **реалізовано й перевірено**, і чесно позначає те, чого
ще немає.

---

## 1. Принцип

Користувач не встановлює LM Studio, Ollama, Python-пакети й не налаштовує
localhost-API. IDE сама:

1. визначає залізо;
2. завантажує збірку llama.cpp під нього;
3. підбирає модель і параметри запуску;
4. піднімає `llama-server` і чекає справжньої готовності;
5. показує стан у панелі.

---

## 2. Склад

| Модуль | Роль |
|---|---|
| `hardware.py` | визначення RAM/VRAM/CPU, підбір моделі й плану запуску |
| `model_hub.py` | каталог моделей, завантаження з HF, пошук `mmproj` |
| `runtime.py` | встановлення рушія, керування `llama-server`, відновлення |
| `native/` | власний in-process рушій (`llama.dll`), без окремого процесу |
| `first_run.py` | майстер першого запуску |
| `model_hub_panel.py` | інтерфейс хаба |

---

## 3. Запуск і перевірка готовності

```python
from blackchpok_ide import hardware as hw, runtime as rt

profile = hw.detect()
choice  = hw.recommend(profile)          # або конкретна модель

servers, detail = rt.launch_with_recovery(
    model_path, choice=choice, profile=profile,
    alias=model_path.stem, mmproj_path=str(projector or ""),
)
```

`launch_with_recovery` повертає `(список_серверів, повідомлення)`. Порожній
список означає, що не вдалося жодного разу, а `detail` містить справжню
причину останньої спроби.

**Готовність визначається реальним запитом** до `/v1/models`, а не наявністю
файлу GGUF. Сервер вважається готовим лише після HTTP 200 із правильним ключем.

---

## 4. Автоматичне відновлення

`runtime.recovery_steps()` будує план Б — від найкращого до найнадійнішого:

| Крок | Що робить | Ціна |
|---|---|---|
| 1 | штатний план (GPU, 16K, `q8_0`) | — |
| 2 | менший контекст (8K) | трохи менше історії |
| 3 | ще менший (4K) | обмежений контекст |
| 4 | гібрид: половина шарів на GPU | повільніше |
| 5 | гібрид: чверть шарів | ще повільніше |
| 6 | чистий CPU | повільно, але працює |

Правила:

* перехід на наступний крок відбувається **лише** якщо збій схожий на
  проблему пам'яті (`is_gpu_failure`: `CUDA error`, `out of memory`,
  `failed to allocate`, `vulkan error` тощо);
* якщо причина інша (немає файлу, невідома архітектура) — повторювати марно,
  тому цикл зупиняється й показується справжня помилка;
* кожна спроба пише людський статус: «Повторюю запуск простіше: гібрид 24
  шарів · 8K».

### Перевірено наживо

## 5. Відеопам'ять: що враховується

`hardware.fit()` рахує:

* ваги моделі (`approx_gb`);
* KV-кеш: `layers × kv_heads × head_dim × 2 × 2 × ctx`;
* накладні витрати рушія (`RUNTIME_OVERHEAD_GB = 0.7`);
* бюджет VRAM = `vram − 1.0 ГБ` (резерв на драйвер і робочий стіл).

Порядок вибору кешу навмисний: **спершу `q8_0`**, потім точний `f16`.
Замір на RTX 3060 12 ГБ (Qwen2.5-Coder-14B):

| Контекст | Кеш | Швидкість |
|---|---|---|
| 8K | f16 | 32.2 ток/с |
| 8K | q8_0 | 31.6 ток/с |
| 16K | f16 | не влазить → деградація до 14.1 ток/с |
| 16K | q8_0 | 31.7 ток/с |

Тобто `q8_0` дає вдвічі більший контекст за ту саму швидкість.

### Про реальний збій

`userdata/runtime/server.log` містить справжню аварію:

```
W common_fit_params: failed to fit params to free device memory:
                     n_gpu_layers already set by user to 999, abort
E CUDA error: unknown error
```

Це сталося при запуску **з f16-кешем** (у команді не було `--cache-type-*`).
llama.cpp сам попереджав, що параметри не влазять, але `999` забороняв йому
підлаштуватись.

**Висновок, який варто зафіксувати:** проблема була не в оцінці бюджету, а в
тому, що план віддавав f16-кеш і не мав плану Б. Обидві частини закрито:
кеш стиснутий, а `launch_with_recovery` повторює запуск простіше.

## 6. Зір

`ServerConfig.command()` додає `--mmproj <файл>`, якщо проєктор знайдено, і
`--image-min-tokens 1024` — більше токенів на зображення означає краще
читання дрібного тексту інтерфейсу.

`main_window._autostart_local_model()` виставляє `agent.vision_enabled` **лише**
коли проєктор справді приєднано. Інакше знімки не передаються як зображення.

## 7. Стан вимог (оновлено 2026-11-10)

* **Watchdog після старту — є.** `LocalServer.start_watchdog()` — потік-демон,
  що раз на 2 с перевіряє `process.poll()`. Коли рушій помирає, панель дізнається
  про це одразу: причина + хвіст журналу (15 рядків), `AutoLauncher.error`
  очищає `base_url` і підказує натиснути «Запустити модель».
  Автоматичного перезапуску свідомо немає: користувач міг хотіти іншу модель,
  а мовчазний перезапуск після збою пам'яті лише повторив би збій.
  Доведено: `tests/test_watchdog.py` — 4 тести на справжніх процесах.
* **Захист від двох копій IDE — є.** `blackchpok_ide/lockfile.py` створює
  `<app_data_dir>/ide.lock` із PID. Друга копія повертає код 2 і називає, хто
  тримає замок. Замок мертвого процесу перебирається автоматично, тож
  «вічно зайнятого» стану немає.
  Доведено: `tests/test_lockfile.py` — 9 тестів; наживо `python main.py` при
  зайнятому замку → `EXIT=2`.
* **Вимірювання реального споживання VRAM** під час роботи — немає (лише оцінка).
* **Автоматичний підбір контексту за результатами тестів** — немає: контекст
  обирається розрахунком, а не заміром швидкості на цій машині.
