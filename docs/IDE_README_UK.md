# BlackChpok IDE — оболонка в стилі сучасного агентного редактора

Локальна desktop-IDE з агентом у стилі Cursor Agents Window: список
агентів-сесій зі статусами (Working / Completed / Queued), чат із
колапсируваними tool-call блоками, diff-перегляд змін і вбудованими
скріншотами, композер із вибором моделі — і світла cream-тема (є й темна).
Плюс класика: файлове дерево, редактор із підсвіткою, вкладки,
живий термінал, пошук по проєкту, палітра команд, **черга завдань**, **скіли
агента** й **MCP-сервери** — і чат агента, який сам читає файли, вносить зміни
та запускає перевірки, а потім **сам тестує застосунок у живому прев'ю**
(запуск, кліки, введення, скріншоти).

**Працює з коробки.** При першому запуску майстер сам визначає залізо (CPU, RAM,
GPU, вільний диск), підбирає модель, яка впевнено на ньому працює, завантажує
рушій llama.cpp із GitHub і піднімає OpenAI-сумісний сервер — втручатися не
обов'язково. Можна також підключити будь-який свій сервер (LM Studio, Ollama,
llama.cpp, vLLM або хмару). Якщо модель не запущена, працює вбудований
офлайн-роутер команд.

Зібраний застосунок: **[dist/BlackChpok.exe](dist/BlackChpok.exe)** (один файл, ~14 МБ).

## 0. Запустив — і працює

Програма стартує з екрана запиту, як сучасний агентний редактор:

![Стартовий екран](assets/welcome.png)

| Що видно | Що робить |
| --- | --- |
| Поле запиту | «Сплануй, збери або `/` для скілів, `@` для контексту» — Enter надсилає |
| 📁 Чип теки | Вибір папки проєкту — **обов'язковий**: без неї запит не піде |
| ▲ Кнопка | Надіслати запит (Shift+Enter — новий рядок) |
| Підказки | Збери з дизайну · Розгорни прототип · Почни з плану · Розбери помилку |

Після запиту відкривається повний інтерфейс. Повернутися до екрана запиту:
**Файл → Стартовий екран**.

### Тека проєкту обов'язкова

Агент працює з файлами, тож без робочої теки кожен його крок або
провалюється, або — гірше — виконується в домашній теці користувача. Тому
до вибору папки замість чату показується екран «Спершу вибери теку
проєкту» з двома діями: **Вибрати папку проєкту** й **Створити нову**.

Перевірка стоїть в **одному шлюзі** — `ChatPanel._send`, через який
проходять усі входи до агента: поле чату, стартовий екран, голосова
команда, скіл, черга задач, `send_to_agent` з меню. Раніше вона була лише
в «Новий чат» і «Відкрити чат», і решта входів створювала чат із
`workspace = C:\Users\<ім'я>`.

Що бачить користувач, коли теки немає:

| Дія | Поведінка |
| --- | --- |
| Надіслати запит | Текст **лишається в полі**, показується екран вибору теки й пояснення |
| Черга задач | Задача не запускається й не позначається «в роботі» — чекає на теку |
| Провідник, «Зміни», панель контексту | Порожні: вміст домашньої теки не показується |
| Статусбар | «теку не обрано» замість `C:\Users\<ім'я>` |

Свідомий вибір домашньої теки працює: вибір запам'ятовується прапорцем
`project_chosen` у налаштуваннях, тож «не вибрано» й «вибрано дім» не
плутаються.

### Автоналагодження без участі користувача

Одразу після старту (у фоні, не блокуючи вікно) IDE:

1. визначає залізо — CPU, RAM, GPU, вільний диск;
2. **сама піднімає локальну модель**: якщо рушій llama.cpp і GGUF уже є,
   запускає `llama-server` на вільному порту, підставляє адресу й модель
   у налаштування (перевірено на реальній Qwen2.5-Coder 14B: сервер
   піднявся за ~6 с, агент одразу працює з інструментами);
3. якщо локальної моделі немає — створює план завантаження (Хаб моделей);
4. **створює скіли проєкту сама** — `tests`, `code-style`, `run-app`,
   `build`, `docs` (лише ті, для яких є реальні підстави: тека тестів, точка
   входу, скрипт збірки, README). Жодних вигаданих команд.

Досвідчений користувач може все перевизначити: `Ctrl+,` → вкладки
**Модель / Редактор / Агент / MCP**.

## 1. Швидкий старт

### Запуск готового .exe

```bat
dist\BlackChpok.exe "C:\AI\blackchpock_ai"
```

Другий аргумент — папка проєкту (необов'язковий; без нього відкриється остання).

Перевірка без відкриття вікна:

```bat
dist\BlackChpok.exe --selftest
```

### Запуск із коду

```bat
install.bat          :: створює .venv і ставить залежності MCP-сервера
run_ide.bat          :: запускає IDE в поточній папці
run_ide.bat C:\проєкт
```

або напряму:

```powershell
.\.venv\Scripts\python.exe main.py C:\проєкт
```

### Перевірки

```bat
run_tests.bat            :: усе: самоперевірка + юніти + e2e + smoke GUI
run_tests.bat --fast     :: без GUI
```

## 2. Перший запуск: усе налаштовується саме

Майстер відкривається автоматично, якщо програма запускається вперше.

![Крок «Залізо»](assets/wizard_hardware.png)

Майстер проходить **чотири кроки**, і кожен можна відкрити кліком по смузі
кроків угорі. Кнопка **«Зробити все»** проходить їх послідовно сама.

| Крок | Що робить |
| --- | --- |
| **1. Залізо** | Читає процесор, RAM, відеокарту й VRAM (`nvidia-smi` + реєстр), вільне місце; обирає найрозумнішу модель, яка працює з прийнятною швидкістю |
| **2. Бібліотеки** | Перевіряє пакети Python (`openai`, `mcp`, `pypdf`, `python-docx`, `pymupdf`, `ollama`, `numpy`, `pillow`, `pygments`) і ставить відсутні через `pip` |
| **3. Програми** | Перевіряє `git`, `node`, `npm`; ставить через `winget`, а якщо він не впорався — відкриває сторінку завантаження **у вбудованому браузері** |
| **4. Модель** | Завантажує з GitHub збірку llama.cpp під залізо (CUDA / Vulkan / CPU), качає GGUF зі смугою прогресу й піднімає `llama-server`, прописуючи адресу в налаштування |

![Крок «Бібліотеки»](assets/wizard_libs.png)

![Крок «Програми»](assets/wizard_tools.png)

### Як ставиться те, чого бракує

| Що | Спосіб | Якщо не вийшло |
| --- | --- | --- |
| Пакет Python | `python -m pip install --upgrade <пакет>` | показує вивід pip і причину |
| Програма (`git`, `node`) | `winget install --id <id> --exact --silent` | відкриває сторінку завантаження у вбудованому браузері |
| `npm` | приходить разом із Node.js | та сама сторінка Node.js |

Кілька важливих деталей:

- **`pip` у зібраному `.exe` немає** (пакети вже всередині архіву). Тоді
  майстер чесно каже «pip недоступний», а не обіцяє установку, яка впаде.
- **Код «вже встановлено»** від `winget` — не помилка: майстер показує
  «уже встановлено» й іде далі.
- **`PATH` перечитується** після установки (`env_setup.reload_path`):
  без цього щойно встановлений git «не знаходився» до перезапуску IDE.
- **Системний браузер не відкривається.** Сторінки завантаження й документації
  показуються в колонці Live Preview, тож налаштування не переривається
  стрибком у Chrome.

Після цього агент одразу працює. Повторно відкрити майстер:
**Вигляд → Майстер налаштування (бібліотеки, програми, модель)**.

### Як обирається модель

Порахувавши бюджети пам'яті (VRAM після резерву на робочий стіл + RAM із запасом),
IDE приміряє кожну модель каталогу й бере найбільшу, яка:

1. повністю вміщається у VRAM — працює швидко; або
2. вміщається частково (гібрид: частина шарів на GPU, решта в RAM); або
3. на слабкому залізі — меншу модель на CPU, щоб чат не «повз».

Оцінюються не лише ваги, а й KV-кеш для контексту, тому на 8 ГБ VRAM
рекомендується 7B, а не «14B, яка насправді не влізе».

Типові результати:

| Залізо | Рекомендація | Режим |
| --- | --- | --- |
| 8 ГБ RAM, без GPU | Qwen3 4B | CPU, 4K контекст |
| 6 ГБ VRAM, 16 ГБ RAM | Qwen3 4B | повністю на GPU |
| 8 ГБ VRAM, 16 ГБ RAM | Qwen2.5-Coder 7B | повністю на GPU, 16K |
| 12 ГБ VRAM, 32 ГБ RAM | Qwen2.5-Coder 14B | повністю на GPU, 8K |
| 24 ГБ VRAM, 64 ГБ RAM | Qwen2.5-Coder 32B | повністю на GPU, 16K |

## 3. Хаб моделей

`Ctrl+Shift+M` або кнопка **⬇** на лівій рейці. Пошук іде паралельно по всіх
джерелах, результати з'являються в міру надходження.

![Хаб моделей](assets/screenshot_hub.png)

| Джерело | Що дає | Стан |
| --- | --- | --- |
| **Hugging Face** | GGUF-моделі для тексту й коду, з розмірами й квантуваннями | повністю автоматично |
| **GitHub** | репозиторії, інструкції, рушії (`llama.cpp`, `llama-cpp-python`) | посилання на сторінку |
| **Civitai** | контрольні точки та LoRA для Stable Diffusion | пошук працює, завантаження — через сайт |
| **TensorArt** | моделі генерації зображень | немає відкритого API — відкриваємо сайт у браузері |

Чесне зауваження щодо TensorArt: публічний API віддає 403, тому панель не
вигадує результатів, а показує пояснення й кнопку переходу на сайт.

### Позначки можливостей моделей

У списку результатів кожна модель має позначки того, що вона вміє:

| Позначка | Значення |
| --- | --- |
| 🔨 | Підтримує **інструменти** (tool calling) |
| 🧠 | **Думаюча** модель (reasoning) |
| 🖼 | Читає **зображення** (vision) |
| 🎙 | Працює з **голосом** (audio) |

Визначення йде за назвою, тегами й описом репозиторію — без вигаданих
даних: якщо ознак немає, позначок не буде. Наведення показує розшифровку.

![Позначки в хабі](assets/hub_icons.png)

Ті самі позначки є у вкладці **Локальні**.

### Виправлення завантаження

Раніше панель показувала **частини** розбитих файлів
(`…-00001-of-00002.gguf`) замість цілої моделі — користувач завантажував
шматок. Тепер показуються лише цілі файли з реальними розмірами
(Qwen2.5-Coder-7B Q4_K_M = 4.36 ГБ). Частини з'являються тільки тоді, коли
цілого файлу в репозиторії немає — із сумою розмірів.

### Смуга завантаження

- живий прогрес у відсотках, у гігабайтах, швидкість (МБ/с) і ETA;
- **докачка**: якщо завантаження обірвалось, файл продовжується з місця
  (HTTP Range), а не з нуля;
- **скасування** у будь-який момент;
- перевірка вільного місця перед стартом;
- після завершення — пропозиція одразу запустити модель.

### Варіанти квантування

Кнопка **«Варіанти квантування…»** показує всі GGUF-файли моделі з розмірами
й позначкою, чи влізе конкретний варіант у твоє залізо. Це важливо: 7B буває
і 2 ГБ (Q2_K), і 8 ГБ (Q8_0).

### Контекст моделі: як дати більше без втрати швидкості

Розмір контексту — це скільки тексту модель тримає «в голові» одночасно
(файли, результати інструментів, історія чату). Він **не робить генерацію
швидшою**: навпаки, великий контекст забирає відеопам'ять у ваг моделі й
кожен токен стає повільнішим. Але замалий контекст змушує агента
перечитувати файли й повторювати роботу — зовні це виглядає як «модель
зависла».

IDE підбирає контекст сама, у порядку переваги, і показує план запуску в
рядку стану хабу (напр. `План запуску: GPU · 16K · KV q8_0`):

| Спосіб | Що дає | Заміряно (RTX 3060 12 ГБ, Qwen2.5-Coder-14B) |
| --- | --- | --- |
| **Стиснутий KV у VRAM** (`q8_0`) | удвічі більший контекст, та сама швидкість | 16K → **31.7 ток/с** |
| **Точний KV у VRAM** (`f16`) | базовий варіант | 8K → 32.1 · 16K → **14.3 ток/с** ⚠ |
| **KV у RAM** (`--no-kv-offload`) | контекст, що не влазить у VRAM | 32K → **20.7 ток/с** |

**Важливо, що показав замір.** `f16` при 16K у 12 ГБ VRAM **не влазить**:
рушій не падає, а тихо деградує до 14 ток/с — удвічі повільніше. `q8_0` при
тому самому 16K дає 31.7 ток/с, тобто майже повну швидкість. Тому IDE
обирає `q8_0` типово: при однаковому контексті він повільніший за `f16` лише
на 2% (31.6 проти 32.2 на 8K), зате дає вдвічі більший контекст.

**Чому «авто» не бере 32K.** Кеш у RAM коштує близько 35% швидкості
(20.7 проти 31.7). Тому в режимі «авто» IDE бере 16K на повній швидкості, а
32K — лише коли ви самі вказали це число.

Приклад для 14B (Q4_K_M, ваги ≈ 8.4 ГБ) на 12 ГБ VRAM:

| Контекст | KV f16 | KV q8_0 | Разом із вагами | Як запускається | Швидкість |
| --- | --- | --- | --- | --- | --- |
| 8K | 1.5 ГБ | 0.75 ГБ | 9.8 ГБ | усе у VRAM | 32.1 ток/с |
| 16K | 3.0 ГБ | 1.5 ГБ | 10.6 ГБ | усе у VRAM (q8_0) | 31.7 ток/с |
| 32K | 6.0 ГБ | 3.0 ГБ | 9.1 ГБ + RAM | KV-кеш у RAM | 20.7 ток/с |

Керування: **Налаштування → Модель → Розмір контексту**. `0` — авто
(IDE бере найбільший, що влазить у VRAM на повній швидкості). Явне число
(напр. `32768`) — «хочу стільки, обери спосіб сам». IDE ніколи не дасть
менше, ніж просили, якщо це взагалі можливо на цьому залізі.

## 4. Підключення свого сервера

Якщо вже є LM Studio, Ollama чи хмара — хаб не потрібен.

1. Запусти LM Studio → **Developer → Start Server** (порт 1234) або Ollama.
2. В IDE: `Ctrl+,` → вкладка **Модель**.
3. URL: `http://127.0.0.1:1234/v1` (кнопки-пресети підставлять адресу самі).
4. **Оновити список** → вибери модель із підтримкою інструментів (tool calling).
5. Зберегти. Рядок стану над чатом показує поточну модель і зелений/червоний індикатор.

Моделі, перевірені на tool calling: `qwen2.5-coder`, `qwen3-coder`, `deepseek-coder-v2`,
`llama-3.1/3.3-instruct`, `ministral`.

### Локальні моделі та виклики інструментів

Малі локальні моделі часто пишуть виклик інструмента **текстом** замість
нативного поля `tool_calls`:

````
```json
{"name": "list_dir", "arguments": {"path": "."}}
```
````

IDE розпізнає такий текст (у блоках коду, тегах `<tool_call>` або як голий JSON),
перетворює його на справжній виклик і виконує. Після цього **сирий JSON виклику
вирізається з відповіді** — користувач бачить звичайний текст, а не службовий
рядок. Це працює і тоді, коли модель повернула водночас нативний `tool_calls`
і його текстову копію.

Перевірено на 1.5B-моделі, яка інакше просто «говорила б» замість того, щоб
працювати. Моделі 3B і більші зазвичай віддають нативний `tool_calls`.

### Офлайн-режим

Якщо сервер моделі недоступний, агент автоматично переходить на вбудований роутер
і розуміє фрази:

- «покажи файли», «що в папці»
- «прочитай server.py»
- «знайди текст "master_agent_router"»
- «дерево проєкту»
- «git status», «git diff»
- «перевір синтаксис main.py»
- «запусти python -m unittest»

## 5. Що є в оболонці

Вікно зібране як професійна десктопна AI-оболонка: вузька навігація зліва,
центральна колонка діалогу комфортної ширини й робоча область із редактором.

```
┌──────────────────┬────────────────────────────────────────────┐
│ BlackChpok       │  ● Сесія      ◈ Режим ▾  ◎ Чат ▾  ⊟ модель ▾   ⋯  │
│ ＋ Новий чат     │  Чат │ Робоча область                       │
│ ⌕ Пошук…         ├─────────────────┬──────────────┬───────────┤
│ ЧАТИ Й АГЕНТИ  1 │  діалог         │  редактор    │ контекст  │
│   перевір проєкт │  (центр)        │  + термінал  │           │
│   задача 2       │  ─────────────  │              │           │
│   задача 3       │  етапи задачі   │              │           │
│                  │  композер       │              │           │
└──────────────────┴─────────────────┴──────────────┴───────────┘
```

| Зона | Що робить |
| --- | --- |
| **Навігація** зліва | Логотип, «Нова сесія», сім розділів із підписами, історія сесій, робочий проєкт |
| **Заголовок сесії** | Назва сесії, режим роботи, активна модель, завдання, перемикач **Чат / Робоча область** |
| **Діалог** (центр) | Повідомлення, виклики інструментів, статуси, результати, згорнуті журнали роботи |
| **Редактор** | Підсвітка синтаксису (Python, JS/TS, C-like, SQL, shell, JSON, HTML, CSS, YAML, Markdown), номери рядків, поточна лінія, авто-відступ, автозакриття дужок, коментування `Ctrl+/`, дублювання рядка `Ctrl+D` |
| **Вкладки** | Кілька файлів, крапка ● на незбережених, закриття хрестиком, захист від втрати змін |
| **Нижня панель** | Термінал, пошук по проєкту, хаб моделей, сайт — висувна, не забирає весь екран |
| **Колонка контексту** | Відкриті вкладки, нещодавно змінені файли, файли проєкту |
| **Рядок стану** | Позиція курсора, мова файлу, стан агента, робоча тека |

### AST у реальному часі

Редактор розуміє Python-код через справжній AST — не регулярні вирази.

![AST-панель](assets/ast_live.png)

**Панель «Структура»** (Проєкти → Структура) оновлюється **під час набору**:

| Позначка | Що означає |
| --- | --- |
| `ƒ` | функція |
| `ƒᵃ` | асинхронна функція |
| `◇` | властивість (`@property`) |
| `◈` | клас |
| `⇢` | імпорт |
| `▪` | змінна (можна ввімкнути) |

- Показано **справжню вкладеність**: методи всередині класів, вкладені класи;
- **пошук** по символах у полі зверху;
- **підпис із параметрами** (`(self, path, *, force=False)`);
- **підказка** при наведенні: тип, декоратори, docstring, кількість рядків;
- символ, у тілі якого стоїть курсор, **підсвічується**;
- клік — перехід до рядка.

**Синтаксичні помилки видно одразу**: рядок підсвічується червоним, у панелі
з'являється «Рядок 12: Очікується двікрапка в кінці рядка», у смузі стану —
той самий текст.

**Смута стану** показує метрики живого розбору:
`410 рядків · 26ƒ · 4◈ · 0.1 мс`.

### Перегляд AST

`Ctrl+Shift+A` — **сире AST-дерево** поточного файлу: усі вузли з
вкладеністю (Module → ClassDef → FunctionDef → If → Return…). Це і є «магія»
в чистому вигляді — видно, як Python розуміє ваш код.

**Правка → Звіт про символи** — повний список із підписами, декораторами й
докстрінгами.

Розбір швидкий: файл на 410 рядків — **0.1 мс** (кешується за хешем тексту).

### Вкладки файлів

- **✕** на вкладці, середня кнопка миші або `Ctrl+W` — закрити;
- **＋** праворуч від смуги вкладок — новий файл;
- смуга вкладок прокручується колесом, якщо файлів багато;
- права кнопка на вкладці: **Закрити**, **Закрити інші**, **Закрити всі**,
  **Зберегти**, **Зберегти як…**, **Показати в провіднику**, **Копіювати шлях**;
- якщо у файлі є незбережені зміни, IDE запитає, що з ними робити.

### Вбудований термінал

Термінал — це **жива сесія** `cmd.exe`, а не одноразові команди. Тому працює так
само, як справжній термінал IDE:

- `cd` змінює теку й вона зберігається для наступних команд;
- змінні середовища, активований `.venv` і стан оболонки не губляться;
- `Enter` — виконати, `↑` / `↓` — історія команд;
- `Ctrl+C` або кнопка **■** — перервати поточну команду (наприклад, довгий `ping`),
  сама сесія при цьому лишається життєздатною;
- **⟳** — перезапустити сесію, **⌫** — очистити екран;
- швидкі кнопки **Тести / Git / Компіляція**;
- тека в підписі оновлюється автоматично після кожної команди.

Якщо постійну сесію підняти не вдалось, панель переходить на одноразові команди
й повідомляє про це в тексті терміналу.

### Колонка контексту

Три секції праворуч від чату:

| Секція | Що показує |
| --- | --- |
| **Відкриті вкладки** | Усі відкриті файли; клік перемикає вкладку, ● — незбережені зміни |
| **Зміни** | Файли, змінені за останній тиждень, від найновіших (службові `.bak` не показуються) |
| **Файли** | Файли робочої теки для швидкого відкриття |

Колонку можна вимкнути: **Вигляд → Колонка контексту**. На вузькому вікні вона
ховається автоматично, щоб чат і редактор не стискались до смужки.

### Смуга статистики контексту

Під полем введення — тонкий рядок із живими метриками діалогу:

![Смуга статистики](assets/stats.png)

```
⟳ Кроків: 2 · 3 ток/с     ⛁ 6,6 тис. ток    ↺ кеш: 65%    ◔ 27%
```

| Показник | Що означає | Звідки |
| --- | --- | --- |
| **Кроків** | Скільки запитів до моделі зробив агент (крок = один виклик) | лічильник агента |
| **ток/с** | Швидкість генерації | `timings.predicted_per_second` |
| **⛁ ток** | Скільки токенів оброблено за діалог | `usage.total_tokens` |
| **↺ кеш** | Частка вхідних токенів, узятих із кешу | `usage.prompt_tokens_details.cached_tokens` |
| **◔ %** | Наскільки заповнене вікно контексту моделі | останній `prompt_tokens` / ctx |

**Розбивка по складових.** Наведення або клік на індикатор `◔ 27%` показує
картку, як у сучасних агентних редакторах:

![Розбивка контексту](assets/context_popover.png)

| Складова | Що це |
| --- | --- |
| ⬜ **Системна підказка** | Системний промпт + увімкнені скіли |
| 🟪 **Опис інструментів** | JSON-схеми, які модель бачить для tool calling |
| 🟦 **Повідомлення** | Історія діалогу разом із результатами інструментів |

Сума складових завжди дорівнює реальному `prompt_tokens` від сервера:
оцінка в токенах масштабується до фактичного лічильника, тому відсотки й
смуга розподілу чесні. Унизу картки — влучання в кеш, кількість кроків,
швидкість і час роботи.

Круговий індикатор змінює колір: зелений → жовтий (70%) → червоний (90%),
тобто попереджає, коли час почати новий чат. Наведення на рядок показує
детальну довідку: вхідні/згенеровані/кешовані токени, влучання у відсотках,
розмір контексту, швидкість і час роботи.

**Усі числа справжні.** Вони беруться з полів `usage` і `timings`, які
повертає сервер моделі (llama.cpp їх віддає). Якщо сервер цих полів не
надсилає, показуються нулі та «—», а не вигадані значення. Перевірено на
живій Qwen2.5-Coder 14B: `Кроків: 2 · 3 ток/с · 6,6 тис. ток · кеш: 65% · 27%`.

Смуга скидається разом із новим чатом. Розмір вікна контексту береться з
плану запуску моделі (`--ctx-size`), тож відсоток заповнення відповідає
реальному ліміту.

### Чати й агенти (один список)

Зліва — панель **Чати й агенти** (◍ на рейці). Раніше «Чати» й «Агенти» були
двома окремими пунктами меню, хоч це той самий список: кожна розмова і є
сесія агента. Тепер пункт один, а «Справи» (живі кроки агента) стали його
підпунктом (`Ctrl+Alt+D`).

#### Спершу тека проєкту

Без вибраної теки проєкту чат не відкривається: замість нього показується
екран із двома діями — **Вибрати папку проєкту** або **Створити нову**.

Це не формальність. Агент працює з файлами, тож без робочої теки він або
провалює кожен крок, або — гірше — починає правити файли в домашній теці
користувача. Стан «нічого не вибрано» визначається просто: тека порожня,
недоступна або дорівнює домашній.

Щойно теку вибрано, чат створюється автоматично.

| Дія | Як |
| --- | --- |
| Новий чат | **＋ Новий чат** угорі панелі |
| Перемкнутися | Клік по чату; історія повідомлень відновлюється |
| **Закрити чат** | **×** праворуч на рядку |
| **Архівувати** | **⊟** праворуч на рядку; повернути — **↩** у вкладці «Архів» |
| **Видалити всі** | **🗑** праворуч від перемикача «Активні / Архів» |
| Закріпити | Права кнопка → Закріпити (закріплені — зверху) |
| Перейменувати | Права кнопка → Перейменувати |
| Дублювати | Права кнопка → Дублювати |
| Експорт | Права кнопка → Експорт у Markdown |
| Видалити один | Права кнопка → Видалити (з підтвердженням) |

**«＋ Новий чат» не створює порожній запис.** Натискання лише готує чисту
стрічку; запис у списку з'являється з **першим повідомленням**. Раніше
кожне натискання додавало рядок «Без назви» з нулем повідомлень, і список
заповнювався порожніми сесіями.
| Пошук | Поле над списком (шукає за назвою й текстом) |

**«×» на порожньому чаті видаляє його повністю**, а на чаті з історією —
переносить у архів. Раніше тут безумовно створювався новий чат: кожне
натискання «×» збільшувало лічильник у панелі замість того, щоб його
зменшувати.

**Задачі черги належать чату.** Коли чат видаляють або чистять, його задачі
зникають разом із ним — інакше вони лишались «сиротами» й агент виконував
їх уже після зникнення розмови. Кожна нова задача дістає `chat_id`: і кроки
плану, і задачі автономного режиму, і ті, що додані з панелі. Задачі, які
лишились без власника від попередніх версій, прив'язуються до активного
чату на старті (`adopt_orphans`). Черга віддає лише задачі **свого** чату —
інакше після зміни проєкту агент виконав би задачу попереднього чату вже
в новій теці.

**🗑 Видалити всі** питає підтвердження й каже, скільки чатів зникне. У
вкладці «Архів» та сама кнопка чистить лише архівні розмови, не чіпаючи
активні.

Іконки **×** і **⊟** живуть на кожному рядку, тож закрити чи заархівувати
чат можна одним кліком, не відкриваючи контекстне меню. Закриття неактивного
чату прибирає його зі списку (в архів) — історія не губиться. Закриття
активного спершу звільняє агента, зберігає зміни й створює нову сесію.

У вузькій панелі рядок перекладається в дві колонки замість трьох: час він
показує другим рядком, а назва отримує всю ширину (інакше вона обрізалась до
кількох символів).

Назва чату створюється автоматично з першого запиту. Історія зберігається у
`%APPDATA%\BlackChpokIDE\chats.json` і переживає перезапуск.

### Журнал роботи в чаті: «Аналіз запиту»

Поки агент працює, у стрічці чату росте **згорнутий блок** — так само, як у
сучасних агентних редакторах. У заголовку пульсує зелена крапка й цокає
таймер («міркую… 2 хв 54 с»), а всередині видно кожен крок:

| Рядок | Що означає |
| --- | --- |
| `✦` фіолетовим курсивом | **роздуми моделі** — справжній `reasoning_content` |
| `▤ Читає › blackchpok_ide/main_window.py` | читання файлу |
| `⌕ Шукає › check\\(\|def test_` | пошук тексту |
| `✎ Записує`, `✎ Редагує` | зміна файлів |
| `❯ Запускає › python tests/run_all.py` | команда в терміналі |
| `✓` / `✗` | крок завершився успішно або з помилкою |
| `│` | проміжний коментар агента («Тепер перевірю тести.») |
| `✓ Готово · 5 кроків · 18 с` | підсумок |

Клік по заголовку згортає або розгортає блок. Клік по довгому рядку
(роздуми, результат інструмента) відкриває повний текст у вікні. Коли агент
завершує, таймер застигає на витраченому часі, а крапка стає спокійною.

Роздуми беруться з поля `reasoning_content`, яке віддають reasoning-моделі
(deepseek-reasoner, o1/o3, QwQ та інші). Звичайні моделі цього поля не
мають — тоді журнал показує лише інструменти й коментарі.

### Етапи задачі над полем вводу

Велике завдання агент розбиває на етапи, і цей поділ видно **просто над
полем вводу** — там, де ви пишете, без переходу в інші панелі:

![Смуга етапів над композером](assets/stage_strip.png)

| Елемент | Що показує |
| --- | --- |
| Заголовок | `Етап 2 з 3` · `Готово · усі 3 етапи` · поруч — початок вашої задачі |
| `○` | етап ще не почато |
| `◐` | етап виконується — **кружечок обертається**, під ним підпис інструментів |
| `✓` | етап виконано — **зелений** |
| `✗` | етап провалено — червоний |

Підпис інструментів (`читання файлу · правка фрагмента`) бачите лише в
поточного етапу — так видно, що саме агент робить цієї миті.

**Як агент розуміє задачу.** Замість пошуку одного «магічного слова» фраза
розбирається на:

1. **намір** — прочитати, створити, змінити, знайти, запустити, перевірити,
   виправити помилку, зробити рефакторинг, оформити документацію, зібрати;
2. **об'єкти** — названі файли (`main.py`) і символи в лапках;
3. **масштаб** — скільки різних робіт просять.

Українські дієслова мають багато форм, тому зіставлення йде **за основою
слова**: «зроби», «зробити», «зробіть», «зробимо» — та сама дія. Запитання
не вважається дорученням: «як зробити чай?» — це розмова, а не команда
відкривати файли.

**Як обираються інструменти.** Кожен намір дає свій набір — наприклад,
«створи файл» → `write_file`, `read_file`, `python_check`; «виправ
помилку» → `read_file`, `search_text`, `run_command`, `edit_file`. Цей
перелік додається до запиту підказкою: модель обирає серед 3–4 доречних,
а не серед усіх 19.

**Як робиться поділ на етапи.** Три способи, у порядку надійності:

1. ви вже написали список (`1) … 2) …` або маркери) — беремо його як є;
2. кілька речень з дієсловом-наказом — кожне стає етапом;
3. усе в одному реченні — ріжемо за «, а також», «потім», «далі» та перед
   дієсловами-наказами.

Поділ робиться **локально, без моделі**, тому смуга з'являється одразу й
працює навіть коли локальна модель недоступна. Якщо модель усе ж склала
план (глибокий аналіз), її кроки показуються в тій самій смузі.

Один етап смуга не показує: рядок-дубль вашого ж тексту лише забирав би
місце над полем вводу.

### Глибокий аналіз і план у чаті

На складну задачу агент не кидається одразу писати код: спершу в **самому
чаті** з'являється картка аналізу, де видно, як він думає, що перевіряє й
що планує робити далі.

![Глибокий аналіз у чаті](assets/deep_card.png)

| Елемент | Що показує |
| --- | --- |
| **Глибоке розмислення** | заголовок з пульсуючою крапкою й таймером (`7м 0с`) |
| **Проміжні думки** | окремі абзаци: «Розберуся, що зараз відкриває браузер…», «Тепер зрозуміло. Перевірю ще кілька місць…» |
| **Згортані групи** | `▸ Читання файлів, пошук коду   6 кроків  ✓` — клік розгортає список викликів |
| **Діла** | панель задач: `◐` у процесі, `○` очікує, `●` готово, `✗` помилка |
| **Поточна ціль** | закріплений блок унизу картки |

#### Коли вмикається

Режим свідомо консервативний — коротке доручення не має розтягуватись на
план із дванадцяти пунктів:

| Умова | Приклад |
| --- | --- |
| Явне прохання | `/план …`, «склади план», «детально проаналізуй», «подумай крок за кроком» |
| Велике завдання | багато вимог у кількох абзацах (той самий поріг, що й для розбиття на чергу) |
| Кілька вимог у змістовному тексті | від 60 символів і 2+ різних дієслів-вимог («зроби», «додай», «виправ»…) |

«Запусти тести» режим не вмикає. Пороги відкалібровані на живому прогоні:
реальне завдання на 184 символи з двома вимогами спершу НЕ проходило старий
поріг «4+ речення й 3+ вимоги» — і режим не вмикався на задачі, для якої
його й зробили.

#### План будується по твоєму проєкту

Перед складанням плану до запиту додається **контекст проєкту**: мова,
фреймворки, точки входу й список справжніх файлів. Це не косметика:
без контексту локальна Qwen2.5-Coder 14B на цьому проєкті склала план
«додати HTML-структуру, CSS-стилі, JavaScript-код» — тобто планувала
вебсайт замість десктопного застосунку. З контекстом план став про
`blackchpok_ide/*.py`, `unittest` і `README_UK.md`.

#### Як це працює

1. Ти надсилаєш складну задачу. Картка з'являється одразу.
2. У фоні окремим коротким запитом модель складає план (не частиною
   основного циклу — так план видно швидко й він не змішується з роботою).
3. План стає списком задач у картці, перша одразу позначається `◐`.
4. Далі агент працює звичайним чином: його проміжні репліки стають
   абзацами картки, виклики інструментів — згортаними групами, а задачі
   змінюють стан на місці.
5. Коли все готово, таймер застигає, заголовок стає «Аналіз завершен», усі
   задачі — `●`.

Якщо модель недоступна або не дала кроків, картка чесно пише причину й
агент усе одно починає роботу: краще працювати без плану, ніж не працювати.

Уся логіка — у [deep_mode.py](blackchpok_ai/deep_mode.py), малювання — у
[deep_view.py](blackchpok_ai/deep_view.py). Логіка без tkinter, тому
перевіряється тестами без вікна.

### Справи: що агент робить просто зараз

Панель **Справи** (◎ на рейці, `Ctrl+Alt+D`) — це живий журнал роботи агента.
Кожен запит у чаті стає **справою**, а все, що агент робить усередині,
з'являється в ній **кроком**: «Запит до моделі…», `read_file(path=main.py)`,
`run_command(python -m unittest)`, «Модель недоступна — працюю локальним
роутером».

Крок, який триває, позначено **зеленою крапкою з кільцем, що розходиться**;
коли крок завершується — кільце зникає, крапка стає спокійною, а поруч
додається витрачений час. Невдалий крок стає **червоною** крапкою. Активна
справа розгортається сама, тож видно саме те, що відбувається зараз.

| Дія | Як |
| --- | --- |
| Показати кроки справи | Клік по рядку справи (або ▸ / ▾) |
| Прибрати завершені | **⌫** у заголовку панелі |
| Відкрити панель | ◎ на рейці, `Ctrl+Alt+D` або **Вигляд → Кроки агента** |

Справи живуть у пам'яті сесії: вони описують поточну роботу, а не історію.
Сама історія розмов, як і раніше, лежить у **чатах**.

### Знання про проєкт (RAG)

Панель **Знання** (🧠 на рейці, `Ctrl+Alt+I`) підключає до IDE наявний рушій
RAG (`rag_engine.py` у корені проєкту) — той самий, яким користується
MCP-сервер. Нічого не дублюється: панель читає реальний індекс
`.mcp_rag/index.sqlite3`.

| Дія | Що робить |
| --- | --- |
| **Індексувати** | Проіндексувати робочу теку (пропускає `.git`, `node_modules`, `.venv`) |
| **Переіндексувати** | Примусово перебудувати індекс |
| Поле пошуку | Гібридний пошук: FTS5/BM25 + вектори, якщо налаштовані |
| **Відкрити** | Відкрити файл у редакторі на знайденому рядку |
| **У контекст** | Вставити фрагмент у поле запиту як контекст |

У заголовку видно реальні числа: скільки файлів і фрагментів в індексі,
режим пошуку (BM25/FTS5 або hybrid) і скільки фрагментів мають вектори.
Кожен результат показує `шлях:рядки` і початок фрагмента.

Векторний пошук вмикається змінними середовища `MCP_RAG_EMBEDDINGS_URL` і
`MCP_RAG_EMBEDDINGS_MODEL` — так само, як для MCP-сервера.

### Інструменти агента

Панель **Інструменти** (⚒ на рейці, `Ctrl+Alt+T`) показує **все**, що агент
справді вміє: 11 вбудованих інструментів (читання, запис, редагування,
пошук, команди, Git, аналіз) і всі інструменти живих MCP-серверів.

Кожен інструмент розгортається у форму зі своїми реальними параметрами
(з тих самих JSON-схем, що бачить модель). Заповніть поля й натисніть
**Виконати** — виклик іде через той самий `ToolRegistry`, що й у агента,
тож результат ідентичний. **Заповнити прикладом** підставляє безпечні
значення.

Результат показується в панелі й дублюється в чаті. Якщо інструмента немає
в реєстрі або MCP-сервер не працює — кнопка не вдає роботу, а показує
справжню помилку.

### Стрімінг відповідей

Відповідь моделі друкується в міру генерації (SSE, `stream: true`), а не
з'являється вся одразу після завершення. Роздуми reasoning-моделей теж
дописуються в журнал роботи в реальному часі.

Вимкнути можна в **Налаштування → Агент → «Показувати відповідь у міру
генерації»**. Якщо сервер не підтримує SSE, IDE читає звичайну відповідь
тим самим запитом — без прихованого повторного звернення.

### Дії з власним запитом

На кожному своєму повідомленні в чаті є три дії:

| Кнопка | Дія |
| --- | --- |
| **↺** | Повторити цей запит ще раз |
| **✎** | Повернути запит у поле вводу для правки |
| **⧉** | Скопіювати текст запиту |

На відповіді агента теж є **↺** — повторити запит, на який вона відповідала.

### Режим «тільки чат»

Коли потрібно працювати лише з розмовою, увімкніть режим **Тільки чат** —
кнопка **▣** на рейці або `Ctrl+Alt+F`. Редактор, нижні вкладки й колонка
контексту згортаються, а чат займає все вікно.

Решта панелей — провідник, скіли, черга, справи, MCP — нікуди не зникають:
їх можна відкрити звичайним способом (навігація, меню **Вигляд**, гарячі клавіші),
і вони не забирають місця, поки не потрібні. Повторне натискання `Ctrl+Alt+F`
повертає попередню розкладку.

### Вкладки: закрити й відкрити знову

Кожна вкладка закривається **✕** (або `Ctrl+W`, або середньою кнопкою миші).
Закрита вкладка не губиться: `Ctrl+Shift+T` відкриває останню закриту, а
**Файл → Відкрити закриту вкладку** показує список останніх (до 40).

### Зміни у файлах

Панель **Зміни** (± на рейці) показує те саме, що агентні редактори:
загальний підсумок `+додано -видалено` і список файлів зі своєю статистикою.

- для git-проєктів — з `git status`/`git diff`;
- без git — за резервними копіями `.bak`, які лишає редактор;
- клік по файлу відкриває його, права кнопка дає **Показати diff**;
- у редакторі рядки, додані після збереження, підсвічуються зеленим.

Можна працювати не лише з локальною моделлю, а й із хмарним агентом —

**Налаштування → Хмарні агенти**:

### Deploy (deploy.com)

Окремий провайдер із власним шлюзом:

![Deploy у налаштуваннях](assets/settings_deploy.png)

| Поле | Значення |
| --- | --- |
| **API-ключ** | Створити на [portal.deploy.com](https://portal.deploy.com/?api_keys=1) → Service API Keys |
| **Базова адреса** | `https://api.deploy.com/api/v1` (шлях саме `/api/v1`) |
| **Регіон** | 6 варіантів: найближчий, CDN, SF, VA та їхні CDN-версії |
| **Моделі** | `deepseek-ai/deepseek-v4.1-flash-1017`, `zai-org/glm-5.3-flash` |

Обидві моделі мають **вікно 1 млн токенів**, **tool calling**, **reasoning** і
**prompt caching**. Deploy підтримує OpenAI-сумісний формат, тому агент
працює з ним так само, як з іншими хмарами — з усіма інструментами IDE й MCP.

**Регіони** (від них залежить затримка):

| Регіон | Адреса |
| --- | --- |
| Найближчий | `https://api.deploy.com/api/v1` |
| CDN (з-за меж США) | `https://api-cdn.deploy.com/api/v1` |
| SF / SF CDN | `https://api-sf1.deploy.com/api/v1` · `…-cdn…` |
| VA / VA CDN | `https://api-va1.deploy.com/api/v1` · `…-cdn…` |

**Рівні міркувань** Deploy приймає `none`, `low`, `high`, `max` — усі є в
меню моделі. Типовий рівень моделі — `high`.

### Підтримка reasoning-моделей

Для «думаючих» моделей (`deepseek-reasoner`, `o3-mini`, `qwq`) є два
важливі моменти, які вже враховано:

1. **`temperature` не надсилається** — ці моделі відповідають помилкою 400,
   якщо передати цей параметр.
2. **`reasoning_content` зберігається окремо** від відповіді — «думки»
   моделі не змішуються з текстом для користувача.

## 4б. Розкладка вікна

![Розкладка](assets/layout.png)

Вікно зібране як професійна десктопна агентна оболонка: вузька навігація

| Зона | Де | Що там |

Усі межі між зонами рухаються мишею, а розміри зберігаються між запусками:

### Колонка контексту

Права колонка показує стан роботи, а не лише список файлів:

| Секція | Що показує |
| --- | --- |

| **Проєкт** | Тека проєкту, коли його востаннє змінювали, стек (Python / Node.js / веб …) |
| **Інструменти** | Реальний перелік інструментів, доступних агенту в поточному режимі |
| **Відкриті вкладки** | Вкладки редактора, активна підсвічена |

Кнопка **»** у шапці колонки згортає її (те саме — **Вигляд → Колонка

### Ліва панель: тільки чати

Ліворуч — **самі розмови**. Жодного меню розділів тут більше немає: раніше
п'ять пунктів («Чати», «MCP Tools», «Проєкти», «База знань»,
«Налаштування») забирали місце в колонці, призначеній для чатів, і
«Проєкти» з «Базою знань» виглядали як ще дві розмови.

| Що є ліворуч | Що робить |
| --- | --- |
| **＋ Новий чат** | Готує чисту стрічку (запис з'явиться з першим повідомленням) |
| **◍ Чати · ≡ Завдання · ▤ Файли · ⚙** | Швидкий доступ: список чатів, центр завдань (`Ctrl+Alt+W`), файли проєкту, налаштування |
| Поле пошуку | Шукає за назвою й текстом розмов |
| Список чатів | Активні / Архів, закріплені, «×» закрити, **🗑** видалити всі |
| 🗂 Робочий проєкт | Тека проєкту; клік змінює її |
| ◔ | Налаштування (`Ctrl+,`) |

(`Ctrl+Shift+P`).

### Центральна колонка діалогу

Розмова займає **всю доступну ширину** колонки діалогу. Раніше вміст
стискався до 920 px і центрувався — на 4K-екрані розмова виглядала вузькою
смужкою посеред порожнього поля.

Дві причини, які довелось виправити окремо:

1. **старе `chat_max_width = 920`** у збереженому `settings.json`
   перекривало новий типовий 0 — тепер це значення автоматично
   скидається до «на всю ширину» під час завантаження;
2. **колонка контексту** забирала 359 px навіть у режимі «Чат», коли
   редактора немає. Тепер вона ховається в режимі чистого чату.

Вузьку колонку можна повернути, задавши `ui.chat_max_width` ≥ 480 у
`settings.json` (типово `0` = без обмеження).

**Відповіді показуються повністю.** Висота картки дорівнює всьому тексту —
жодних власних смуг прокрутки всередині повідомлення. Раніше висота
обрізалась на 12–70 рядків залежно від екрана, і решта ховалась у прокрутку
віджета: саме та смуга й з'являлась між відповідями. Лишився один запобіжник
на 400 рядків — полотно Tk перестає малювати вміст під ~24 000 px, тож
відповідь на тисячі рядків усе одно треба обмежити, інакше вона зникне.

Прокручується вся стрічка цілком — звичайним колесом миші.

### Ліва панель: перетягування ширини

Межу лівої панелі можна тягнути мишею (типово 300 px, межі 180 px і 45 %
вікна). Ширина зберігається в `layout.json` і відновлюється після
перезапуску. Згорнути панель до рейки — **«** у її заголовку або `Ctrl+B`.

### Чат і робоча область

Перемикач у заголовку сесії змінює композицію, а не лише вигляд:

![Робоча область](assets/workspace.png)

| Вид | Композиція |
| --- | --- |
| **Чат** | Діалог на весь центр — концентрація на розмові |
| **Робоча область** | Діалог + редактор поруч: розмова й код одночасно |

Вибір запам'ятовується в `ui.view`. Режим «тільки чат» (`Ctrl+Alt+F`)
ховає ще й колонку контексту та нижню панель.

### Адаптивність

Композиція підлаштовується під ширину вікна, а не ламається на малому екрані:

| Ширина | Що видно |
| --- | --- |
| Широка (≥ 1180 px) | Діалог + редактор + контекст |
| Середня | Діалог + редактор (контекст згортається) |
| Вузька | Діалог (другорядні підписи композера ховаються) |

Розміри рахуються з екрана, а не беруться сталими числами (модуль
`blackchpok_ide/adaptive.py`):

| Що | Як обчислюється |
| --- | --- |
| Ширина колонки діалогу | комфортна довжина рядка (~92 символи), але не менше 34 % і не більше 46 % доступного місця; межі 320–1180 px |
| Ширина композера | на 24 px вужча за стрічку (поле не «злипається» з краєм) |
| Рядків в одній відповіді | 58 % видимої висоти стрічки, межа 12–70 рядків |
| Ширина бічної панелі | 220 px на екрані &lt; 1280, 300 px на ≥ 2200 |

Тому на ноутбуці 1366×768 чат не з'їдає редактор, а на 4K відповідь не
губиться у вузькій смужці. Ліміт рядків перераховується під час ресайзу:
уже намальовані картки міняють висоту, а не лишаються обрізаними.

Якщо користувач сам перемикав колонку контексту, його вибір поважається.

### Рухомі межі

Усі межі перетягуються мишею: між навігацією і робочою областю, між
діалогом, редактором і контекстом, і між стрічкою діалогу та композером.

**Позиції запам'ятовуються автоматично** у
`%APPDATA%\BlackChpokIDE\layout.json` і відновлюються при наступному
запуску.

| Дія | Як |
| --- | --- |
| Зберегти зараз | **Вигляд → Зберегти розкладку** |
| Скинути до типової | **Вигляд → Скинути розкладку** (`Ctrl+Alt+R`) |
| Сховати колонку | Вигляд → Бічна панель / Колонка контексту |

Перевірено: позиції сашів зберігаються й відновлюються з точністю до
кількох пікселів після перезапуску.

## 5аб. Розуміння людської мови

Агент розуміє запити так, як їх каже замовник: без назв інструментів,
шляхів і команд. Це окремий шар (`task_plan.understand`), який працює
**без моделі**, тож намір визначається навіть коли модель повільна.

### Як читається проста фраза

Розуміння будується на трьох незалежних ознаках, а не на одному
«магічному слові»:

| Ознака | Приклад | Що дає |
| --- | --- | --- |
| **Дія** | «зроби», «поміняй», «прибери», «накидай» | намір: створити / змінити |
| **Предмет** | сайт, гра, кнопка, файл, тест, база | що саме робити |
| **Бажання** | «хочу», «потрібен», «треба», «мені» | це прохання, а не розповідь |

Дієслово може бути будь-яке: «зроби», «напиши», «накидай», «намути»,
«перероби», «поміняй», «прибери», «збільш». Відмінки й помилки в словах —
норма, зіставляємо за основою слова.

### Що тепер розуміється

| Фраза | Незрозуміло без шару | Розуміється як |
| --- | --- | --- |
| «мені потрібен калькулятор» | балачка | створити |
| «хочу гру змійку» | балачка | створити |
| «треба щоб був сайт з меню» | лише «інтерфейс» | створити сайт |
| «поміняй колір фону» | балачка | змінити |
| «перероби меню під мобільні» | балачка | змінити |
| «зроби шрифт більшим» | створити файл ❌ | змінити |
| «прибери зайвий рядок» | балачка | змінити |
| «воно не працює, допоможи» | балачка | полагодити |
| «чомусь нічого не відображається» | балачка | полагодити |
| «зламалось після моїх змін» | балачка | полагодити |
| «що в цьому файлі» | балачка | прочитати відкритий файл |
| «де використовується ця змінна» | балачка (питання) | пошук у коді |
| «накидай простий бот» | балачка | створити |

**Скарга — це завжди завдання.** «Не працює», «падає», «нічого не видно»,
«вилітає», «глючить», «зламалось» — агент не просить текст помилки, а йде
шукати причину сам.

**Питання про код ≠ балачка.** «Що в цьому файлі» і «де використовується
ця змінна» — це доручення подивитись проєкт, бо відповісти без читання
файлів неможливо. А от «як зробити чай» і «що таке рекурсія» лишаються
розмовою: інструменти на них не запускаються.

### Агент сам виправляє зламаний код

Локальні моделі регулярно пишуть код, який не запускається — найчастіше
апостроф усередині лапок:

```python
name = input('Введіть ім'я: ')     # ❌ рядок обривається
name = input("Введіть ім'я: ")     # ✅ ось як треба
```

Раніше користувач бачив «готово», а програма не запускалась. Тепер:

1. `write_file`, `edit_file` і `append_file` **перевіряють синтаксис
   одразу** й пишуть у результаті «УВАГА: синтаксична помилка — …» (файл
   усе одно записується, щоб модель бачила свій текст).
2. Після кожного ходу агент перевіряє записані `.py`-файли.
3. Апостроф у лапках виправляється **механічно й одразу** — без запиту до
   моделі. Заміряно: коли моделі просто казали «виправ помилку», вона
   повторювала той самий рядок 15 разів і не змінювала його.
4. Якщо помилка інша — модель отримує конкретний рядок і номер, і цикл
   робить ще один хід (не більше двох разів, щоб не зациклитись).
5. **Пробний запуск**: створений скрипт запускається з таймаутом 20 с, і
   якщо він падає під час виконання (`ZeroDivisionError`, `KeyError`), агент
   отримує traceback і виправляє. Синтаксис цього не ловить — компілятор
   пропускає логічні помилки. Скрипти з `input()` не запускаються, щоб не
   зависнути на очікуванні вводу.

Перевірено наживо: файл із зламаними лапками виправляється за 14–24 с і
компілюється.

### Дописування не затирає файл

На фразу «додай у notes.txt рядок» модель викликала `write_file` і
**затирала весь попередній вміст**: файл із трьох рядків ставав одним.
Тепер є окремий інструмент **`append_file`**, який дописує в кінець і не
чіпає наявне. Модель отримує пряму підказку в запиті кроку, що для
дописування треба саме він.

Додатково `write_file` попереджає, якщо новий вміст помітно коротший за
попередній — агенту видно, що він міг загубити текст.

### Правка прощає неточності

Локальна модель майже ніколи не відтворює фрагмент точно: міняє лапки,
зсуває відступи, додає пробіли. Раніше це зривало правку з «фрагмент не
знайдено», і агент переписував файл цілком — ризик втратити чужий код.
Тепер `edit_file` порівнює фрагмент за «скелетом» (без пробілів і лапок),
знаходить реальний текст у файлі й замінює саме його. Якщо збігу немає —
відмова з поясненням, а не мовчазна перезапис.

### Кілька робіт в одному реченні

«Додай у calc.py множення, а в notes.txt запиши що зроблено» — це дві
роботи. Раніше агент робив лише першу й звітував «готово». Тепер фраза з
кількома різними файлами розбивається на окремі етапи, і роутер бачить
**усі** названі файли, а не лише перший.

### Як перевірити самому

```powershell
.\.venv\Scripts\python.exe tools\check_language.py        # 44 фрази, без моделі
.\.venv\Scripts\python.exe tools\check_quote_fix.py        # виправлення лапок
.\.venv\Scripts\python.exe tools\check_fuzzy_edit.py       # толерантна правка
.\.venv\Scripts\python.exe tools\check_smoke_check.py      # пробний запуск
.\.venv\Scripts\python.exe tools\check_plain_language_live.py  # фрази → файли
.\.venv\Scripts\python.exe tools\check_self_heal_live.py   # самовиправлення
.\.venv\Scripts\python.exe tools\eval_agent.py             # 10 архетипів задач
```

`eval_agent.py` — головний стенд: створення, правка, виправлення за
скаргою, дописування, тести, читання, перейменування по проєкту, кілька
робіт, документація й «питання не має ламати файли». Кожен сценарій
перевіряє **факт на диску**, а не слова моделі.

### Модель для поточного чату

Кнопка **⊟** у рядку композера відкриває компактне меню — як у сучасних
агентних редакторах:

![Меню моделі](assets/model_menu.png)

| Рядок | Що робить |
| --- | --- |
| **Модель …›** | Вибір моделі з переліку (хмара + локальні) |
| **Зусилля …›** | Рівень міркувань для reasoning-моделей |

Модель зберігається **за чатом**, а не глобально: різні розмови можуть

![Список моделей](assets/model_list.png)

Рівні зусилля:

| Рівень | Що робить |
| --- | --- |
| За замовчуванням | Як вирішує сама модель (нічого не передається) |

| Збалансовано | Помірні міркування |
| Ретельно | Максимум міркувань, повільніше |

Рівень передається як `reasoning_effort` (OpenAI o-серія) і бюджет
міркувань — для інших провайдерів. Клавіатура: **↑↓** вибір, **Enter**
застосувати, **Esc** назад.

### Селектор моделей і провайдерів

Клік по назві моделі в заголовку сесії (або по **⊟** у композері)
відкриває повний селектор — це головне місце, де видно, **звідки** береться
модель.

![Селектор моделей](assets/model_selector.png)

| Елемент | Що показує |
| --- | --- |
| **●** зліва від назви | Реальний статус: зелений — сервер відповів, червоний — не відповів |
| Назва моделі | Те, що повернув сервер (`GET /models`) або знайдено на диску |

| **✓** | Активна модель |

Моделі згруповані: спершу **ЛОКАЛЬНІ**, потім **ХМАРНІ · необов'язково**.
Пошук у картці фільтрує список. Кнопка **⟳** перевіряє всі локальні

вікно контексту — з каталогу провайдера або з плану запуску рушія. Якщо
значення невідоме, показується **—**.

Кнопка режиму в заголовку сесії (наприклад **◈ Агент ▾**) перемикає

| Режим | Дозволи | Кроків | Інструменти | Підказка моделі |
| --- | --- | --- | --- | --- |
| **◌ Чат** | лише читання | 1 | вимкнені | відповідати текстом |

### Режими дозволів

![Режими дозволів](assets/permission_menu.png)

| Режим | Що дозволено |
| --- | --- |
| 🛡 **Лише читання** | Читати файли, шукати, аналізувати. Будь-який запис і команди — заборонені |
| 🖊 **Запис у робочій області** | Створювати й правити файли **лише в теці проєкту**. Вихід за теку та системні шляхи — заборонені |
| ⚠ **Повний доступ** | Без обмежень; системні шляхи — з підтвердженням |

Перевірка відбувається в **єдиному місці** — перед виконанням інструмента,
тож обійти її не можна ні моделлю, ні автовиконанням. Небезпечні команди
(`rm -rf`, `format`, `reg delete`, `diskpart`…) дозволені лише в повному
доступі.

Режим зберігається в налаштуваннях і відновлюється при старті.

## 5б. Публікація в соцмережі

Агент може писати пости й **справді публікувати** їх: телеграм, X (Twitter),
Facebook, Mastodon, Discord.

**Налаштування → Соцмережі** — ключі вписуються прямо в програмі:

![Соцмережі](assets/settings_social.png)

| Мережа | Що потрібно | Ліміт |
| --- | --- | --- |
| **Telegram** | Токен бота (@BotFather) + Chat ID | 4096 |
| **X (Twitter)** | OAuth 2.0 user token із правом `tweet.write` | 280 |
| **Facebook** | Page ID + Page Access Token | 63 206 |
| **Mastodon** | Адреса сервера + токен застосунку | 500 |
| **Discord** | URL вебхука каналу | 2000 |

Кожна мережа має підказку, де взяти ключ, і кнопку переходу на потрібну
сторінку.

### Як це працює в розмові

Просто скажи агенту:

- «опублікуй пост у телеграм про новий реліз»
- «напиши пост у X про наш проєкт і виклади»
- «запости в мастодон: сьогодні вийшла версія 1.2»

Агент згенерує текст, сам визначить мережу з фрази й опублікує справжнім
запитом до API. У відповідь прийде підсумок із посиланням на пост:

```
✓ Telegram: опубліковано — https://t.me/mychannel/77
```

Довгі тексти автоматично обрізаються під ліміт конкретної мережі. Якщо
мережу не названо, агент бере ту, що налаштована. Якщо ключів немає —
пояснить, чого бракує, і куди його вписати.

Перевірено на справжньому HTTP-сервері: запит іде на правильний шлях
`/bot<token>/sendMessage`, текст і `chat_id` передаються, посилання
повертається.

## 5г. Сайт у вбудованому браузері

![Сайт у браузері](assets/web_preview.png)

**Вигляд → Сайт у браузері** (`Ctrl+Alt+P`) або вкладка **🌐 Сайт** знизу.

### Автоматичне визначення стеку

IDE сама розуміє, як запустити проєкт:

| Стек | Що робить |
| --- | --- |
| 🌐 **Статика** | Вбудований сервер віддає теку (без залежностей) |
| 🐍 **Flask** | `python app.py` |
| 🐍 **FastAPI** | `uvicorn main:app --reload` |
| 🐍 **Django** | `manage.py runserver` |
| 🟩 **Node.js** | `npm run dev` / `npm start` (Vite, Next визначаються) |
| 🐘 **PHP** | `php -S 127.0.0.1:PORT` |
| 💎 **Ruby**, 🔵 **Go**, 🦀 **Rust**, 🟣 **.NET** | відповідні команди |

Стек підписано у панелі: `🌐 Статичний сайт · Статичний HTML`.

### Вбудований браузер

Справжній Chrome/Edge **усередині вікна IDE** — через Windows API
(`SetParent` + `WS_CHILD`), без сторонніх пакетів. Сторінка рендериться
повністю: CSS, JavaScript, зображення, кнопки.

#### Адреси: локальні сайти й інтернет

У тулбарі є **рядок адреси**, тож вікно не обмежене сайтом проєкту:

![Вбудований браузер](assets/browser_embedded.png)

| Що ввести | Що станеться |
| --- | --- |
| `127.0.0.1:8000` | відкриється локальний сайт проєкту (`http://`) |
| `localhost:3000/app` | те саме, з підшляхом |
| `git-scm.com/download/win` | відкриється сторінка в інтернеті (`https://`) |
| `https://docs.python.org` | повна адреса — як є |
| `C:\temp\report.html` | локальний файл через `file://` |
| `mailto:…` | не відкриється: вікно підтримує лише `http`, `https`, `file` |

Локальним адресам додається `http://` (у них майже ніколи немає TLS), а
решті — `https://`. Схема, яку вікно не вміє, не переписується навмання:
замість дивної адреси ви побачите пояснення.

Кнопки поруч: **‹** назад, **→** перейти, **⟳** перезавантажити,
**◉** живе оновлення, **↗** відкрити в системному браузері (свідомий вибір
користувача, а не типова поведінка). У вузькій колонці другорядні кнопки
ховаються, щоб адреса лишалась читабельною.

**Масштаб під ширину колонки.** Сторінка з інтернету у 400-500 px
відкривалась у мобільній розкладці — величезні заголовки, обрізані меню.
Тепер масштаб підбирається сам: 0.55 за ширини до 360 px, 0.65 до 460,
0.8 до 560, далі 1.0. Локальні сайти проєкту не масштабуються, поки
колонка не зовсім вузька: у них своя адаптивна верстка.

#### Системний браузер більше не відкривається

Раніше кілька місць IDE кликали `webbrowser.open`: клік «Встановити git» у
панелі «Зміни» викидав користувача з IDE в Chrome на git-scm.com, а
сторінки моделей і ключів відкривались там само. Тепер **усе** йде через
єдиний відкривач (`browser_panel.open_url`), який показує сторінку поруч, у
колонці Live Preview, і заодно вмикає рядок адреси.

Це зафіксовано тестами: `tests/test_browser_url.py` розбирає код через `ast`
і падає, якщо в інтерфейсі з'явиться справжній виклик `webbrowser.open`, а
`tests/test_browser_wizard_live.py` підміняє його «шпигуном» і перевіряє, що
за весь сеанс він не викликався жодного разу.

### Живе оновлення

Стежимо за файлами проєкту (`.html`, `.css`, `.js`, `.py`, `.php`…). Щойно
файл збережено — сторінка перезавантажується сама:

```
Змінено: index.html — оновлюю сторінку…
```

Кеш вимкнено на сервері (`no-store`), тому зміни видно одразу. Кнопка **◉**
вмикає/вимикає живе оновлення, **⟳** — ручне перезавантаження, **↗** —
відкрити в системному браузері.

Сервер піднімається на вільному порту й зупиняється разом із вкладкою.
Порт можна змінити; якщо зайнятий — береться наступний.

### Live Preview — права колонка

Сайт проєкту показується в колонці **Live Preview** праворуч від чата:
**Вигляд → Live Preview** (`Ctrl+Alt+V`). Вона показує застосунок поруч із
розмовою — агент і ви бачите результат змін одночасно. Коли агент запускає
застосунок інструментом `app_start`, колонка відкривається сама.

![Локальний сайт у вбудованому браузері](assets/local_site.png)

Це **єдине** місце, де живе вбудований браузер. Раніше «Сайт у браузері»
додатково відкривало вкладку «🌐 Сайт» знизу, і виходило два незалежні
вікна Chromium для тієї самої адреси: кнопка «■» в одній панелі не
зупиняла другу, а сторінка вантажилась двічі.

**Статика віддається з кодуванням UTF-8.** Без цього заголовка браузер
вгадував кодування й український текст у `index.html` показувався
кракозябрами — тепер `charset=utf-8` стоїть і для `text/*`, і для
`application/javascript`, `application/json`, `image/svg+xml`.

## 6. Черга завдань

Агент уміє працювати не лише з одним запитом: задачі можна скласти в чергу, і
IDE виконає їх одну за одною тим самим агентом.

### 6.0. Чергу формує локальна модель

Найважливіше: коли ви пишете **одне велике завдання**, план складає сама
локальна модель — окремим коротким запитом вона повертає нумерований список
кроків. Програмний код не містить жодного зашитого списку на кшталт «спершу
база даних, потім реєстрація»: він лише дає моделі контекст проєкту (стек і
файли), перевіряє відповідь і ставить кроки в чергу.

Ланцюг працює так:

1. Ви пишете завдання в чаті.
2. `task_planner` питає модель і отримує JSON: назва кроку, опис, доречні
   інструменти, залежності.
3. Кроки нормалізуються: назва скорочується до 4–12 слів (решта йде в опис,
   який видно при кліку), дублікати зливаються, самопосилання й цикли в
   залежностях прибираються, порядок відновлюється топологічним сортуванням.
4. `queue_engine` зберігає кроки з номерами 01, 02, … і залежностями.
5. `task_executor` бере **перший готовий** крок (усі залежності виконано),
   віддає його справжньому агенту й чекає на результат.
6. Результат перевіряється: «готово» ставиться лише тоді, коли перевірка
   знайшла підтвердження (див. нижче).
7. Після завершення кроку автоматично стартує наступний; коли план
   вичерпано, у чат іде підсумковий звіт.

Якщо модель недоступна або не дала кроків, завдання ставиться **одним**
пунктом, а в статусі буде справжня причина — вигаданого плану не буде.

### 6.1. Центр завдань (нижня панель)

Черга має повноцінний центр керування — вкладка **≡ Завдання** в нижній
панелі (`Ctrl+Alt+W`, або **Агент → Центр завдань**):

- **Шапка:** назва черги, скільки кроків усього / завершено / у черзі / з
  помилками, смуга прогресу й короткий підпис того, що робиться зараз
  (напр. «03 · write_file(auth/register.py) · 2/10 (20%)»).
- **Список:** нумеровані кроки `01`, `02`, … зі статусом, кольоровим
  індикатором (активні кроки пульсують) і рядком поточної операції або
  причини помилки.
- **Деталі (клік по кроку):** що потрібно було зробити, загальна мета,
  статус і витрачений час, залежності (і що саме ще не завершено), доречні
  інструменти, журнал реальних дій агента (виклики інструментів і їхні
  результати) та змінені файли з відкриттям у редакторі.
- **Кнопки:** **⏸ Пауза**, **▶ Продовжити**, **■ Зупинити**, **↻ Повторити**
  (обраний крок), **⌫ Очистити** (завершені), **☰ Журнал**.
- **Права кнопка на кроці:** повторити, скасувати, перемістити вище/нижче,
  показати змінені файли, прибрати.

Межі панелей рухаються мишею, розміри запам'ятовуються між запусками.

### 6.2. Статуси

| Статус | Що означає |
| --- | --- |
| `очікує` | крок ще не починався (або чекає на залежності) |
| `аналіз` | модель читає файли й планує, що саме зробити |
| `виконується` | агент реально викликає інструменти |
| `перевірка` | перевіряємо, що результат справді є на диску |
| `готово` | крок завершено й **підтверджено** |
| `помилка` | крок не вдався (причина видна в деталях) |
| `призупинено` | виконання зупинене користувачем, прогрес не втрачено |
| `скасовано` | крок знято з черги |

Кольорові індикатори: синій — активні стани, зелений — готово, червоний —
помилка, бурштиновий — призупинено, сірий — очікує.

### 6.3. Чому «готово» не можна підробити

Головна пастка локальних моделей — написати «Файл створено», коли файлу
немає. Тому `task_executor.TaskValidator` перевіряє кожен крок:

- якщо крок згадує файли — вони мають існувати в теці проєкту (або агент
  справді їх записав інструментом `write_file`/`edit_file`);
- відповідь-обіцянка («я зроблю це далі») не зараховується;
- порожня відповідь — помилка.

Модель не може сама оголосити успіх: статус ставить код після перевірки.

### 6.4. Перепланування й динаміка

Черга не статична. Якщо підхід не спрацював, **Агент → Перепланувати
залишок роботи** просить модель скласти новий план з огляду на вже
виконані кроки (вони зберігаються — вони реально змінили файли), а
незавершені замінюються. Новий крок можна додати й вручну (**＋ крок** у
шапці центра завдань), і він житиме в тій самій нумерації.

### 6.6. Повторні спроби й захист від циклів

Кожен крок має лічильник спроб (`MAX_ATTEMPTS = 3`). Після вичерпання
повторний запуск не робиться — інакше агент нескінченно повторював би один і
той самий невдалий крок. Крок із невиконаними залежностями не запускається,
навіть якщо він стоїть першим у списку.

**Одна повторна спроба з підказкою.** Локальна модель іноді відповідає
словами замість виклику інструмента (заміряно: приблизно кожен четвертий
прогін на тому самому запиті). Тому перший «непідтверджений результат» не
закриває крок одразу: агент отримує повтор із прямою підказкою «не описуй
дії словами — ВИКЛИКАЙ інструмент». На живому прогоні це підняло
стабільність повного циклу з 2/3 до 4/4.

### 6.6. Додавання задач вручну

- кнопка **≡** у композері чату — бере поточний текст із поля вводу;
- **＋ крок** у шапці центра завдань;
- поле в панелі **Черга завдань** (`Enter` — додати);
- `Ctrl+Alt+Q` — перейти до черги й почати вводити;
- **вставити список**: кожен рядок, що починається з `-`, `*`, `•` або числа
  з крапкою, стає окремою задачею.

```text
- прогнати тести
- виправити знайдені помилки
3. оновити README
```

### 6.7. Керування

| Дія | Як |
| --- | --- |
| Автозапуск | Увімкнено за замовчуванням: щойно крок завершено, береться наступний готовий |
| Пауза / продовжити | **⏸ Пауза** / **▶ Продовжити** у центрі завдань (*Продовжити* також повертає призупинені кроки в чергу) |
| Зупинити виконання | **■ Зупинити** (`Ctrl+Alt+S`): активний крок стає «призупинено» |
| Запустити вручну | **Агент → Запустити наступну задачу** |
| Повторити | **↻ Повторити** або права кнопка → **Повторити** |
| Перемістити | Права кнопка → **Вище** / **Нижче** (номери перенумеровуються) |
| Скасувати / видалити | Права кнопка на кроці |
| Прибрати завершені | **⌫ Очистити** |
| Підсумок | **Агент → Підсумковий звіт** — у чат іде звіт по плану |

Черга зберігається у `%APPDATA%\BlackChpokIDE\queue.json`, тож переживає
перезапуск разом із номерами, залежностями й журналом кроків. Крок, який на
момент закриття був активним, після старту знову стає `очікує` — нічого не
«висить» назавжди.

Композер чату показує лічильник **«Черга: N»**; клік по ньому відкриває
панель.

Вимкнути автозапуск можна в **Налаштування → Агент → Автоматично виконувати
чергу завдань**.

### 6.8. Зависання, які були виправлені

На локальній моделі ці випадки справді зупиняли роботу. Тепер кожен
закритий і покритий тестами (`tests/test_task_queue_engine.py`,
клас `TestNoHang`):

| Що виглядало як «модель зависла» | Справжня причина | Виправлення |
| --- | --- | --- |
| Крок вічно в стані «аналіз», жодної дії з файлами | Крок містив загальну мету → текст перевищував поріг «велике завдання» → замість виконання запускалось **нове планування** (рекурсія) | Готовий крок виконується з `plan_step=True`: розбиття й глибокий аналіз усередині кроку вимкнені |
| Черга мовчки стояла зі списком «очікує» | Крок упав → залежні кроки чекали на нього **вічно** | Після невдачі залежні кроки знімаються (`cascade_failure`) із поясненням, який саме крок їх заблокував |
| Крок «виконується», але агент вільний | `_send` тихо відмовляв (агент ще зайнятий), крок лишався активним | Запуск кроку повертає `True/False`; на `False` крок повертається в чергу |
| Крок повертався в чергу **під час роботи** | Перевірка «завислого кроку» спрацьовувала в проміжку між стартом і запуском потоку | Перевірка часова: крок вважається завислим лише після 25 с без роботи агента |
| На кроці N+1 модель казала «вже зроблено» | Сесія агента накопичувала історію попередніх кроків | Кожен крок — чистий запит (`fresh=True`): окремий фокус, без «пам'яті» про інші кроки |

## 6а. Автономний режим: безперервне покращення проєкту

Режим **Continuous Autonomous Improver** працює всередині вікна IDE (не
окремим процесом): агент сам шукає покращення, ставить їх собі в чергу й
виконує тим самим інструментарієм, що й у чаті. Усе видно в інтерфейсі —
відкрита вкладка, підсвітка змін, diff у стрічці, живий план і журнал.

Панель: **Агент → Автономний режим** або `Ctrl+Alt+A`, а також кнопка
**режим чату** в заголовку сесії (там же видно, до якого чату й теки він
належить). Старт/стоп — той самий `Ctrl+Alt+A`.

Режим **прив'язаний до чату й проєкту**: задачі, які він ставить, дістають
`chat_id` цього чату й зникають разом із ним. Зміна теки під час роботи
питає підтвердження й зупиняє режим — інакше агент почав би правити файли
іншого проєкту без відома користувача.

![Автономний режим](assets/autonomous_panel.png)

| Елемент | Що показує |
| --- | --- |
| **Статус** | `вимкнено` · `працює` · `зупиняється` |
| **Проєкт** | тека, для якої режим увімкнено (кнопка 🗂 змінює) |
| **Зараз** | поточна дія людською мовою + витрачений час |
| **План** | короткий список «що далі»; `◆` — зараз, `·` — далі, `✓` — готово |
| **Черга завдань** | з позначками **«від тебе»** / **«від агента»**, `×` знімає задачу |
| **Журнал дій** | часові позначки кожної події режиму |
| **Поле внизу** | своя задача в чергу (Enter) |

### Як це працює

1. Обираєш теку проєкту й натискаєш **▶ Старт**.
2. Агент сканує проєкт (`blackchpok_ide/autonomous.py`) і знаходить
   конкретні приводи: позначки `TODO`/`FIXME`, проковтнуті винятки
   (`except …: pass`), `print()` замість журналу, завеликі файли, модулі без
   тестів. Додає до цього дослідницьку задачу — пошукати в інтернеті кращі
   практики для залежностей із `requirements.txt`.
3. Знайдене стає задачами черги й одразу виконується звичайним агентом:
   він відкриває файли, править їх, запускає перевірки.
4. Коли черга спорожніла — режим знову сканує проєкт. І так, поки не
   натиснеш **■ Зупинити**.

### Пріоритет користувача

Будь-яка твоя задача стає **першою**, навіть якщо агент уже напланував собі
десяток інших: `TaskQueue.next_pending()` спершу віддає задачі з позначкою
«від користувача». Побачити це можна з черги — вони зверху й позначені ●.

### Коректна зупинка

**■ Зупинити** не обриває роботу посеред файлу:

1. режим переходить у стан `зупиняється` і показує це в панелі;
2. агент дописує поточний хід до кінця;
3. усі змінені вкладки зберігаються на диск;
4. задачі агента знімаються з черги (твої лишаються);
5. режим вимикається.

Незакінчених змін на диску не лишається. Те саме відбувається при закритті
IDE, якщо режим був увімкнений.

### Тільки один проєкт

Одночасно автономний режим може працювати лише з **однією** текою. Спроба
ввімкнути його для другої відхиляється з поясненням, у якому названо
поточний проєкт. Це навмисно: інакше агент правив би два проєкти одночасно,
а в редакторі й журналі змішались би файли.

### Автономний режим і відеокарта

Поки режим увімкнений, модель **не вивантажується**: агент працює
безперервно, і «холодний» старт з'їдав би хвилини на кожен цикл. Політика
простою діє лише тоді, коли режим вимкнено (див. розділ про звільнення
відеокарти).

### Вимоги

- Модель має бути підключена: без неї агент не править код, і старт
  відмовить із підказкою (не «тихо» зламається).
- Дозволи агента діють як звичайно (`workspace` типово): автономність не
  розширює доступ до диска за межі робочої теки.

## 6б. Зупинка агента й звільнення відеокарти

Дві різні дії, які легко переплутати:

| Дія | Що робить | Де |
| --- | --- | --- |
| **Зупинити агента** | обриває поточний запит; модель лишається в пам'яті | **■** у композері, **Агент → Зупинити агента** |
| **Вивантажити модель** | зупиняє `llama-server`, повертає VRAM | **Агент → Вивантажити модель із відеокарти** |

Друге — те, що потрібне, коли ти пішов грати чи рендерити відео, а модель
тримає гігабайти. Є й автоматичний шлях (`blackchpok_ide/power.py`):

- будь-яка твоя дія (натискання клавіші, клік, надісланий запит) скидає
  таймер простою;
- після `engine.idle_unload_seconds` (типово 300 с) простою модель
  вивантажується, і в статусбарі з'являється «Модель вивантажено з
  відеокарти»;
- вимкнути автовивантаження можна полем `engine.unload_when_idle` у
  `settings.json`;
- **в автономному режимі автовивантаження не спрацьовує** — інакше агент
  прокидався б до мертвого сервера й зупинявся;
- модель піднімається назад автоматично, коли ти знову пишеш агенту.

## 7. Скіли агента

Скіл — це текстова інструкція, яку агент застосовує до задачі. Формат такий
самий, як у інших агентних середовищах: тека з файлом `SKILL.md`.

```
.agents/skills/<назва>/SKILL.md
```

Файл складається із заголовка між `---` (поля `name` і `description`) і тексту
інструкції:

```markdown
---
name: release-notes
description: Скласти нотатки релізу за останніми комітами.
---

1. Прочитай `git log --oneline` за останній тиждень.
2. Згрупуй зміни: нове, виправлення, внутрішнє.
3. Запиши результат у `CHANGELOG.md`, не переписуючи старі розділи.
```

Панель **Скіли агента** (`Ctrl+Alt+K` або ✦ на рейці):

| Дія | Що робить |
| --- | --- |
| **○ / ✓** | Увімкнути скіл: його інструкція додається в системний промпт агента |
| **У чат** | Надіслати скіл агенту як задачу |
| **У чергу** | Поставити скіл у чергу завдань |
| **＋ Новий скіл** | Створити теку й шаблон `SKILL.md` |
| **⟳ Оновити** | Перечитати скіли з диска |

Права кнопка на скілі: надіслати в чат, додати в чергу, увімкнути/вимкнути,
відкрити `SKILL.md`, відкрити теку.

Агент також бачить скіли інструментами `list_skills` (перелік) і `read_skill`
(повна інструкція за назвою) — тож може звертатись до них сам.

Вимкнути додавання скілів у промпт: **Налаштування → Агент → Додавати увімкнені
скіли в системний промпт**.

## 8. MCP-сервери

MCP (Model Context Protocol) дає агенту інструменти із зовнішніх процесів.
IDE підключається до них по stdio і додає їхні інструменти до загального набору.

**Налаштування.** Поклади у теку проєкту файл `.mcp.json` (або `.cursor/mcp.json`):

```json
{
  "mcpServers": {
    "blackchpok-ai": {
      "command": "C:\\AI\\blackchpock_ai\\.venv\\Scripts\\python.exe",
      "args": ["C:\\AI\\blackchpock_ai\\server.py"],
      "cwd": "C:\\AI\\blackchpock_ai",
      "env": { "MCP_WORKSPACE": "C:\\AI\\blackchpock_ai" }
    }
  }
}
```

IDE читає конфігурацію при старті, запускає сервери у фоні й показує стан у
панелі **MCP-сервери** (⚒ на рейці): зелений індикатор — сервер працює,
перелічено його інструменти; червоний — не піднявся, з текстом причини.

| Дія | Де |
| --- | --- |
| Перепідключити все | Кнопка **⟳ Перезапустити** в панелі або **Агент → Перепідключити MCP** |
| Підхопити нову конфігурацію | Кнопка **＋ З конфігурації** в панелі |
| Показати/вимкнути автозавантаження | **Налаштування → MCP** (там же показано знайдений файл) |

Інструменти MCP потрапляють до моделі під іменами `mcp__<сервер>__<інструмент>`,
тож не конфліктують із вбудованими. Сервери, що впали, не ламають агента: виклик
повертає помилку, робота продовжується.

Підтримуються саме інструменти (`tools/*`); ресурси, промпти й семплінг — ні.

## 9б. Агент сам добирає інструменти

Агент не «розмовляє» про задачу — він її виконує. За це відповідає
`tool_router.py`: звичайна фраза перетворюється на конкретний виклик.

| Фраза | Що робить агент |
| --- | --- |
| «покажи файли» | `list_dir` |
| «прочитай main.py» | `read_file(path="main.py")` |
| «знайди, де оголошена launch» | `search_text` |
| «знайди в інтернеті новини» | `router:search_web` (а не пошук по коду!) |
| «що ти пам'ятаєш про проєкт» | `router:memory_search` (RAG) |
| «працюй вночі 4 години» | `router:night_shift` |
| «проіндексуй проєкт» | `router:index_project` |
| «які є скіли» | `list_skills` |
| «привіт, як справи?» | нічого — просто відповідає |

### Три механізми

1. **Каталог дій у системному промпті** — модель бачить, що взагалі вміє,
   і не вигадує неіснуючих інструментів.
2. **Прямі схеми `router:*`** — багатофункціональний MCP-роутер ховає
   десятки дій за одним інструментом. Тепер 15 найуживаніших дій
   (`search_web`, `memory_search`, `night_shift`, `index_project`…) мають
   власні схеми, тож модель бачить їх напряму.
3. **Самовиконання, якщо модель лише відповіла текстом** — якщо фраза явно
   вимагає дії, а модель не покликала інструмент, агент виконує знайдену дію
   сам і відповідає її результатом. Перевірено на моделі, яка відмовлялась
   діяти: агент усе одно показав реальний вміст папки.

### Перевірено на живих фразах (Qwen2.5-Coder 14B, MCP підключено)

```
>>> Покажи файли в папці blackchpok_ide
    → list_dir   ✓ відповідь зі справжнім списком файлів
>>> Знайди, де оголошена функція launch
    → search_text ✓ «main_window.py, рядок 1751»
>>> Що ти пам'ятаєш про наш проєкт?
    → router:memory_search ✓ згадав факти попередніх розмов
```

50 перевірок маршрутизації — `python tests/test_tool_router.py`.

2. `memory_search` повертає його в секції «Правила і розмови».

   збережений у першій сесії, знайдено в новій сесії окремого процесу MCP-сервера.

### Нічний режим (night_shift)

Перевірено на реальному виконанні: черга задач пише в SQLite, `work_one`
викликає модель, застосовує патч до файлу, запускає перевірку, оновлює статус.
Захист шляху не дає вийти за робочу теку.

### Виправлено під час перевірки

| Проблема | Було | Стало |
| --- | --- | --- |

## 12. Як це узгоджується з MCP-сервером

Репозиторій містить і сервер MCP (`server.py` + `agent_tools.py` + `vibe_router.py` +
`rag_engine.py`) для MCP-клієнтів, і цю IDE. Це два незалежні входи в одну логіку:

- `server.py` — один інструмент `master_agent_router` для зовнішніх клієнтів (stdio).
- `blackchpok_ide/` — нативне вікно з тим самим принципом «фраза → інструмент».

При цьому IDE тепер може **підключити цей сервер як MCP-сервер** (§8) і
використовувати його інструмент `master_agent_router` поруч зі своїми. Саме так
налаштовано в `.cursor/mcp.json` цього репозиторію.

Офлайн-роутер IDE додатково пробує підвантажити `vibe_router` з кореня репозиторію,
тож набір українських фраз збігається з сервером.

## 13. Часті проблеми

**Вікно не з'являється в .exe.** Антивірус або політика можуть блокувати
однофайлову збірку, бо вона розпаковується в `%TEMP%`. Додай теку в винятки або
зібери onedir-версію:
`python -m PyInstaller --onedir --windowed --name BlackChpok main.py`.

**«Немає з'єднання» в чаті.** Сервер моделі не запущений, або порт інший. Натисни
**⟳** над чатом; якщо нічого не знайдено — відкрий **Хаб моделей** і запусти
модель там. Пресети дають типові адреси (1234, 1235, 11434, 8080, 8000).

**Модель відповідає, але файли не змінюються.** Модель надто мала: 0.5B–1.5B
часто не тримають формат інструментів навіть із запасним розбором. Візьми 3B
або більшу. Якщо у відповіді видно сирий JSON виклику — це стара збірка; у
поточній він вирізається.

**Термінал показує «команда не завершилась».** Натисни **■** біля поля вводу або
`Ctrl+C` — команда перерветься, а сесія лишиться робочою. Якщо сесія «залипла»,
натисни **⟳**, щоб перезапустити її.

**MCP-сервер не запустився.** У панелі **MCP-сервери** буде причина. Найчастіше:
невірний `command` (вкажи повний шлях до `python.exe`), відсутній файл скрипта,
або сервер пише у stdout щось, крім JSON-RPC. Перевір, що команда запускається
вручну з указаним `cwd`. Після правки конфігурації натисни **⟳ Перезапустити**.

**Скіл не з'являється в панелі.** Перевір шлях: `.agents/skills/<назва>/SKILL.md`
(саме тека + файл `SKILL.md`). Файл має починатися із заголовка між `---`.
Натисни **⟳ Оновити** в панелі скілів.

**Черга не виконується.** Вона на паузі (кнопка показує **▶ Продовжити**) або
вимкнено автозапуск у налаштуваннях. Натисни **▶ Запустити** — задача стартує
одразу, щойно агент звільниться.

**Центр завдань каже «чекають на попередні кроки».** Це нормально: наступний
крок справді має залежність. Відкрий деталі кроку — там видно, який саме
крок його тримає. Якщо попередній крок завершився помилкою, натисни
**↻ Повторити** на ньому (або **Агент → Перепланувати залишок роботи**).

**Крок позначено «помилка», хоч модель написала «готово».** Перевірка не
знайшла результату: або файлу немає на диску, або відповідь була обіцянкою.
Причина видна в деталях кроку — це захист від вигаданих результатів.

**Крок не запускається після кількох повторів.** Вичерпано ліміт спроб
(3). Переплануй залишок роботи або прибери крок і додай новий.

**Модель «думає» дуже довго на кожному кроці.** Перевір контекст: якщо він
більший за потрібний, читання промпту сповільнюється. Постав
**Налаштування → Модель → Розмір контексту** менше (напр. `8192`) — на
кроках черги цього досить. І навпаки: якщо агент постійно перечитує файли й
«забуває» попереднє, контексту бракує — підніми до `16384`/`32768`.

**Хочу ще більший контекст, а VRAM закінчилась.** IDE вже це вміє: підніми
**Розмір контексту** до `32768`, і вона винесе KV-кеш у системну пам'ять
(`--no-kv-offload`), лишивши ваги на відеокарті. Заміряно: 32K дає
20.7 ток/с проти 31.7 на 16K — тобто плата ≈35% швидкості за вдвічі
більший контекст. Потрібно ≥16 ГБ RAM.

**Модель стала вдвічі повільнішою (14 замість 31 ток/с).** Майже завжди це
означає, що контекст **не влазить у VRAM** і рушій тихо деградував.
Перевір план запуску в рядку стану хабу: якщо там `KV f16` і 16K — постави
**Розмір контексту = 16384** (або `0`), і IDE перейде на `q8_0`, який дає ту
саму швидкість при половині пам'яті.

**«Немає відкритих файлів» у колонці контексту.** Секція показує саме вкладки
редактора; відкрий файл із провідника або через `Ctrl+P`.

**Хаб не знаходить моделей.** Перевір інтернет і чи не вимкнено джерело
галочкою. TensorArt навмисно не шукає — у нього немає відкритого API.

**Завантаження обірвалось.** Натисни «Завантажити» ще раз: файл докачається з
місця, а не з нуля (лишається `.part`).

**Рушій не стартує / «Модель не запустилась».** Відкрий
`%APPDATA%\BlackChpokIDE\runtime\server.log` — там справжня причина (найчастіше
бракує VRAM: вибери менше квантування або менший контекст).

## 14. Перевірено

### 14.0. Як перевірити самому

```powershell

.\.venv\Scripts\python.exe tools\check_live.py     # живі перевірки на твоїй моделі
```

`check_live.py` іде на **справжній** локальний сервер і виконує справжні
файлові дії. Окремі перевірки:

| Ключ | Що перевіряє |
| --- | --- |
| `controls` | Кожна кнопка, пункт меню й панель центру завдань |
| `setting` | Поле «Розмір контексту»: збереження й вплив на план запуску |
| `server` | Підхоплення вже запущеного сервера, визначення «локальна/хмара», реальний ліміт контексту |
| `launch` | IDE сама піднімає рушій із правильним планом і чекає готовності |
| `plan` | План складає **модель**, а не шаблон (три різні запити → три різні плани) |
| `cycle` | Повний цикл: план → виконання → файли на диску → звіт → перезапуск |
| `replan` | Перепланування зберігає виконане й замінює лише залишок |
| `context` | Запуск рушія з 16K і 32K, фактичний `n_ctx` і відповідь моделі |
| `nomodel` | Робота без моделі: чесні відмови замість вигаданих планів |
