# Screenshot → код

Дата: 2026-11-09.

---

## 1. Стан: частково реалізовано

Агент **уже може** пройти шлях «зображення → розуміння → правка файлу».
Доведено: модель із `mmproj` описує скріншот, потім викликає `read_file` і
`edit_file` тим самим конвеєром.

Агент **не має** окремого механізму, який перетворює координати елемента на
конкретний CSS-селектор чи компонент. Зараз зв'язок «піксель → файл»
встановлює сама модель через пошук у проєкті.

---

## 2. Що реально працює

| Крок | Механізм | Стан |
|---|---|---|
| отримати зображення | `app_screenshot` / `＋` | ✅ |
| передати в модель | `image_url` + base64 | ✅ |
| побачити layout і текст | vision encoder | ✅ |
| знайти файл | `search_text`, `find_files`, `project_tree` | ✅ |
| прочитати | `read_file` | ✅ |
| змінити | `edit_file`, `write_file`, `append_file` | ✅ |
| перевірити синтаксис | `python_check` | ✅ |
| запустити | `run_command` | ✅ |
| новий знімок | `app_screenshot` | ✅ |
| порівняти | модель описує обидва знімки | ⚠️ вручну, без diff |

## 3. Чого немає

### 3.1. Прив'язка координат до компонентів

Немає:

* bounding boxes елементів у координатах **оригіналу**;
* DOM-інспекції Live Preview для точного зв'язку «елемент → файл»;
* пошуку за CSS-селектором або компонентом із зображення.

Тобто на «зроби як на картинці» агент діє через **семантичний** пошук
(«знайди, де описано цю кнопку»), а не через геометрію.

### 3.2. Порівняння знімків

Немає:

* pixel diff;
* структурного порівняння;
* перевірки видимості тексту;
* порівняння bounding box;
* історії знімків.

Pixel diff сам по собі ненадійний (шрифти, згладжування, масштаб дають шум),
тому його треба поєднувати з семантичним описом моделі — але базового
механізму немає взагалі.

### 3.3. Multi-scale

Великі скріншоти (3440×1440) ідуть одним зображенням. Дрібні елементи
втрачаються. Немає ні оглядового кадру, ні crops важливих ділянок.

---

## 4. Реалістичний сценарій сьогодні

```
Користувач: [PNG інтерфейсу] «Зроби, щоб кнопки були як тут»

1. Модель бачить картинку (перевірено).
2. Викликає find_files("*.css") або search_text("button").
3. Читає знайдений файл.
4. Вносить правку через edit_file.
5. Викликає python_check / run_command для перевірки.
6. Може викликати app_screenshot і подивитись результат.
```

Це працює. Але **крок 6 не гарантує порівняння**: модель описує новий знімок
словами, автоматичного «стало / треба» немає.

---

## 5. Що треба зробити далі

1. `capture_region(x, y, w, h)` як окремий інструмент.
2. `analyze_image(path, question)` — вузький інструмент для одного питання
   про зображення.
3. `crop(path, out_dir, box)` + збереження координат відносно оригіналу.
4. Multi-scale: огляд + 2–4 crops для широких скріншотів.
5. `compare_screenshots(a, b)` — спершу геометрія й текст, потім семантика.
6. Історія знімків у межах чату.
7. DOM-міст із Live Preview: `elementFromPoint` → селектор → файл.

Поки цього немає, «screenshot to code» — це **скерована модель агента**, а не
окремий детермінований конвеєр. Так і треба це називати.
