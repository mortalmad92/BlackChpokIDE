## 2. Другий тест: агент сам робить знімок

Запит: «Зроби скріншот екрана інструментом `app_screenshot` і опиши вікна.»

Агент викликав інструмент, знімок (`shot-20497265.png`, 308 КБ) автоматично
потрапив у `pending_images`, модель отримала його і відповіла описом.

### Важливе застереження

Опис повноекранного знімка **3440×1440 був частково вигаданий**: модель назвала
елементи іншого застосунку. Загальний характер вона вловила правильно, але
конкретні деталі — ні.

Це означає дві речі:

1. зображення **справді дійшло** до vision encoder (інакше не було б нічого
   конкретного);
2. **якість недостатня для надійної роботи з великими скриншотами**.

Причина — відсутність multi-scale: знімок іде одним шматком і після
масштабування дрібні елементи нечитабельні. На меншому зображенні (800×552)
модель читала дрібний український текст бездоганно.

**Висновок:** для реальних скриншотів multi-scale — не «покращення», а
обов'язкова умова. Поки його немає, агент надійно працює з невеликими
зображеннями й знімками окремих вікон, а не з повним екраном 4K.

## 3. Два дефекти, які блокували зір

### 2.1. «Балачка» губила зображення

`_chat_only()` збирав повідомлення напряму:

```python
messages = [self.session.system_message(), *self.session.messages]
```

Це обходило `AgentSession.build()` — єдине місце, де `pending_images`
перетворюються на `image_url`. Результат:

```
ANSWER: Я не можу аналізувати зображення, оскільки немає доступу до зображень…
```

Виправлено: `_chat_only()` тепер викликає `self.session.build()`.

### 2.2. Запитання про зображення вважалось розмовою

«Що написано на картках моделей у цьому зображенні?» класифікувалось як
`converse` → шлях без інструментів. Тепер `_is_small_talk()` повертає `False`,
якщо в сесії є `pending_images`: користувач, який прикріпив скриншот, чекає
роботи, а не балачки.

## 3. Передача зображень: механізм

```
_user attach / app_screenshot
        ↓
session.pending_images
        ↓
AgentSession.build()                ← trim() + _attach_images()
        ↓
останнє повідомлення user стає списком частин:
  [{"type":"text", ...},
   {"type":"image_url","image_url":{"url":"data:image/png;base64,…"}}]
        ↓
черга очищується (той самий знімок не дублюється в наступних запитах)
```

Ліміт — 2 зображення в черзі: кожне додає тисячі токенів, а старі знімки
втрачають сенс після нових правок.

## 4. Вимоги до runtime

| Вимога | Наслідок, якщо не виконана |
|---|---|
| `--mmproj` | модель не бачить картинку взагалі |
| сумісний проєктор | llama.cpp падає на несумісності |
| `--image-min-tokens` | дрібний текст інтерфейсу не читається |

`main_window` виставляє `agent.vision_enabled = bool(projector)` лише після
реального запуску з проєктором. Без нього знімки не передаються, щоб сервер
не відхиляв запит.

## 5. Чого немає (відкриті пункти)

1. **Multi-scale аналіз.** Знімок 3440×1440 іде одним шматком. Дрібні
   елементи інтерфейсу при цьому втрачаються. Потрібні оглядовий кадр плюс
   перекривні crops із прив'язкою до координат оригіналу.
2. **`capture_region` як окремий інструмент** із власною схемою.
3. **`crop_image`, `compare_screenshots`, `analyze_image`** — окремі
   інструменти з валідованими схемами.
4. **Історія знімків** для циклу «знімок → правка → контрольний знімок».
5. **Автоматичне визначення, що модель справді бачить.** Зараз перевірка —
   це факт наявності `mmproj` плюс ручний тест; кнопки «Перевірити зір»
   немає.
6. **Маскування чутливих полів** на знімку.

Пункти 1–4 — це наступна фаза. Видавати їх за реалізовані не можна: зараз
агент бачить зображення **цілком**, без ієрархії «огляд → ділянка».

## 6. Практичний сценарій, який працює сьогодні

1. Користувач натискає `＋` і вибирає PNG (або модель сама викликає
   `app_screenshot`).
2. Пише: «Що не так із цим інтерфейсом? Виправ».
3. Модель бачить картинку, викликає `read_file`/`search_text`, знаходить
   файл, викликає `edit_file`.
4. Результат перевіряється `python_check` або `run_command`.
5. Модель може зробити новий знімок і порівняти — але **порівняння
   робить вона сама**, автоматичного pixel/структурного diff немає.
