## Етап 2: старт IDE — 6.3 с → 1.86 с

### 2.1. Що саме гальмувало

Профілювання показало чотири незалежні джерела — **усі в головному потоці**:

| Джерело | Час | Причина |
|---|---|---|
| `discover_server_url` | **8.3 с** | 24 порти × таймаут `connect` (345 мс на закритий порт) |
| `server_responds` | **4.6 с** | до 3 HTTP-спроб, кожна впиралась у таймаут |
| 22× розбір метаданих GGUF | **2.3 с** | `ModelManager.refresh` читав файли повторно |
| `probe_context_window` з UI | **1.0 с** | `tool_schemas()` робить мережевий запит на кожне оновлення панелі |

Ключове відкриття про цю машину: **connect до закритого локального порту
коштує рівно стільки, скільки задано в таймауті**:

```
timeout=0.35 → 369 мс
timeout=0.15 → 152 мс
timeout=0.05 →  61 мс
```

Тобто ціна — не «мережа повільна», а «ми самі попросили чекати».

### 2.2. Виправлення

**`runtime.py` — дешевша перевірка портів.**
Додано `PORT_PROBE_TIMEOUT = 0.05` (було жорстко 0.35) і
`PORT_SCAN_RANGE = 8` (було 24). Разом: 8.3 с → 1.5 с.

**`runtime.py` — кеш `server_responds`.**
Результат (успіх **і** невдача) живе 20 с. Раніше та сама перевірка
повторювалась перед кожним ходом агента й на кожне оновлення панелі.
Додано `forget_server_responds()` — скидання після запуску/зупинки сервера.

**`runtime.py` — `_reconcile_server_url` у фоні.**
Функція узгоджує «плаваючий» порт рушія. Тепер перевірка йде в потоці, а
результат застосовується через `_ui_call`. Інтерфейс малюється одразу.

**`native/gguf.py` — кеш метаданих `read_meta_cached`.**
Ключ = шлях + `mtime_ns` + розмір, тому заміна файлу автоматично дає новий
запис — застарілих даних не буває. Кеш пишеться на диск
(`.gguf-meta-cache.json`), щоб пережити перезапуск. Заміряно на 7 моделях:
**682 мс → 0 мс**.

**`agent.tool_schemas(probe_window=False)` — для інтерфейсу.**
Панель контексту кличе метод кілька разів на секунду; визначення вікна
робить мережевий запит. Тепер UI бере наявне значення, а справжнє
підтягується перед першим ходом агента (там запит уже у фоновому потоці).

### 2.3. Результат

```
БУЛО:   construct: 2251 ms | first paint: 4077 ms | TOTAL: 6328 ms
СТАЛО:  construct:  849 ms | first paint: 1006 ms | TOTAL: 1855 ms
```

**Прискорення 3.4×.** Профіль підтверджує, що мережевих викликів у
головному потоці більше немає — лишились фонові потоки (вони не блокують
кадр) і сам tkinter.

## Етап 3: точний підрахунок токенів

### 3.1. Два дефекти, а не один

**Дефект 1: лічильник не доходив до агента.**
`main_window._wire_exact_tokens` кликав
`getattr(self.agent, "set_token_counter", None)`, а такого методу в
`AgentRunner` **не існувало** — `getattr` повертав `None`, виклик ставав
тихим no-op.

**Дефект 2: `contextvars` не переходять у новий потік.**
Навіть модульний `set_token_counter` не допомагав: лічильник зберігався в
`contextvars.ContextVar`, а агент працює в новому потоці
(`AgentRunner._run` стартує через `threading.Thread`). Перевірено:

```
child thread sees: None
```

**Дефект 3: евристик було ЧОТИРИ.**

| Модуль | Формула |
|---|---|
| `agent.py:669` | `кирилиця/1.6 + латиниця/3.6 + 8` |
| `context_budget.py:198` | `кирилиця/1.6 + латиниця/3.6 + 6 + 2` |
| `context_stats.py:438` | `len(text)/3.5` |
| `tool_lazy.py:611` | `len(json)/3.5` |

Заміряно на одному реченні: **50 проти 23** токенів.

### 3.2. Виправлення

* `contextvars` → звичайна модульна змінна під замком (в `agent.py` і
  `context_stats.py`). Видно з будь-якого потоку.
* Додано `AgentRunner.set_token_counter` — тепер `getattr` не дає no-op, а
  метод додатково **перераховує бюджет**: похідні числа рахувались за
  старою оцінкою.
* Усі чотири формули зведено до **однієї** —
  `context_budget.estimate_tokens`.

### 3.3. Яке число правильне: перевірка на справжньому tokenizer

Заміряно на завантаженій моделі (`NativeRuntime.count_tokens`, тобто
`llama_tokenize`):

| Текст | Точних токенів | Стара формула `/3.5` | Нова єдина |
|---|---|---|---|
| 100 × `а` (кирилиця) | **100** | 28 | 70 |
| українське речення (83 симв.) | **36** | 23 | 50 |
| 100 × `a` (латиниця) | **13** | 28 | 35 |

Висновок: стара формула занижувала кирилицю **утричі** (28 замість 100).
Нова евристика ближча (70 проти 100), а коли модель завантажена — число
взагалі точне. Це важливо: занижена оцінка → рушій відмовляє з
переповненням контексту; завищена → історія ріжеться завчасно.

### 3.4. Виправлений тест, що кодував хибну формулу

`tests/test_context_stats.py` перевіряв `20 <= tokens("а"*100) <= 40` —
тобто **фіксував стару помилку**. Перевірено на справжньому tokenizer:
100 символів кирилиці = 100 токенів. Тест замінено на чесний:

* «оцінка токенів для кирилиці не занижена» — 55..110;
* «кирилиця дорожча за латиницю» — 70 vs 35.
