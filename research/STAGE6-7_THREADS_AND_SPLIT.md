## Етап 6: потокобезпека інтерфейсу

Tkinter не потокобезпечний, і в проєкті вже був правильний механізм —
`main_window._ui_call` (черга + `_drain_ui` у головному потоці). Три місця
його обходили.

### 6.1. `settings_dialog._ui_text` — `after()` з фонового потоку

**Було:**

```python
def _ui_text(self, text):
    self.after(0, lambda: self._runtime_text(text))
```

Викликалось із `work()` (рядки 1051 і 1086) — тобто з фонового потоку.
`after` сам звертається до інтерпретатора Tcl, що заборонено поза головним
потоком. У `chat_panel.py` ця сама пастка вже описана коментарем
(«викликати after() з фонового потоку не можна … main thread is not in main
loop»), а тут лишалась.

**Стало:** черга `queue.Queue` + `_pump_text_queue`, який читає її в
головному потоці через `after(120, …)`. Фон лише кладе повідомлення.

### 6.2. `QueueExecutor` — колбеки з потоку агента

**Було:**

```python
on_status=self.set_status,
on_change=self._update_queue_badge,
```

Обидва чіпають віджети (статусбар, панель черги, центр завдань, панель
контексту), а викликаються з потоку агента.

**Стало:**

```python
on_status=lambda text: self._ui_call(self.set_status, text),
on_change=lambda: self._ui_call(self._update_queue_badge),
```

Так само, як це вже було зроблено для `mcp_watcher` рядком нижче.

### 6.3. `cancel_probe` — гарантований no-op

`main_window.on_close` кликав `getattr(self.chat, "cancel_probe", None)`.
Перевірено:

```
hasattr(ChatPanel, "cancel_probe")  →  False
hasattr(ModelBar,  "cancel_probe")  →  True
```

Метод живе в `chat_panel.ModelBar`, а `ModelBar` **ніде не створюється**.
Тобто таймер опитування не скасовувався ніколи.

**Стало:** пошук іде по кількох власниках (`self.chat`, потім
`chat.model_bar`, потім `self.model_bar`) — і якщо метод колись з'явиться
на панелі, він спрацює.

## Етап 7: `main_window.py` — 318 рядків винесено

### 7.1. Що зроблено

`_register_commands` — **найдовший метод файлу** (318 рядків на 8003).
Він не чіпає tkinter безпосередньо: лише створює `commands.Command` із
посиланнями на методи вікна.

**Винесено в [`command_registry.py`](../blackchpok_ide/command_registry.py):**

* сигнатура `register_all(window)` — вікно приходить аргументом;
* `self.` → `window.`;
* у `main_window` лишилось делегування (5 рядків).

```
main_window.py:  8003 → 7692 рядків  (−311)
command_registry.py: 317 рядків (нова таблиця)
```

Перевірено: реєстр наповнюється тими самими **95 командами** з тими самими
групами й категоріями.

### 7.2. Чому це лише частина роботи

План передбачав розділення на 11 одиниць (~3600 рядків). Я зробив **одну**
— найбезпечнішу, з повним покриттям тестами. Решту свідомо **не робив
наосліп**, і ось причина.

Аудит радив «видалити 13 методів без посилань». Перевірка показала, що
**всі 8** методів зі списку мають справжні тіла й виконують роботу:

| Метод | Що робить |
|---|---|
| `_show_site_if_started` | показує сайт, коли агент його запустив |
| `_speak_answer` | озвучує відповідь |
| `search_project_for` | відкриває пошук по проєкту |
| `_recent_closed_tabs` | меню «Відкрити знову» |
| `inspect_element_at` | читає елемент сторінки |
| `_open_welcome` | показує довідку на порожньому проєкті |
| `_pending_chat_active` | стан «чернетка чату» |
| `_forget_centre` | прибирає центральну панель |

Це **неготові входи** до робочих можливостей: логіка є, виклику немає.
Видалити їх — втратити функції; підключити — змінити поведінку інтерфейсу,
що вимагає окремого рішення власника продукту. Тому вони лишились, і це
зафіксовано як борг, а не «прибрано».

### 7.3. Що лишається для повного розділення

Файл усе ще 7692 рядки / 326 методів. Наступні кроки — за зростанням
ризику (кожен потребує окремого прогону живих GUI-тестів):

| Винести | Рядків | Ризик |
|---|---|---|
| `StatusPresenter` (`set_status`, `_paint_failures`) | ~150 | низький |
| `BrowserController` (сайти, вбудований браузер) | ~195 | середній |
| `McpController` (`_load_mcp_*`, `reload_mcp`) | ~75 | середній |
| `SessionController` (чати) | ~320 | високий |
| `PlanController` (черга, плани) | ~530 | високий |
| `ModelController` (сервер, моделі, контекст) | ~990 | високий |
| `LayoutController` (саші, розкладка) | ~1360 | **найвищий** |

`LayoutController` торкається того, що вже ламалось у Етапі 1
(`_do_apply_sash` і відновлення розкладки), тому його варто робити
останнім і з живим прогоном вікна, а не лише `unittest`.
