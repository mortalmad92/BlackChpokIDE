# Аудит автоматичного запуску MCP

Дата: 2026-11-09. Перевірено на реальному коді та реальним запуском сервера.

---

## 1. Короткий підсумок

**MCP-клієнт і менеджер процесів написані добре й реально працюють.**
Перевірено живим запуском: сервер `blackchpok-ai` стартує через stdio,
виконує `initialize` і повертає інструмент `master_agent_router`.

Головна проблема — не в клієнті, а в **конфігурації та в тому, що показує
інтерфейс**.

| № | Проблема | Стан |
|---|---|---|
| 1 | Конфіг робочої теки вказує на LM Studio (порт 1235), якого немає | сервер запускається, але його внутрішні виклики мертві |
| 2 | `settings.mcp.servers` — порожній список, сервер «увімкнений» | немає явного увімкнення в UI |
| 3 | MCP стартує лише через 400 мс після вікна, без ретраю | збій = «MCP: працює 0 з 1» і край |
| 4 | Немає health check після старту | «працює» означає лише «initialize не впав» |
| 5 | Немає restart policy | померлий сервер не піднімається |

---

## 2. Що працює (підтверджено запуском)

`blackchpok_ide/mcp_client.py`:

* `McpClient` — stdio-транспорт, JSON-RPC, `initialize` handshake, `list_tools`,
  `call_tool`, таймаути, черга запитів.
* `McpManager.load_configs()` (рядок 892) — читає `{"mcpServers": {...}}` і
  «голий» dict, пізніші файли перекривають попередні.
* `McpManager.start_all()` (рядок 926) — запускає все, **не блокуючись на
  помилці одного сервера** (правильно), збирає статуси
  `працює / не запустився: … / вимкнено`.
* `McpPanel.workspace_config_paths()` (mcp_panel.py:25) — шукає `.mcp.json`,
  `.cursor/mcp.json`, `mcp.json`, `.vscode/mcp.json`.

### Реальний прогін

```
CONFIG PATHS: [WindowsPath('C:/AI/blackchpock_ai/.cursor/mcp.json')]
SERVERS: ['blackchpok-ai']
STATUS: {"blackchpok-ai": "працює"}
TOOLS: 1 ['master_agent_router']
```

**Висновок:** транспорт і реєстрація інструментів працюють. MCP не є «фікцією».

## 3. Проблема №1: конфіг вказує на неіснуючий LM Studio

`.cursor/mcp.json` (фактичний вміст):

```json
"env": {
  "MCP_LLM_BACKEND": "lmstudio",
  "MCP_LMSTUDIO_URL": "http://127.0.0.1:1235/v1",
  "MCP_LMSTUDIO_MODEL": "ministral-3-14b-reasoning",
  "MCP_LMSTUDIO_API_KEY": "lm-studio",
  "MCP_RAG_EMBEDDINGS_URL": "http://127.0.0.1:1235/v1/embeddings"
}
```

Тут три розбіжності з реальністю:

1. Порт **1235** — це LM Studio. Поточної IDE піднімає llama-server на **8080**
   з ключем `local`.
2. Модель **`ministral-3-14b-reasoning`** у LM Studio не завантажена й на диску
   відсутня (у `userdata/models` лише Qwen).
3. Отже сервер стартує, `initialize` проходить, інструмент видно — але будь-який
   виклик, що всередині звертається до LLM або до embeddings, поверне помилку
   з'єднання.

Це найковаріший тип дефекту: **статус «працює», а функція не працює.**
Саме тому самоперевірка й панель нічого не підозрюють.

### Наслідок для агента

Агент отримує схеми MCP-інструментів, модель їх викликає, сервер повертає
помилку звернення до 1235. Користувач бачить «інструмент не спрацював», хоча
насправді треба лише узгодити адресу.

## 4. Проблема №2: немає явного увімкнення серверів

`McpSettings` (config.py:407):

```python
servers: list[str] = field(default_factory=list)   # імена ВИМКНЕНИХ серверів
```

У конфігу `"servers": []`. Логіка така: усе, що є у файлі, запускається, окрім
перелічених. Тобто сервер із `.cursor/mcp.json` піднімається автоматично **без
жодної дії користувача** — це добре.

Але зворотний бік: **будь-який** сторонній `.mcp.json` у робочій теці почне
виконувати команди з конфіга без показу користувачу. Оскільки в проєкті діє
режим дозволів і заборона на невідомі команди (вимога безпеки), це варто
лишати, але **показувати в статусі**, що саме запускається й звідки.

## 5. Проблема №3: старт без ретраю

`main_window.py:2197`:

```python
self.after(400, self._load_mcp_async)
```

`_load_mcp_async()` (рядок 2973) одразу віддає роботу у фоновий потік і більше
не повертається до неї. Якщо сервер не встиг піднятись (повільний імпорт
`server.py`, антивірус, cold start Python) — статус лишається
`не запустився: …` до ручного «Перезапустити MCP».

Ретраю немає, бекофу немає, повторної спроби після зміни конфігу немає.

---

## 6. Проблема №4: «працює» не означає «готовий»

`McpManager.start_all()` вважає сервер робочим, якщо `client.initialize()` не
кинув виняток. Не перевіряється:

* що `list_tools()` повернув хоч один інструмент;
* що схеми інструментів валідні (мають `inputSchema`);
* що хоча б один безпечний інструмент реально виконується (end-to-end).

Тому `.cursor/mcp.json` з мертвими env змінними проходить як «працює».

---

## 7. Проблема №5: немає наглядача

Немає:

* періодичного health check (heartbeat);
* виявлення смерті дочірнього процесу;
* політики перезапуску з обмеженням кількості спроб;
* graceful shutdown із очікуванням (у `_on_close` викликається
  `threading.Thread(target=self.mcp_manager.stop_all)`, тобто без очікування —
  процес може лишитись сиротою).

Пункт 4.2 техзавдання не реалізований.

## 8. Як інструменти доходять до моделі (ланцюг перевірено)

```
agent.tool_schemas()                       agent.py:1266
  ├─ TOOL_SCHEMAS (37 вбудованих)          agent_tools.py
  ├─ registry_memory_schemas()             пам'ять NEUROMESH
  ├─ skills_module.tool_schemas()
  ├─ social.tool_schemas()
  └─ manager.tool_schemas()  ← MCP        mcp_client.py
       └─ _router_schemas()  ← прямі дії роутера   agent.py:1365
            (list_dir, read_file, search_web…)
```

Далі `_fit_schemas()` (рядок 1329) лишає стільки схем, скільки вміщається в
40% вікна контексту — це правильне рішення проти `exceed_context_size_error`.

Відповіді інструментів повертаються моделі через `call_tool()` (рядок 1409) і
`tool_orchestrator`. Ланцюг повний: **модель → tool call → MCP → результат →
модель**.

**Висновок:** твердження «модель отримує лише список назв» — хибне. Схеми
передаються повністю, з описами й параметрами; окремі прямі схеми створені,
бо модель не здогадувалась про `intent` роутера.

## 9. Що треба зробити (реалізовано в цьому аудиті)

1. Узгодити env MCP-конфіга з реальним рушієм (8080/`local`), а не з LM Studio.
2. Додати health check після `initialize`: `list_tools()` + перевірка схем.
3. Додати обмежений ретрай старту з бекофом.
4. Додати watchdog: якщо процес помер — позначити статус і спробувати підняти.
5. Показувати в статусі джерело конфіга, щоб користувач бачив, що запускається.

Докладно — у `docs/MCP_SUPERVISOR.md`.
