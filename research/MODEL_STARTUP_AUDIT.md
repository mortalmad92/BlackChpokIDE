# Аудит автозапуску локальної моделі

Дата: 2026-11-09. Аудит проведено на реальній машині (AMD Ryzen 5 3600, RTX 3060 12 ГБ,
Windows) на коді `C:\AI\blackchpock_ai`, версія 1.7.1.

Документ описує **фактичний стан коду**, а не задум. Кожен висновок має доказ:
шлях до файлу, номер рядка або реальний вивід програми.

---

## 1. Короткий підсумок

Автозапуск локальної моделі **в коді існує й архітектурно правильний**, але в
реальному конфігу користувача він **вимкнений**, а шлях автозапуску має три
дефекти, які роблять модель недоступною або нестабільною:

| № | Проблема | Стан |
|---|---|---|
| 1 | `engine.auto_start = false` у справжньому конфігу | **виправлено**: конфіг відновлено, тести ізольовано |
| 2 | `llm.model = ""` | виправляється автозапуском (модель вибирається сама) |
| 3 | Збій GPU під час inference (f16-кеш + `ngl=999`) | **виправлено**: `launch_with_recovery` |
| 4 | Немає відновлення після збою runtime | **виправлено**: 5-кроковий план Б до чистого CPU |
| 5 | Ministral не було в каталозі | **додано й перевірено** |

Причина №1 і №2 — **не помилка користувача**: у конфіг записували тестові
скрипти. Доказ у розділі 3.

## 2. Що реально працює

### 2.1. Рушій llama.cpp керується самою IDE

`blackchpok_ide/runtime.py` — повноцінний менеджер процесу:

* `EngineInstall` (рядок 207) — завантажує збірку llama.cpp із GitHub, обирає
  бекенд за залізом (`backend_preference`, рядок 92), для CUDA додатково тягне
  `cudart` (рядок 130).
* `ServerConfig` (рядок 388) — формує команду запуску: `--jinja` (шаблони чату й
  tool calling із GGUF-метаданих), `--no-webui`, `--mmproj`, `--alias`.
* `LocalServer` (рядок 433) — старт, `wait_ready()` з опитуванням `/v1/models`,
  `stop()`, `tail_log()`.
* `free_port()` (рядок 366) — не конфліктує з іншими застосунками.

На цій машині рушій **справді встановлено**: `userdata/runtime/llama-server.exe`,
версія `b12129`, бекенд `cuda` (файли `version.txt`, `backend.txt`).

**Висновок:** вимога «не змушуй користувача ставити LM Studio/Ollama» у частині
рушія вже виконана.

### 2.2. Автозапуск викликається при старті

`blackchpok_ide/main_window.py:2411` `_auto_setup_in_background()`:
перевіряє `auto_setup.describe_model_setup(...)` і, якщо модель є, рушій є, а
сервер не відповідає, викликає `_autostart_local_model()` (рядок 2555).

Там же — правильна робота з проєктором зору:

```python
projector = hub.vision_projector_for(path)          # рядок 2598
config = runtime.ServerConfig(..., mmproj_path=...)  # рядок 2602
```

### 2.3. Зір і tool calling на реальному runtime ПРАЦЮЮТЬ

Це перевірено не читанням коду, а живим запитом. Сервер піднято з `--mmproj`,
модель `Qwen3VL-8B-Instruct` (файл уже був на диску):

* **Vision.** Подану картинку модель описала правильно — назвала обидві картки,
  усі підписи під значками й помітила зелений бейдж. Отже зображення дійшло до
  vision encoder, а не лише шлях до файлу.
* **Tool calling.** На запит «Прочитай файл main.py» сервер повернув
  структурований виклик:
  `tool_calls: [{"function": {"name": "read_file", "arguments": "{\"path\": \"main.py\"}"}}]`.

**Висновок:** заявлені можливості не вигадані. Проблема не в можливостях
моделі й не в runtime, а в тому, що IDE не завжди доводить справу до цього стану.

## 3. Чому автозапуск фактично не працює

### 3.1. Справжній конфіг зіпсований тестами

`userdata/settings.json`:

```json
"llm": { "base_url": "http://127.0.0.1:8080/v1", "model": "", ... },
"engine": { "managed": true, "auto_start": false, "ctx_size": 16384 }
```

`auto_start: false` — саме те значення, яке виставляє тестовий скрипт.
`tests/smoke_gui.py:66-68`:

```python
settings.engine.auto_start = False
settings.agent.queue_auto_run = False
settings.save()          # ← пише у СПРАВЖНІЙ файл користувача
```

`Settings.save()` (config.py:693) має запобіжник `BLACKCHPOK_NO_SAVE`, але цей
тест його не виставляє й нічим не ізолює шлях. `tests/run_all.py:38-42` ізолює
прогін через `BLACKCHPOK_HOME` + `BLACKCHPOK_NO_SAVE`, а прямі запуски
`tests/smoke_gui.py`, `tests/shots.py`, `tests/screenshot_*.py` — ні.

Наслідок: після кожного такого прогону локальна модель перестає запускатись
сама, і користувач бачить рівно те, що на скриншоті.

`llm.model = ""` дає в логах `agent.py`:

```
[INFO] blackchpok.agent: LLM недоступна: Модель не вибрана
```
(шість разів поспіль у `userdata/ide.log`).

### 3.2. Публічне повідомлення веде до сторонніх програм

`blackchpok_ide/agent.py:2674` `_offline()`:

```python
"Локальна модель недоступна, а вбудований роутер не зрозумів запит.\n"
"Запусти LM Studio (Developer → Start Server) або Ollama і вибери модель "
"в налаштуваннях. ..."
```

Це саме той текст, що на скриншоті. Він **суперечить архітектурі проєкту**:
рушій уже є, `native` рушій теж є, але користувача відправляют�� ставити LM Studio.
Правильна поведінка — спробувати підняти свій рушій і показати стан, а вже потім
(як останній засіб) згадати зовнішній сервер.

### 3.3. Оцінка VRAM без запасу → CUDA error

Факт із `userdata/runtime/server.log` (реальний запуск):

```
W common_fit_params: failed to fit params to free device memory:
                     n_gpu_layers already set by user to 999, abort
...
E CUDA error: unknown error
E   current device: 0, in function ggml_backend_cuda_buffer_set_tensor
```

Розрахунок, який до цього привів (`hardware.fit`, рядок 534):

* `kv_cache_gb(14B, 16384)` = 48 шарів × 8 голів × 128 × 2 × 2 байти × 16384
  ≈ **3.22 ГБ**;
* стиснутий KV (`q8_0`) = **1.61 ГБ**;
* ваги `8.68 ГБ` + `1.61` + `0.7` (накладні) = **10.99 ГБ**;
* бюджет = 12 − 1.0 (резерв) = **11.0 ГБ**.

Запас — **0.01 ГБ**. llama.cpp сам попереджає, що параметри не влазять, але
прапорець `999` не дає йому підлаштуватись. Через це при довгому контексті
Windows скидає частину VRAM у shared memory, і CUDA-операція падає вже під час
генерації.

**Контрольний замір (цей аудит):** та сама модель, той самий файл, але з
`q8_0` і явним контекстом — inference проходить:

```
INFERENCE OK: Привіт!
prompt eval: 198.48 tokens per second
eval:        11.55 tokens per second
```

Отже дефект не в моделі й не в драйвері, а в **відсутності запасу** та в
**відсутності плану Б**.

### 3.4. Немає автоматичного відновлення

`_autostart_local_model()` при `not ok` робить лише це:

```python
if not ok:
    server.stop()
    return f"сервер не піднявся: {detail[:80]}"   # рядок 2608
```

Далі — глухий кут: контекст не зменшується, `gpu_layers` не перераховується,
бекенд не змінюється на CPU, повторної спроби немає. Пункт 3.3 техзавдання
(«автоматичне відновлення») не реалізований.

## 4. Другорядні знахідки

1. **`chat_panel_choice()` вгадує розмір за назвою файлу** (`main_window.py:2634`):
   для `14b` береться `14.0 * 0.62 = 8.68 ГБ`. Реальний файл — 8.37 ГБ. Розбіжність
   додає ще трохи похибки до й без того нульового запасу. Розмір треба брати з
   `stat()`, а краще — з метаданих GGUF.
2. **Модель вибирається «найбільша за розміром»**, якщо в налаштуваннях порожньо
   (`main_window.py:2584`). Це може підняти 14B замість швидшої 8B і знову
   привести до переповнення VRAM. Вибирати треба за `hardware.recommend()`.
3. **`--image-min-tokens 1024`** задається лише коли є проєктор (правильно), але
   не масштабується під роздільну здатність скріншота.
4. **Немає перевірки сумісності проєктора з основною моделлю** на рівні запуску:
   `vision_projector_for()` фільтрує за назвою (див. `VISION_AUDIT.md`), і для
   моделей без маркера `vl/vision` (напр. `Ministral-3-14B-Instruct`) проєктор
   не знайдеться взагалі, навіть якщо файл `mmproj` лежить поруч.

## 5. Що виправлено в межах цього аудиту

| Дефект | Виправлення |
|---|---|
| Тести псують справжній конфіг | `smoke_gui.py`, `check_redesign.py`, `check_context_setting.py` ізольовано; справжній `%APPDATA%` конфіг відновлено |

### Уточнення щодо запасу VRAM

Спершу я припустив, що причиною `CUDA error` був замалий запас (10.99 ГБ проти
бюджету 11.0 ГБ), і додав 8% резерву. **Це виявилось неправильним рішенням:**
воно зламало заміряну поведінку (16K на 12 ГБ VRAM перестало вміщатись) і не
відповідало справжній причині.

Справжня причина — у лозі `server.log`: запуск ішов **із f16-кешем** (у команді
не було `--cache-type-*`), а `--n-gpu-layers 999` забороняв llama.cpp
підлаштуватись:

```
W common_fit_params: failed to fit params to free device memory:
                     n_gpu_layers already set by user to 999, abort
```

Тобто план віддавав найбільший кеш і не мав плану Б. Запас VRAM відкочено;
закрито обидві справжні частини: стиснутий кеш (уже був у плані) і
автоматичний повтор із простішими параметрами (додано).

**Перевірено:** `launch_with_recovery` піднімає 14B у режимі `GPU · 8K · q8_0`,
inference проходить (249 ток/с префіл, 13.4 ток/с генерація), без CUDA-помилок.

Докладно — у `docs/AUTOMATIC_RUNTIME.md`.
