# PRIOR ART — на чому стоїть система

Цей документ — **чесний огляд відомих підходів**, які використані в проєкті.
Жодного твердження про власні винаходи тут немає й бути не може: усі механізми

проєкт спирається.

Для кожного пункту: **що це** → **що з нього взято в BLACKCHPOK IDE**.

## 1. llama.cpp і формат GGUF

**Що це.** `llama.cpp` — C/C++-реалізація інференсу великих мовних моделей
(ggml як тензорна бібліотека). GGUF — контейнерний формат для ваг і метаданих:
магія `GGUF`, версія, лічильники тензорів і ключів, далі пари «ключ-значення»
(рядок = `uint64` довжина + UTF-8) і тензори. Метадані містять архітектуру,
кількість шарів, тренувальний контекст, розмірність ембедингів, кількість голів,
тип quantization, tokenizer і **шаблон чату** (`tokenizer.chat_template`).

**Що взято:**

* рушій не реалізується з нуля — викликається `llama.dll` зі збірки
  llama.cpp (`native/_bindings.py`);
* власний читач метаданих GGUF (`native/gguf.py:read_meta`) — за
  специфікацією формату, з mmap і без завантаження великих масивів;
* таблиця `llama_ftype` → назва quantization (`native/_quant.py`, копія
  переліку з `llama.h`);
* формула обсягу KV-кешу: `layers × kv_heads × head_dim × 2 × ctx × байтів`
  (`native/inspect.py:kv_cache_gb`) — та сама, що в llama.cpp;
* порядок семплерів `penalties → top_k → top_p → min_p → temp → dist`
  (`native/sampling.py`) — типовий для llama.cpp;
* застосування Jinja-шаблону чату через `llama_chat_apply_template`
  (`native/chatfmt.py:ChatFormatter.render`).

**Не взято:** збірка llama.cpp не входить у репозиторій — вона ставиться
окремо (`runtime.py:EngineInstall`) у `userdata/runtime`.

## 2. BM25 і SQLite FTS5

**Що це.** BM25 — класична функція ранжування документів за запитом (Robertson &
Zaragoza, 2009): враховує частоту терміна в документі, рідкість терміна в
колекції (IDF) і нормування на довжину документа. SQLite FTS5 надає
повнотекстовий індекс і вбудовану функцію `bm25()`; значення **від'ємне**, менше
= краще.

**Що взято** (`pcmm/retrieval.py:Retriever._lexical`):

```sql
SELECT m.*, bm25(memory_fts) AS rank_score
FROM memory_fts JOIN memories m ON m.rowid = memory_fts.rowid
WHERE memory_fts MATCH ? AND m.superseded_by = ''
ORDER BY rank_score LIMIT 60
```

* BM25 рахує сама SQLite — власної реалізації немає;
* від'ємні значення нормалізуються в 0..1 через `(score - worst) / span`;
* **запасний шлях** на випадок, коли FTS5 недоступний або MATCH не спрацював:
  звичайний підрахунок входжень термів у `content+summary+tags`
  (`_lexical_fallback`, до 4000 рядків);
* через відсутність стемера у FTS5 застосовано **префіксні запити** (`"term"*`)
  і грубу «скорочену основу» для довгих слів (відкидання двох останніх літер) —
  це прямо названо евристикою в коментарі, а не лематизацією.

Той самий BM25/FTS5 використовує й старий файловий RAG (`rag_engine.py`).

## 3. Косинусна схожість і векторний пошук

**Що це.** Косинус кута між векторами: `dot(a,b) / (‖a‖·‖b‖)`. Для
L2-нормалізованих векторів дорівнює скалярному добутку. Класичний підхід
векторного пошуку — знайти k найближчих сусідів.

**Що взято:**

* `native/embeddings.py:cosine()` — власна реалізація без numpy (чистий Python),
  повертає `0.0` для різних розмірностей, а не «тихо 1.0»;
* `top_k()` — найближчі сусіді за косинусом;
* `pcmm/retrieval.py:_semantic()` — скалярний добуток нормалізованих векторів
  (спрощений косинус), кандидати беруться з `memories.embedding != ''`;
* `engine._normalise()` — L2-нормалізація, щоб косинус дорівнював добутку.

**Специфіка цього проєкту (інженерна, не алгоритмічна):** вектори рахує **та
сама генеративна модель**, якою генерується текст, методом **mean pooling**
прихованих станів усіх токенів (`engine.embed`). У docstring зафіксовано
причину: для генеративних моделей останній токен кодує «що буде далі», і
косинус між кодом і SQL виходив 0.90 — тобто розділення не було.

**Обмеження, назване відкрито:** повноцінного ANN-пошуку (HNSW, IVF) немає —
семантика перебирає до 5000 рядків лінійно. Для обсягів персональної пам'яті
цього достатньо; для мільйонів записів — ні.

## 4. Reciprocal Rank Fusion (RRF)

**Що це.** Спосіб об'єднати кілька ранжованих списків без узгодження шкал
(Cormack, Clarke, Buettcher, 2009): документ отримує
`Σ 1/(k + rank_i)` по каналах, де `k` — згладжувальна стала.

**Що взято:** **сам принцип** об'єднання різнорідних каналів, але **не формула
RRF**. Замість `1/(k+rank)` використано **зважену суму нормалізованих оцінок**:

```python
# pcmm/retrieval.py:BASE_WEIGHTS
{"lexical": 0.34, "semantic": 0.34, "graph": 0.12, "temporal": 0.10, "confidence": 0.10}
```

Ваги змінює `choose_policy()` залежно від запиту. `pcmm/__init__.py` згадує RRF
у списку відомих механізмів — і це коректно лише як «споріднений підхід», а не
як «ми реалізували RRF». **Чесно: RRF у коді немає.**

MRR у бенчмарку (`bench.py:321`, `1/rank`) — це метрика оцінки, а не механізм
об'єднання; плутати їх не можна.

## 5. Prefix caching / переиспользование KV-кешу

**Що це.** У transformer-декодері кожен новий токен потребує ключів і значень
усіх попередніх. Якщо новий запит має той самий префікс, що й попередній,
обчислені K/V можна не перераховувати — досить продовжити з наявної позиції.
llama.cpp надає для цього `llama_memory_seq_rm`, `llama_memory_seq_pos_max`,
`llama_memory_clear`.

**Що взято** (`native/kv.py:CacheManager`):

* «дзеркало» вмісту кешу — список токенів у Python;
* `_common_prefix()` — найдовший спільний префікс старого й нового промпту;
* `truncate(keep)` — ріже хвіст через `llama_memory_seq_rm`; якщо рушій
  відмовив — повне очищення й повернення **0** (реальна довжина, не бажана);
* `prepare(tokens)` — повертає `skip`, з якого треба декодувати;
* `committed(tokens)` — фіксує, що токени справді декодовані.

Це стандартний підхід; у docstring прямо написано «класичний prefix caching;
нічого екзотичного».

**Виміряний ефект** (мої прогони, 14B Q4_K_M, ctx 4096, RTX 3060): prefill
повторного промпту з 1547 токенів — **0.4–7.5 мс** проти **1497.9 мс** для
свіжого.

## 6. RAG

**Що це.** Retrieval-Augmented Generation (Lewis et al., 2020): генерація
обумовлюється не лише параметрами моделі, а й документами, знайденими зовнішнім
пошукачем. Класична схема: індекс → пошук за запитом → додати знайдене в промпт →
згенерувати відповідь.

**Що взято:**

* сам принцип: `pcmm/service.py:project_context()` збирає блок зі спогадів і
  віддає його як текст для промпту;
* Пояснення кожного знайденого фрагмента (`Hit.explanation`) — щоб було видно,
  **чому** він у контексті, а не просто «ось результати»;
* окремий файловий RAG для коду (`rag_engine.py` + `rag.py:RagService`) —
  індексація файлів проєкту й пошук по них.

**Відмінність, яку варто назвати:** у проєкті RAG застосовано не до документів, а
до **власної пам'яті тверджень** із типами (`error`, `fix`, `constraint`…),
впевненістю й часовою дійсністю. Це інженерне застосування того самого принципу,
а не новий алгоритм.

## 7. MemGPT

**Що це.** Підхід (Packer et al., 2023) до «операційної системи для LLM»:
модель сама керує власною пам'яттю через інструменти — вирішує, що записати в
довготривале сховище, що підняти в робочий контекст, що витіснити. Ключова ідея —
**ієрархія пам'яті** (основна в контексті / зовнішня в сховищі) і те, що
переміщення між рівнями ініціює сама модель.

**Що взято:**

* модель керує пам'яттю **сама**, через інструменти `memory_store`,
  `memory_search`, `memory_recall`, `memory_update`, `memory_project_context` —
  це прямий аналог ідеї;
* ієрархія: робочий контекст (промпт) ↔ довготривале сховище (SQLite) ↔
  «забуте, але не втрачене» (`superseded_by`, `memory_versions`);
* перед завантаженням у контекст відбувається **відбір** під бюджет
  (`BudgetGovernor`), а не «все, що знайшлось».

**Що не взято:** автоматичної компресії історії діалогу за допомогою самої моделі
(«recursive summarization» зі статті) немає.

## 8. Generative Agents (memory stream)

**Що це.** Park et al. (2023), «Generative Agents: Interactive Simulacra of Human
Behavior». Агенти мають **потік пам'яті** (memory stream) — журнал спостережень.
Для дії виконується **retrieval** за трьома сигналами: **recency** (свіжість),
**importance** (важливість, оцінює сама модель), **relevance** (релевантність
запиту). Далі — **reflection**: періодичне узагальнення потоку у вищі за рівнем
висновки.

**Що взято:**

* журнал як джерело істини: `memories` + `memory_events` (кожна дія пишеться);
* **recency**: `Retriever._temporal()` — `0.7 · exp(-age_days / 30) + 0.3 ·
  recency`, тобто часовий спад із півперіодом 30 днів;
* **importance**: `KIND_WEIGHT` (`constraint` 1.30, `fix` 1.20, … `tool` 0.80) і
  поле `confidence` — окремо від важливості, як і в статті;
* **relevance**: лексемний і семантичний канали.

**Що не взято:** **reflection** як окремий механізм узагальнення немає.
Найближче, що є, — `repository.consolidate()`, але це дедуплікація, а не
породження висновків вищого рівня.

Також важливо: у статті `importance` оцінює **модель** запитом; у проєкті
важливість задана таблицею ваг за типом — це простіше й детерміноване, але й
менш гнучке.

## 9. LoCoMo і LongMemEval

**Що це.** Бенчмарки для оцінки довготривалої пам'яті діалогових агентів.

* **LoCoMo** (Maharana et al., 2024) — дуже довгі діалоги (десятки сесій) із
  питаннями, які вимагають: одно- і багатокрокового пригадування, розуміння
  часових проміжків, знання про співрозмовника, відстеження змін фактів із часом.
* **LongMemEval** (Wu et al., 2024) — п'ять здібностей: витяг інформації з
  історії, пригадування деталей, відстеження оновлень знань, узагальнення
  часових проміжків, уникання згадок про відсутню інформацію.

**Що взято (як орієнтир, не як реалізація):**

* **відстеження оновлень знань** — саме під це побудовані `superseded_by`,
  `valid_from`/`valid_to`, `memory_versions` і таблиця `contradictions`. Це та
  сама «knowledge update»-здібність, яку міряє LongMemEval;
* **часові проміжки** — `_temporal()` зі спадом і `accessed_at`;
* **уникання згадок про відсутнє** — `memory_recover` з `integrity` і чесні
  `✗`-відповіді замість вигаданого успіху.

**Що НЕ зроблено:** система **не прогнана** ні через LoCoMo, ні через
LongMemEval. Власний набір — 6 запитів (`bench.CASES`). Твердити про якість
пам'яті в термінах цих бенчмарків підстав немає.

## 10. Causal memory / граф знань

**Що це.** Зберігання знань як орієнтованого графа: вузли — сутності/твердження,
ребра — типізовані відношення (`caused`, `depends_on`, `contradicts`, …). Обхід у
ширину з обмеженою глибиною дає «сусідів», яких немає в текстовому збігу.
Споріднені реалізації: графові БД (Neo4j), `petgraph` у Rust, типові схеми
knowledge graph у RDF/SPARQL.

**Що взято:**

* таблиця `memory_links(src, dst, relation, weight)` — напрямлений граф у SQLite,
  без окремої графової БД;
* 7 типів зв'язків (`models.RELATIONS`);
* `repository.neighbours(id, depth)` — обхід у ширину з обмеженням глибини,
  рівно як це робить будь-який графовий API;
* `retriever._graph()` — підтягує **один крок** сусідів від 8 найкращих
  кандидатів (не повний обхід);
* `ContextPredictor._has_fix()` — перевіряє, чи має помилка зв'язок `fixed_by` або
  `supersedes`.

**Що це дає практично:** у тестовому наборі два запити («що було з помилкою
theme» і «як виправлено імпорт») дали по 2 результати, і граф допоміг знайти
другий — виправлення — за зв'язком, а не за словами.

**Не взято:** транзитивного замикання, виводу нових фактів із графа
(матеріалізації), SPARQL-подібних запитів.

## 11. Стохастичне семплінування

**Що це.** Способи вибору наступного токена з розподілу, який видає модель:

* **temperature** — масштабування логітів перед softmax: `T < 1` робить розподіл
  гострішим, `T > 1` — пласкішим; `T = 0` = детермінований вибір (greedy);
* **top-k** — лишити k найімовірніших токенів, решту відкинути;
* **top-p (nucleus)** — лишити найменший набір токенів із сумарною ймовірністю
  ≥ p (Holtzman et al., 2019);
* **min-p** — лишити токени з ймовірністю ≥ `min_p × p_max` (Nguyen et al., 2024);
* **repetition / presence / frequency penalties** — штрафи за повторне вживання
  токенів.

**Що взято** (`native/sampling.py`):

* усі п'ять механізмів реалізовані **самплерами llama.cpp**, не власним кодом;
* фіксований порядок `penalties → top_k → top_p → min_p → temp → dist`, з
  поясненням у docstring: штраф має діяти на сирі логіти, `temp` — останньою перед
  випадковим вибором;
* `temperature <= 0` → `llama_sampler_init_greedy()` (детерміновано);
* `LIMITS` — жорсткі межі, за які користувач не вийде (щоб «фільтр, що нічого не
  фільтрує» не зламав генерацію);
* `StopMatcher` — коректне відрізання стоп-послідовностей у потоці: тримає хвіст
  довжиною в найдовший стоп, щоб не «з'їсти» легітимний текст, який лише
  починається так само.

**Не працює:** `grammar` (GBNF) — самплер не додається, бо словник на момент
побудови ланцюжка ще 0 (деталі — в аудиті, розділ 5.2).

## 12. Інші відомі підходи, які явно використані

| Підхід | Що це | Де в проєкті |
|---|---|---|
| Jaccard-перекриття лексем | `|A∩B| / |A∪B|` | `models.overlap()` для виявлення дублікатів |
| Евристика суперечності | високе перекриття теми + низька схожість решти | `models.contradiction_score()` — прямо названа евристикою |
| Експоненційний часовий спад | `exp(-age/half_life)` | `retrieval._temporal()` |
| Knapsack-подібний відбір за «цінність/токен» | жадібний відбір за щільністю цінності | `budget.BudgetGovernor.fit()` |
| Бінарний пошук по довжині тексту | пошук максимального префікса, що влазить у ліміт | `budget.trim_to_tokens()` |
| SQLite Backup API | консистентний бекап під WAL | `store.backup()` |
| Перцентилі p50/p95/p99 | статистика вимірів | `bench.percentile()` |
| Abort callback | callback, що повертає `True` для переривання графа | `engine._AbortCallback` |
| Функція виклику інструментів (tool calling) | JSON-схема + виклик + результат | `agent_tools.TOOL_SCHEMAS`, `chatfmt.extract_tool_calls` |
| MCP (Model Context Protocol) | стандарт підключення інструментів через stdio | `mcp_client.py` |

## Підсумок

Система стоїть на **відомих механізмах**: llama.cpp/GGUF для інференсу, BM25 і
FTS5 для лексики, косинус для семантики, зважена сума каналів (споріднена з RRF,
але не RRF) для гібридного ранжування, prefix caching для KV, RAG-принцип для
контексту, ідеї MemGPT для керування пам'яттю моделлю, Generative Agents для
recency/importance/relevance, LoCoMo/LongMemEval як орієнтир для відстеження
оновлень знань, граф знань для зв'язків і стандартні семплери llama.cpp.

Три речі, які треба назвати прямо:

1. **RRF у коді немає** — є зважена сума з нормалізованих оцінок; згадка RRF у
   `pcmm/__init__.py` коректна лише як «споріднений підхід».
2. **Система не прогнана через LoCoMo чи LongMemEval** — власний набір 6 запитів.
3. **`reflection` із Generative Agents не реалізовано** — `consolidate()` це
   дедуплікація, а не породження висновків вищого рівня.
