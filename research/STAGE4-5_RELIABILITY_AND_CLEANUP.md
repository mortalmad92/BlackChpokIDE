## Етап 4: рушій і пам'ять

### 4.1. `bridge` обходив чергу й телеметрію

**Було.** `bridge.chat` і `bridge.chat_stream` кликали `rt.engine.generate*`
**напряму**, повз `NativeRuntime`. Наслідки:

* `rt._pending` не зростав → `bridge.busy()` **завжди** `False`;
* `_record()` не викликався → запити не потрапляли в історію;
* тайм-аут `NativeRuntime.generate` не діяв.

Агент ходить саме через `bridge` (`llm_client._chat_embedded`), тому
«зайнятий рушій» не бачив ніхто.

**Стало.** Обидві функції йдуть через `NativeRuntime.generate` /
`generate_stream`. Перевірено наживо:

```
busy() before: False
chunks: 3
busy during stream (any True): True     ← раніше тут завжди було False
busy after: False
pending now: 0
```

### 4.2. `generate_stream` — тайм-аут і покинутий генератор

**Було.** Потокова функція приймала лише `should_stop` — тобто **агент**
(який іде стрімом) міг чекати вічно. Крім того, `_enter()` збільшував
`_pending`, а `finally` спрацьовує лише коли генератор дочитано або
закрито: якщо викликач кидав ітерацію, лічильник лишався >0 **назавжди**.

**Стало.** Додано `timeout` (перетворюється в `should_stop`, як у
блокуючому шляху) і обробку `GeneratorExit` — лічильник знімається завжди.

### 4.3. SQLite: `with conn` не закриває з'єднання

Перевірено дослідом:

```
with sqlite3.connect(path) as conn:  ...
conn.execute("SELECT 1")   →  працює (з'єднання ВІДКРИТЕ)
```

`with` робить лише commit/rollback. Кожен `encode` / запис у кеш лишав
відкритий дескриптор і WAL; на Windows це зрештою блокує базу.

**Виправлено:** `EmbeddingService._connect` став контекстним менеджером
(`@contextlib.contextmanager` + `finally: conn.close()`), тому всі **5**
місць використання закривають з'єднання автоматично. `pcmm/store.py:backup`
— явний `try/finally` (там `with` теж не закривав файл-призначення).

Перевірено: після блоку `conn.execute` кидає `ProgrammingError: Cannot
operate on a closed database`.

### 4.4. Embeddings скидають KV-кеш — тепер про це сказано

Кожен текст для embedding декодується з позиції 0, інакше приховані стани
прийшли б із чужого контексту. **Обійти це в межах одного контексту
неможливо** — тому «виправити» тут нічого, але мовчати про це не можна:
раніше запис у пам'ять непомітно знищував кеш префікса, і наступний хід
пере-прокладав весь промпт. Тепер у журналі є попередження.

### 4.5. Обрізання промпту відрізало СИСТЕМНИЙ промпт

Коли промпт не влазив у вікно, рушій брав `prompt_tokens[-keep:]` —
тобто відрізав **голову**, а там роль, правила, описи інструментів і
обмеження проєкту. Модель мовчки позбавлялась інструкцій.

**Стало:** журнал прямо називає небезпеку («відрізано N токенів З ГОЛОВИ
(там системний промпт і правила)»), а в статистиці з'являється
`truncated_head_tokens`, щоб викликач міг попередити людину.

### 4.6. `.part` — прибирання недокачуваних файлів

**Було.** При скасуванні або пошкодженому файлі `.part` лишався назавжди.
`_scan` його не показує (фільтр за `.gguf`), тому місце займалось
невидимо. На цій машині так лежало **945 МБ**.

**Стало.** `_drop_part()` прибирає файл при скасуванні й пошкодженні, але
**НЕ** при мережевому обриві — такий `.part` придатний для докачки через
`Range`. Наявний 945-МБ файл теж видалено.

## Етап 5: мертвий код і дублювання

### 5.1. Мертвий код

| Що | Дія |
|---|---|
| `manager._scan`: `if entry.is_projector: continue`, далі `if not entry.is_projector:` — недосяжне | прибрано другу умову |
| `gguf._array_length()` — завжди `0`, **ніде не викликався** | видалено |
| `chatfmt.ToolCallParser` — оголошений, експортований, не інстанційований | **підключено** в `generate_stream` |
| `live_browser_panel.py` (372 рядки) — жодного імпортера | видалено |
| `main_window._git_branch` / `_git_changes` — читались, **ніколи не присвоювались** | замінено на справжні дані |
| `native_unload_on_exit` — зберігався, не читався | тепер поважається |

**Про `ToolCallParser`:** це не «сміття», а реалізована функціональність,
яку просто не викликали. Його призначення — не показувати користувачу
сирий JSON виклику в стрімі. Підключено в `generate_stream`:

```
вхід:  'Дам відповідь. {"name": "read_file", "arguments": {}} Готово.'
вихід: 'Дам відповідь.  Готово.'      ← JSON прибрано
calls: ['read_file']                  ← виклик розпізнано
```

**Про git-чип:** `header_bar.set_git` показує гілку й кількість змін, але
`main_window` читав атрибути, яких ніхто не встановлював — тобто вічно
«⑂ —». Додано `diff_stats.git_branch()` (з деградацією, коли git немає) і
`_git_badge_state()` з кешем 15 с, щоб не запускати зовнішній процес на
кожне оновлення шапки.

### 5.2. «Локальний чи хмарний»: сім реалізацій → одна

Було сім незалежних способів, з різними списками хостів:

| Місце | Підхід |
|---|---|
| `llm_client._is_local_url` | 4 маркери підрядком |
| `auto_setup._is_local_url` | власний `LOCAL_HOSTS` із 7 хостів |
| `providers.LocalProvider.is_local` | завжди `True` |
| `providers.ModelEntry.is_local` | `kind == LOCAL` |
| `main_window._model_summary` | інлайн-список + перевірка `native://` |
| `browser_panel.is_local_url` | власний набір хостів |
| `config.LLMSettings.normalise` | інлайн-перевірка схеми |

**Стало:** `provider_adapters.is_local_url()` + `is_cloud_url()` +
`LOCAL_HOSTS`/`LOCAL_PREFIXES`. Решта — тонкі делегати.

Важлива різниця в поведінці: стара реалізація шукала **підрядок**, тому
`https://notlocalhost.example.com/v1` вважався локальним. Нова розбирає
хост і порівнює точно.

Перевірено: `llm_client`, `auto_setup`, `browser_panel` і спільна функція
дають однаковий результат на всіх тестових адресах. `file://` — свідомий
виняток браузера (це файл на диску, а не сервер).
