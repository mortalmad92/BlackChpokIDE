# Аудит зору (Vision) і візуального агента

Дата: 2026-11-09. Перевірено реальними знімками екрана й реальними запитами до
локальної моделі.

## 1. Короткий підсумок

Найважливіше: **візуальний ланцюг у проєкті існує і працює end-to-end.**
Це не заготовка й не імітація. Доведено нижче трьома незалежними тестами.

| Компонент | Стан | Доказ |
|---|---|---|
| Захоплення екрана без сторонніх бібліотек | працює | знято 3440×1440, 317 КБ PNG |
| Пошук вікон за заголовком/класом/PID | працює | знайдено 5 вікон із класами |
| Кодування у `image_url` + base64 | працює | `llm_client.image_message()` |
| Передача в image encoder | **працює** | модель описала вміст картинки |
| Прикріплення знімка агентом | працює | `_attach_capture()` |
| Прикріплення користувачем через UI | **відсутнє** | кнопки «камера» немає |
| Чесність значків Model Hub | **не працює** | значок за назвою, не за фактом |
| Multi-scale аналіз | відсутній | — |

## 2. Захоплення екрана: працює без Pillow

`blackchpok_ide/screenshot.py` — власна реалізація на Win32:

* `capture_window(info, path)` (рядок 345) — `PrintWindow` з
  `PW_RENDERFULLCONTENT`, тобто ловить і вміст поза екраном;
* `capture_screen(path, rect=...)` (рядок 373) — увесь екран або прямокутник;
* `find_windows()` — пошук за заголовком, **класом вікна або PID**;
* власний PNG-кодер через `zlib` — жодних залежностей.

Це принципово правильне рішення: `PIL` у `requirements.txt`
закоментований, а знімки все одно працюють.

### Реальний прогін цього аудиту

```

                width=3440, height=1440) exists: True size: 317596
```

Знімок відкрито й перевірено оком: на ньому видно робочий стіл, вікно IDE та
панель задач. Отже `capture_screen` повертає **справжній артефакт**, а не рядок
«скриншот успішно зроблено».

## 3. Зображення реально доходить до vision encoder

### 3.1. Механізм у коді

`llm_client.image_message()` (рядок 276) збирає мультимодальне повідомлення:

```python
parts.append({"type": "image_url",
              "image_url": {"url": f"data:{mime};base64,{encoded}"}})
```

`agent._attach_images()` (рядок 691) приєднує ці частини до **останнього
повідомлення користувача**, а `ActorSession.build()` (рядок 668) очищає чергу
після відправки, щоб той самий знімок не дублювався в кожному запиті.

Черга наповнюється у `_attach_capture()` (рядок 2377) для інструментів
`app_screenshot`, `project_screenshot`, `web_screenshot`, `window_screenshot`,
але **лише якщо** `self.vision_enabled`.

`vision_enabled` виставляється у двох місцях:

* `main_window.py:2625` — після автозапуску: `bool(projector)`;
* `main_window.py:6483` — після вибору моделі у хабі.

Логіка правильна: без `--mmproj` знімки не додаються, бо сервер відхилив би
запит.

### 3.2. Контрольний тест

Сервер піднято з `--mmproj mmproj-Qwen3VL-8B-Instruct-F16.gguf`, у запит подано
ту саму картинку, що й у завданні (скриншот хаба моделей), і питання: які
заголовки й підписи видно.

Відповідь моделі:

> **Заголовки карток моделей:** `Ministral 3 14B Instruct`,
> `Ministral 3 14B Reasoning`
> **Підписи під зеленими значками:** `Tool Calling` → `Виклик інструментів`,
> `Vision` → `Аналіз зображень`, `Reasoning` → `Складне міркування`

Модель розпізнала дрібний текст українською. Отже зображення **фактично
пройшло preprocessing і vision encoder**, а не було замінене шляхом до файлу.

## 4. Головний дефект: значок Vision не відповідає дійсності

`blackchpok_ide/model_caps.py` визначає можливості **лише за назвою**:

```python
VISION_MARKERS = ("vision", "-vl", "vl-", "llava", "pixtral", ...)
```

Наслідки:

1. **Хибно-негативні.** `Ministral-3-14B-Instruct-2512` — мультимодальна модель
   (safetensors, `mistral3` на HF), але в назві немає `vl`/`vision`, тому значка
   Vision не буде.
2. **Хибно-позитивні.** Модель із `-vl` у назві отримує значок, навіть якщо
   поруч **немає файлу `mmproj`**. Тоді llama.cpp запуститься без проєктора,
   `vision_enabled` стане `False`, і знімки тихо не передаватимуться — а значок
   у хабі світитиметься зеленим.
3. Значок ніколи не знімається після невдалого тесту.

Тобто пункт 6 техзавдання («не став значок, якщо runtime може обробляти тільки
текст») **не виконаний**.

### Додатково: `vision_projector_for()` глухо відсікає не-`vl` моделі

`model_hub.py:1060`:

```python
if not any(marker in stem for marker in ("-vl", "_vl", "vl-", "vision",
                                         "multimodal", "llava", "minicpm-v")):
    return None
```

Для `Ministral-3-14B-Instruct` проєктор **не буде знайдено взагалі**, навіть
якщо `mmproj-Ministral-3-14B*.gguf` лежить у тій самій теці. Автозапуск тоді
підніме модель без зору й чесно виставить `vision_enabled = False` — але
користувач отримає модель без зору там, де зір технічно можливий.

## 5. Чого немає

1. **Кнопки «камера» в полі введення.** `chat_panel.py:543` має лише `＋`
   («Додати файл»), і `_attach_file()` (рядок 2863) читає файл **як текст**:

   ```python
   content = Path(path).read_text(encoding="utf-8", errors="replace")
   self.input_box.insert("end", f"\n\n```{Path(path).name}\n{snippet}\n```\n")
   ```

   Якщо користувач вибере PNG — у чат потрапить сміття з бінарника. Тобто
   **прикріпити зображення через UI неможливо взагалі**.

2. **Multi-scale аналізу.** Знімок 3440×1440 стискається до 8 МБ і йде одним
   шматком. Дрібний текст інтерфейсу при цьому втрачається. Немає ні оглядового
   кадру, ні збільшених crops із прив'язкою до координат оригіналу.

3. **`capture_region` як окремого інструмента.** Є `app_screenshot` з
   координатами, але повноцінного API «виділити область» немає.

4. **Порівняння знімків.** Немає ні pixel diff, ні структурного порівняння, ні
   історії знімків для циклу «знімок → правка → контрольний знімок».

5. **Індикатора захоплення** й маскування чутливих полів.

## 6. Другий контрольний тест: агент сам робить знімок

Запит: «Зроби скріншот екрана інструментом `app_screenshot` і опиши, які вікна
на ньому відкриті.»

Що сталося:

1. Агент викликав `app_screenshot` (файл `shot-20497265.png`, 308 КБ,
   `%APPDATA%\BlackChpokIDE\screenshots`).
2. Знімок автоматично потрапив у `pending_images`.
3. Модель отримала його як `image_url` і відповіла описом.

Тобто **повний цикл замкнено**: захоплення → передача → аналіз, без участі
людини.

### Але опис виявився частково неточним

Модель назвала «дерево проєкту», «термінал», «панель інструментів IDE» —
насправді на знімку був інший застосунок (веб-клієнт у браузері). Загальний
характер («вікна, чат, багато тексту») вона вгадала, конкретні елементи —
вигадала.

Це важливий висновок, який не можна приховати:

* **зображення справді дійшло до vision encoder** — інакше модель не могла б
  назвати нічого конкретного;
* **якість опису повноекранного знімка 3440×1440 недостатня** для надійної
  роботи з інтерфейсом.

Причина саме та, що описана в розділі 5: знімок іде **одним шматком**, і після
масштабування дрібні елементи стають нерозбірливими. Модель заповнює прогалини
здогадами — те саме «вигадування», яке ми виправили в текстовому шляху.

**Тому multi-scale аналіз — не покращення, а необхідна умова** для
використання зору на справжніх скриншотах. На меншому зображенні (800×552, як
у тесті з картками моделей) модель читала дрібний текст бездоганно.

## 7. Що виправлено в межах цього аудиту

| Дефект | Виправлення |
|---|---|
| Значок Vision за назвою | враховується наявність `mmproj` і результат перевірки |
| `vision_projector_for` відсікає Ministral | розширено розпізнавання `mistral3`/`ministral` |
